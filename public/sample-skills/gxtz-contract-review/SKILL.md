## 合规红线（agent 执行前必读，违反即停止）

> **第一要求：严谨合规。所有审查结论必须有法规依据，禁止主观臆断。**

### 禁止事项（违反任何一条立即停止并告警）

1. **禁止无依据判定**：每条审查结论必须引用具体法规条款（管理办法/认定规则/民法典），不得凭经验臆断
2. **禁止跳过关键审查维度**：10个审查维度必须逐一审查，不得遗漏
3. **禁止忽略上下文关联**：合同条款之间存在关联（如技术内容与知识产权归属必须对应），不得孤立审查
4. **禁止跳过脚本执行**：所有 `python {{PONOS_SKILLS}}/_common/xxx.py` 命令必须通过 Bash 真正执行
5. **禁止自行兜底**：脚本报错时不得自行编写兜底代码，必须停止并告警
6. **禁止合并/简化审查结论**：每条问题必须独立编号、独立描述，不得合并表述
7. **禁止跨技能污染**：仅读取当前项目留痕，不跨项目读取

### 法规依据层级（高 -> 低）

- **《民法典》合同编**：合同基础法律依据 -> 可直接引用
- **《技术合同认定登记管理办法》**：认定登记基本制度 -> 可直接引用
- **《技术合同认定规则》**：具体认定标准和规范 -> 可直接引用
- **《促进科技成果转化法》**：税收优惠依据 -> 可补充引用
- **地方性政策文件**：仅作为参考，不作为强制性判定依据

### 无法确认时的处理

- **法规无明确规定**：标注"法规未明确要求，建议咨询当地登记机构"
- **合同内容模糊无法判断**：标注"无法判定（需补充 xxx 信息）"
- **脚本报错**：立即停止，输出错误日志，由用户决定修复方案

### 本技能特有确认场景

以下场景需主动暂停确认：
- **合同类型模糊**：合同标题与内容不一致，无法确定属于哪类"四技"合同 -> A 类（多源冲突）
- **技术性收入占比临界**：技术性收入占比在60%临界线附近 -> B 类（接近阈值）
- **知识产权归属歧义**：条款表述存在多种解读 -> C 类（需专业判断）
- **合同附件缺失**：合同引用附件但未提供 -> D 类（材料缺失）
- **签章不规范但可补正**：骑缝章缺失、授权书未提供等 -> D 类

## 描述

本技能用于对客户提供的技术合同草稿件进行认定登记前的合规评估审查。基于《中华人民共和国民法典》合同编、《技术合同认定登记管理办法》（2026）、《技术合同认定规则》等法规，从10个维度对合同进行系统化审查，输出结构化评估报告。

## 使用场景

- 客户提供技术合同草稿件，需要评估是否符合认定登记条件
- 项目人员需要在正式提交前进行合同预审
- 用户提到"技术合同审查"、"合同评估"、"合同合规检查"
- 用户提到"技术开发合同审查"、"技术转让合同审查"、"技术咨询合同"、"技术服务合同"
- 需要了解合同存在哪些可能导致不予登记的风险点

## 审查体系总览

### 四大合同类型

| 类型 | 定义 | 关键认定要素 |
|------|------|-------------|
| 技术开发合同 | 就新技术、新产品、新工艺、新材料、新品种及其系统的研究开发所订立的合同 | 新颖性、创造性、有技术成果交付物 |
| 技术转让合同 | 就专利权转让、专利申请权转让、技术秘密转让、专利实施许可所订立的合同 | 既有技术成果、权属清晰 |
| 技术咨询合同 | 就特定技术项目提供可行性论证、技术预测、专题技术调查、分析评价报告所订立的合同 | 技术性分析评价、不涉及权属 |
| 技术服务合同 | 以技术知识解决特定技术问题所订立的合同 | 专业技术服务、一般不涉及权属 |

### 10维审查体系

| 维度 | 审查内容 | 风险等级 |
|------|---------|---------|
| 维度1-合同类型判定 | 合同是否属于"四技"合同 | 🔴 否决级 |
| 维度2-合同主体审查 | 法人资格、授权、签章 | 🔴 否决级 |
| 维度3-技术内容审查 | 技术标的、技术内容、方法路线 | 🔴 否决级 |
| 维度4-知识产权归属 | 权属约定是否明确 | 🟠 高风险 |
| 维度5-价款与报酬 | 金额明确、技术交易额计算 | 🔴 否决级 |
| 维度6-合同文本完整性 | 必备条款是否齐全 | 🟠 高风险 |
| 维度7-合同有效期 | 期限是否明确合理 | 🟡 中风险 |
| 维度8-签字盖章 | 各方签章是否规范 | 🟡 中风险 |
| 维度9-附件完整性 | 技术需求书、明细等附件 | 🟡 中风险 |
| 维度10-财务税务合规 | 技术性收入与非技术性收入区分 | 🟡 中风险 |

### 问题五级分类

| 级别 | 标识 | 含义 | 处理要求 |
|------|------|------|---------|
| F级 | 🔴 F-致命 | 直接导致不予登记 | 必须修改 |
| H级 | 🟠 H-高风险 | 极大概率为登记障碍 | 强烈建议修改 |
| M级 | 🟡 M-中风险 | 可能被要求补正 | 建议修改 |
| L级 | 🟢 L-低风险 | 可能有形式瑕疵 | 建议优化 |
| I级 | 🔵 I-信息提示 | 无合规问题，仅信息参考 | 知晓即可 |

## 第二步：维度1 - 合同类型判定（F-否决级）

### 审查要点

**2.1 判断合同是否属于"四技"合同**
- 技术开发合同：标的是否涉及新技术/新产品/新工艺/新材料的研究开发
- 技术转让合同：标的是否涉及专利权/专利申请权/技术秘密的转让或许可
- 技术咨询合同：标的是否为特定技术项目的可行性论证/技术预测/分析评价
- 技术服务合同：标的是否为运用专业技术知识解决特定技术问题

**2.2 排除非技术合同**
以下情形不属于技术合同，直接判定为F级问题：
- 一般设备维修、改装、常规设计变更
- 合同标的为当事人已掌握的技术方案（已完成产业化开发）
- 仅通过简单改变尺寸/参数/排列实现的产品改型
- 一般检验、测试、鉴定、仿制和应用
- 单纯制定规划和工作计划
- 基础性研究项目（单纯揭示自然现象/规律/特征）
- 软件复制和无原创性的程序编制
- 就经济分析/法律咨询/社会发展项目论证订立的合同
- 就购买设备/仪器/原材料/配套产品提供商业信息订立的合同
- 常规手段的加工承揽合同和建设工程合同

**2.3 合同标题与内容一致性**
- 合同标题应与实际内容一致
- 标题使用规范名称（"技术开发（委托）合同"/"技术转让合同"/"技术咨询合同"/"技术服务合同"）

### 判定脚本
```bash
python {{PONOS_SKILLS}}/gxtz-contract-review/contract_review.py classify --contract-json <合同内容JSON> --output <评估JSON>
```

### 输出
- 合同类型判定结果及依据
- 是否符合认定条件
- 若不符合，列出具体原因


## 第三步：维度2 - 合同主体审查（F-否决级）

### 审查要点

**3.1 法人资格审查**
- 签约主体是否具有独立法人资格
- 分公司签约：是否具有独立法人资格（不具有的需附总部授权书）
- 内部机构签约：是否取得法定代表人书面授权

**3.2 主体信息完整性**
- 双方名称是否完整准确（与营业执照一致）
- 统一社会信用代码是否填写
- 法定代表人/授权代表人信息是否完整
- 联系人、联系电话、通讯地址是否填写

**3.3 主体资质匹配**
- 技术开发方/转让方是否具备相应技术能力
- 经营范围是否包含合同涉及的技术领域

### 审查脚本
```bash
python {{PONOS_SKILLS}}/gxtz-contract-review/contract_review.py check-parties --contract-json <合同内容JSON> --output <评估JSON>
```


## 第四步：维度3 - 技术内容审查（F-否决级）

### 审查要点

**4.1 技术标的是否明确**
- 技术标的描述是否清晰，能否使登记人员了解其技术内容
- 是否包含具体的技术目标、技术内容、技术方法和路线

**4.2 技术开发合同特有要求**
- 是否具有新颖性（当事人在订立合同时尚未掌握的技术）
- 是否有明确的开发过程描述
- 合同成果是否有创新点
- 提交的成果是否为相对完整的可实施技术方案
- 同一标的是否只签订一次（重复签订视为非技术开发合同）
- 是否有明确的技术成果交付物

**4.3 技术转让合同特有要求**
- 技术成果权属是否清晰
- 合同标的不得为已进入公有领域的技术
- 技术秘密转让是否约定了转让权或使用权归属
- 高新技术产品交易是否包含技术转让成分（仅有产品交易不属于技术转让）

**4.4 技术咨询合同特有要求**
- 是否为特定技术项目的咨询课题
- 是否运用科学知识和技术手段进行分析/论证/评价/预测
- 目的是否为委托方在科研/技术开发/成果推广等方面提出建议/意见/方案

**4.5 技术服务合同特有要求**
- 是否运用专业技术知识/经验/信息解决特定技术问题
- 服务内容是否包含：改进产品结构/改良工艺流程/提高产品质量/降低产品成本/节约资源能耗/保护资源环境/实现安全操作等
- 是否以非常规技术手段解决复杂/特殊技术问题

### 审查脚本
```bash
python {{PONOS_SKILLS}}/gxtz-contract-review/contract_review.py check-tech-content --contract-json <合同内容JSON> --contract-type <合同类型> --output <评估JSON>
```


## 第五步：维度4 - 知识产权归属（H-高风险）

### 审查要点

**5.1 技术开发合同知识产权归属**
- 必须明确约定技术成果的归属（委托方所有/双方共有/开发方所有）
- 计算机软件开发合同：知识产权必须约定归甲方（委托方）或双方共有，方可登记免税
- 必须明确双方的权利义务（使用权/转让权/收益分配）

**5.2 技术转让合同知识产权归属**
- 专利转让：须明确专利号、专利名称、专利权人
- 技术秘密转让：须明确技术秘密的内容和范围
- 软件著作权转让：须明确办理著作权变更手续

**5.3 技术服务/咨询合同**
- 一般不涉及知识产权权属约定
- 若涉及新产生的技术成果，必须明确约定归属

### 审查脚本
```bash
python {{PONOS_SKILLS}}/gxtz-contract-review/contract_review.py check-ip-rights --contract-json <合同内容JSON> --contract-type <合同类型> --output <评估JSON>
```


## 第六步：维度5 - 价款与报酬（F-否决级）

### 审查要点

**6.1 金额明确性**
- 合同价款/报酬/使用费是否明确约定
- 约定不明确的 → 不予登记
- "提成支付"方式：初次登记时合同交易额为首次支付金额

**6.2 技术交易额计算**
- 技术交易额 = 合同成交额 - 非技术性费用（设备/仪器/零部件/原材料等）
- 合理数量标的物的直接成本不计入非技术性费用
- 成套技术设备和试验装置一般限于1-2套

**6.3 技术性收入占比**
- 技术性收入占合同总金额的比例应合理
- 非技术性收入应有明确构成说明（管理费/折旧费等）
- 技术性收入占比过低可能导致实质审查不通过

**6.4 支付方式**
- 支付方式是否明确（一次性/分期/提成）
- 分期支付：各期金额和支付时间是否明确

### 审查脚本
```bash
python {{PONOS_SKILLS}}/gxtz-contract-review/contract_review.py check-pricing --contract-json <合同内容JSON> --output <评估JSON>
```


## 第七步：维度6-10 合同文本综合审查

### 7.1 维度6 - 合同文本完整性（H-高风险）

审查以下必备条款是否齐全：
- 项目名称（使用规范名称，完整准确表达合同内容）
- 标的内容、范围和要求
- 履行的计划、进度、期限、地点和方式
- 技术情报和资料的保密
- 风险责任的承担
- 技术成果的归属和收益的分配办法
- 验收标准和方法
- 价款或者报酬及支付方式
- 违约金或者损失赔偿的计算方法
- 解决争议的方法
- 名词和术语的解释（必要时）

**框架协议无法认定为技术合同**。

### 7.2 维度7 - 合同有效期（M-中风险）

- 合同必须有明确的有效期限
- 技术开发期限不能替代合同有效期
- 合同结束日期须大于认定登记填报日期超过十五个工作日
- 合同必须在有效期内（未生效或已过期的合同不予登记）

### 7.3 维度8 - 签字盖章（M-中风险）

- 双方签字盖章是否正规、齐全
- 法人：法人公章或合同专用章 + 法定代表人（授权人）签名或盖章 + 授权书
- 自然人：本人签名或盖章
- 非法人组织：组织印章 + 组织负责人签名或盖章
- 超过三页的合同建议加盖骑缝章
- 书写名称与印章要求一致、清晰
- 签署页必须有签订日期
- 合同非原件彩色扫描件（签章页为替换页）→ 不予认可
- 补充协议须双方签字盖章

### 7.4 维度9 - 附件完整性（M-中风险）

- 合同引用的附件是否全部提供
- 若使用模板合同但实际无附件，建议删除附件名称或在附件后标注"无"
- 技术需求说明书：技术开发合同建议附上技术需求说明书
- 财务情况说明：涉及金额拆分的建议附财务情况说明

### 7.5 维度10 - 财务税务合规（M-中风险）

- 技术性收入与非技术性收入是否区分核算
- 关联交易（100%关联）不享受所得税优惠，可免增值税
- 技术开发费能否开具增值税专用发票：不能（免税项目不得开具专票；开专票=放弃免税资格，36个月内不得再申请）
- 合同金额为外币的需换算为人民币备案，汇率由买卖双方约定

### 综合审查脚本
```bash
python {{PONOS_SKILLS}}/gxtz-contract-review/contract_review.py check-comprehensive --contract-json <合同内容JSON> --contract-type <合同类型> --output <评估JSON>
```

```bash

  --contract-name "合同名称"  \
  --output-dir <Word报告输出目录>
```

### 8.3 报告结构

评估报告包含以下部分：

**一、评估概要**
- 合同基本信息（企业名称、合同名称、评估日期、评估依据）
- 总体评估结论（通过/有条件通过/不予通过）
- 问题统计表（F级/H级/M级/L级/I级数量及合计）

**二、各维度审查明细**
- 10个维度逐一列出审查结果
- 每项标注：✓ 通过 / ⚠ 警告 / ✗ 不通过（含颜色区分）
- 每个问题标注级别（F/H/M/L/I）+ 法规依据 + 整改建议

**三、整改建议汇总**
- 按优先级排列的整改建议清单
- 每条建议标注：整改项、当前状态、整改方案、法规依据

**四、政策适用提示**
- 可享受的税收优惠（增值税减免/所得税减免）
- 研发费用加计扣除适用性
- 技术合同认定登记后奖酬金提取规则
- 关联交易注意事项

**五、风险评估**
- 综合风险等级
- 不予登记的风险评估
- 影响登记的关键因素

### 8.4 Word 报告排版特性

Word 版报告（.docx）具有以下专业排版：
- 封面标题（深蓝色大标题 + 灰色副标题）
- 基本信息表格（标签栏蓝底白字）
- 问题统计表（6列彩色标注）
- 各维度审查明细（按风险等级颜色编码：红🔴F / 橙🟠H / 黄🟡M / 绿🟢L / 蓝🔵I）
- 政策优惠对照表
- 风险等级颜色标注（高风险红色、低风险蓝色）
- 页脚声明

### 8.5 输出文件

生成以下文件：
- `{企业名称}_合同评估报告_{合同名称}.md` - Markdown格式评估报告
- `{企业名称}_合同评估报告_{合同名称}.docx` - Word格式正式评估报告（专业排版）
- `{企业名称}_合同评估明细_{合同名称}.json` - 结构化审查数据
- `{企业名称}_整改建议清单_{合同名称}.md` - 整改建议清单


## 第八步补充：源文件审查批注

### 8A.1 功能说明

可在客户提供的源合同文件（.docx）中直接插入审查批注（Word注释），标注具体问题点位、问题描述、法规依据和改正建议。**批注版另存为新文件，不修改原始合同**。

### 8A.2 批注内容

每条批注包含：
- 问题等级标识（🔴F/🟠H/🟡M）+ 问题编号
- 问题标题
- 问题描述
- 法规依据
- 整改建议

I级（信息提示）问题统一在文档末尾以汇总批注形式呈现。

### 8A.3 执行命令

```bash
python {{PONOS_SKILLS}}/gxtz-contract-review/contract_review.py annotate-contract  \
  --source-contract <源合同文件路径(.docx/.doc)>  \
  --review-results <审查结果JSON文件路径>  \
  --output-dir <批注版输出目录>
```

### 8A.4 支持格式

| 源文件格式 | 处理方式 |
|-----------|---------|
| .docx | 直接添加批注 |
| .doc | 自动调用 doc_toolkit.py 转换为 .docx 后添加批注 |
| .pdf | 不支持批注，请使用 PDF 注释工具另行处理 |

### 8A.5 输出文件

- `{合同文件名}_审查批注版.docx` - 含审查批注的合同副本（原始合同不受影响）

### 8A.6 批注定位规则

系统根据各维度关键词自动在合同文本中定位问题位置：
- 合同类型判定 → 搜索关键词：技术开发/技术转让/技术咨询/技术服务/标的
- 合同主体审查 → 搜索关键词：甲方/乙方/法定代表人/统一社会信用代码
- 技术内容审查 → 搜索关键词：技术目标/技术内容/创新/交付
- 知识产权归属 → 搜索关键词：知识产权/归属/成果/专利/著作权
- 价款与报酬 → 搜索关键词：金额/价款/报酬/支付
- 其他维度类似规则

若无法在文档中精确定位到对应段落，会输出 WARN 提示，但仍会继续处理其他可定位的问题。
