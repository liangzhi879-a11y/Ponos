## 质疑与协同审查机制（agent 发现不符时必须质疑，禁止默认执行）

> **核心原则：当 agent 发现撰写的资料或用户要求与现实资料不符时，必须明确与用户确认并提供质疑依据，禁止默认执行、禁止悄悄自行纠正。**

### 适用场景

本机制适用于"产出内容与现实资料的对照"场景，与"自主确认机制"互补：
- 自主确认机制：识别执行过程中的数据冲突/异常/缺失/推断
- 质疑审查机制：识别产出内容或用户要求与现实资料的实质性不符

### 四类触发场景

| 类型 | 触发场景 | 核心判别逻辑 | 示例 |
|------|---------|-------------|------|
| **E 类** | 撰写内容与原始资料不符 | agent 撰写的 RD/PS/IP/制度等内容与原始辅助账、发票、证书等不一致 | 撰写 RD 名称"LCM 测试软件"但辅助账中是"显示驱动板研发" |
| **F 类** | 用户要求与数据可行性不符 | 用户要求的数量/范围/金额等超出现有资料支撑 | 用户要求 10 个 PS 但发票仅覆盖 5 个产品方向 |
| **G 类** | 跨技能/跨表数据不一致 | 同一字段在不同表/技能中描述不同 | IP 表与 RD 表对同一 IP 的技术领域描述不同 |
| **H 类** | 计算结果与原始资料不符 | 金额加总、占比、天数等计算与原始资料不符 | 研发费用加总与辅助账合计不一致；科技人员天数计算错误 |

### 每步产出后自问速查

agent 在每次产出内容（撰写文档、填写表格、生成报告）后，必须自问以下 6 个问题。任一答案为"是"，立即暂停并启动质疑流程：

- [ ] 我撰写的内容是否与原始资料（辅助账/发票/证书/台账）逐字对照一致？（E 类）
- [ ] 用户的要求是否有原始资料支撑？数量/范围/金额是否在资料覆盖范围内？（F 类）
- [ ] 同一字段在多个表/技能中是否描述一致？（G 类）
- [ ] 我的计算结果（加总/占比/天数）是否与原始资料一致？（H 类）
- [ ] 我是否在"悄悄纠正"某个差异而未告知用户？（禁止行为）
- [ ] 如果我继续执行，是否会产出与事实不符的资料？（质量保证）

### 质疑交互规范（使用 AskUserQuestion 工具，减少对话打断）

当 agent 发现不符时，按以下两步执行：

**第一步：输出质疑依据**（文本格式，必须包含具体数据支撑）

```
⚠️【质疑审查】[触发类型：E/F/G/H] - [步骤名称/产出物名称]

📋 质疑依据：

【原始资料】
- 来源：[文件完整路径]
- 位置：[Sheet名/段落/行号]
- 原文内容：[逐字引用]

【agent 产出或用户要求】
- 位置：[产出文件路径/表格行号]
- 内容：[逐字引用]

【差异说明】
- 原始资料显示：[X]
- 产出/要求显示：[Y]
- 差异性质：[实质性不符 / 数量超出支撑 / 描述不一致 / 计算错误]

⚠️ 影响评估：如不修正，将导致 [具体后果]

✅ 推荐方案：[方案X]
理由：[推荐理由，必须基于"严谨合规"原则]
```

**第二步：调用 AskUserQuestion 工具**（让用户点击选择，无需手动输入）

agent 必须使用 AskUserQuestion 工具提供结构化选项，格式如下：
- question: 质疑摘要+差异说明（如"RD名称撰写为'LCM测试软件'但辅助账中是'显示驱动板研发'，请选择以哪个为准？"）
- header: 短标签，≤12字符（如"内容不符"、"数量超限"、"跨表不一致"、"计算错误"）
- options: 每个方案一个选项（2-4个），推荐方案放第一个并标注"(推荐)"
  - label: 方案简称，1-5个字
  - description: 方案详情+影响评估
- multiSelect: false

**示例：**
```json
{
  "questions": [{
    "question": "RD名称撰写为'LCM测试软件'但辅助账中是'显示驱动板研发'。原始资料显示应为后者。请选择处理方案：",
    "header": "内容不符",
    "options": [
      {"label": "(推荐)用辅助账", "description": "以辅助账'显示驱动板研发'为准，真实可溯源，避免专审核对失败"},
      {"label": "用撰写内容", "description": "保持'LCM测试软件'，但与辅助账不符，专审核对会报错"},
      {"label": "合并调整", "description": "合并两个名称为'显示驱动板(LCM)研发'，兼顾两者但需确认辅助账方同意"}
    ],
    "multiSelect": false
  }]
}
```

**关键规则：**
1. 必须先输出文本质疑依据（含文件路径、位置、原文引用），再调用AskUserQuestion
2. 推荐方案必须放在options第一个，label前加"(推荐)"
3. 用户选择"Other"时表示要自定义方案，agent应按用户输入执行
4. 禁止只输出文本"请确认"而不调用AskUserQuestion工具
5. 禁止只调用AskUserQuestion而不输出文本质疑依据（用户需要完整数据支撑才能决策）

### 禁止行为（6 条）

1. **禁止默认执行**：发现不符时不得继续执行，必须暂停
2. **禁止悄悄纠正**：不得在未告知用户的情况下"自行纠正"差异
3. **禁止空泛质疑**：质疑必须包含具体文件路径、位置、原文引用
4. **禁止替代用户决策**：agent 提供方案和推荐，但决策权在用户
5. **禁止忽略差异**：任何实质性不符都必须质疑，不得"小事化了"
6. **禁止跳过质疑依据**：必须提供原始资料引用，否则质疑无效

### 人机协同审查流程

```
agent 产出 → 自问6个问题 → 发现不符？
                              ├─ 是 → 启动质疑流程（提供依据→方案对比→推荐→等待）
                              │        ↓
                              │     用户决定 → 执行用户方案 → 记录到留痕
                              │
                              └─ 否 → 继续执行下一步
```

### 质疑记录要求

每次质疑必须在 .trae/working_trace.md 中记录：
- 质疑类型（E/F/G/H）
- 质疑依据（原始资料引用）
- 用户决定（采纳的方案）
- 执行结果（是否按用户决定执行）
