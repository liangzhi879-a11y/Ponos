# yfwdoc-word — 企业Word文档生成与排版

企业咨询场景的 Word 文档专业制作技能，覆盖公文、标书、合同、日常信函四大类，提供模板化生成、样式目录、邮件合并与修订痕迹全流程。

## 3. 合规红线（不可逾越）

1. **禁止编造内容**：文号、日期、主送机关、正文事实、金额、条款只能来自用户提供的信息。缺失必须暂停询问，禁止"合理补充"或编造。
2. **禁止跳过人工审核闸门**：任何交付用户的 .docx 必须经用户审核确认；审核通过前禁止交付终稿、禁止声称"已完成"。
3. **禁止AI水印**：遵循 `C:/Users/T203-15/.yfworking/skills/_common/SHARED_no_ai_watermark.md`——输出文档中禁止出现AI生成提示、水印、示例占位残留；未确认项以"【待用户确认】"显式标注而非占位符。
4. **禁止覆盖用户文件**：不修改用户原始文件；多版本并存输出，禁止静默覆盖。
5. **扫描件/图片内容**：若需从图片提取文字，遵守 `C:/Users/T203-15/.yfworking/skills/_common/SHARED_ocr_mandatory.md`——先OCR后操作，禁止凭文件名猜测内容。

## 4. 自主确认机制

遵循 `C:/Users/T203-15/.yfworking/skills/_common/SHARED_autonomous_confirmation.md` 的5原则（数据一致性/完整性/推断性/异常性/质量保证）。Word场景高发确认点：

| 触发类型 | 场景 | 处理 |
|---------|------|------|
| A 数据源冲突 | 同一内容（如发布日期）在用户提供的多个来源中不一致 | 暂停，列出各来源，请用户指定 |
| B 格式异常 | 用户给出 .doc/PDF 旧版要求直接套模板 | 先转换/读取，确认内容后再生成 |
| C 关键推断 | 文号建议格式、正文需补充公司简介等推断性内容 | 说明推断依据，用户确认后才填入 |
| D 资料不完整 | 文号/日期/落款/主送机关缺失 | 暂停，列缺失清单请用户补充 |

确认方式：先输出文本问题描述（含方案对比表），再调用 AskUserQuestion 提供结构化选项，禁止只喊"请确认"。

## 5. 执行顺序契约

本技能严格按以下顺序执行，**禁止跳步、禁止并行**：

```
步骤1 确认文档类型 → 步骤2 收集内容要点 → 步骤3 选择模板
→ 步骤4 生成初稿 → 步骤5 人工审核闸门 → 步骤6 输出交付
```

- 仅当步骤5审核通过，才执行步骤6
- 任一中间步骤触发自主确认机制，**冻结后续步骤**直到用户明确答复
- 上一步骤验证标准未通过，不得进入下一步骤

## 6. 工作流

### 步骤1：确认文档类型

**输入**：用户原始需求描述
**操作**：从以下分类锁定唯一类型（多类型或含糊时用 AskUserQuestion 单选）：

| 类别 | 子类 | 模板来源 |
|------|------|---------|
| 公文类 | 红头文件/通知/函/会议纪要/简报 | 公文模板库 |
| 商务类 | 标书/方案书/立项报告 | 商务模板库 |
| 法律类 | 合同/协议/意向书 | 合同模板库（仅搭框架，条款须用户提供或法务确认） |
| 日常类 | 信函/便签/公告 | 通用模板库 |

**输出**：`{文档类型, 模板库类别}`
**验证标准**：类型唯一；用户表述含糊（"帮我写个东西"）时必停确认，禁止自行假设

### 步骤2：收集内容要点

**输入**：文档类型
**操作**：按类型结构化收集（清单式提问，逐项记录来源）：
- **公文**：发文机关、文号、标题、主送机关、正文要点（何时/何地/何事/何要求）、落款单位、日期
- **标书**：项目名称、招标编号、响应范围、技术要点、商务要点、资格材料清单
- **合同**：主体双方、标的、金额、期限、条款清单（由用户提供；拿不准的法律条款标注"需法务确认"）
- 正文中的数字、引文、政策条款**必须逐条注明来源**

**输出**：`content_plan.json`（结构化内容要点，每条事实性内容带来源标注）
**验证标准**：完整性自检——文号/日期/落款等关键项缺失时暂停补问（D类）；任何推断性内容先确认后填入

### 步骤3：选择模板

**输入**：文档类型 + 模板库
**操作**：
1. 查模板库注册表：读 `C:/Users/T203-15/.yfworking/skills/yfwdoc-template/_templates/template_index.json`（或 `ls` 该目录）
2. 无匹配模板 → 提示用户先运行 yfwdoc-template 技能创建/注册模板，或选用通用模板
3. 校验品牌合规：颜色/字体/Logo 是否符合用户企业品牌规范（查 yfwdoc-template 的 `brand_spec_*.json`）

**输出**：选定模板文件路径 + 模板类型
**验证标准**：模板存在且类型匹配；同类型多模板时展示对比由用户选择，禁止擅自决定

### 步骤4：生成初稿

**输入**：选定模板 + content_plan.json
**操作**：
```bash
# 1) 读取模板结构（样式/占位符/分节）
python "C:/Users/T203-15/.yfworking/skills/_common/doc_toolkit.py" info --file "<模板路径>"
python "C:/Users/T203-15/.yfworking/skills/_common/doc_toolkit.py" read --file "<模板路径>" --format docx

# 2) 按 content_plan 组装内容 JSON（段落/标题/表格/落款），写入初稿
python "C:/Users/T203-15/.yfworking/skills/_common/doc_toolkit.py" write ^
    --file "初稿_通知_20260804_v1.docx" --format docx --data-file content_docx.json
```
- **样式与目录**：模板已带样式时严格保留；需自动目录/页眉页脚/分节时，用 python-docx 直编脚本补充（标题样式层级 + TOC域 + 页眉页脚），生成后读取校验样式生效
- **邮件合并**：读收件人表（`doc_toolkit.py read --file 名单.xlsx --format xlsx`），按行生成合并文档，输出到 `{输出目录}/mailmerge/收件人_文档.docx`；合并前确认正文中替换字段标记与表头一致
- 未确认项（文号/日期等）以 **【待用户确认】** 显式标注写入初稿，**禁止编造数值**

**输出**：`初稿_{类型}_{标题}_{YYYYMMDD}_v1.docx`
**验证标准**：初稿覆盖 content_plan 全部要点；所有事实性内容有来源；模板样式保留；占位项全部为【待用户确认】形式而非虚构

### 步骤5：人工审核闸门（Human-in-the-Loop，强制）

**输入**：初稿
**操作**：
1. 逐项自检：事实性内容是否有来源、格式一致性（标题层级/字体/编号）、【待用户确认】项清单是否完整
2. 输出《修订说明清单》：逐条列出待确认项（文号/日期/落款/条款）及建议值、修改建议
3. 将初稿 + 清单交用户审核，**等待明确回复**；禁止默认用户同意

**验证标准**（全部满足才进入步骤6）：
- [ ] 用户明确回复"审核通过"或逐项确认了修订说明清单
- [ ] 文号、日期、落款、金额、条款等关键字段全部由用户提供或确认
- [ ] 正文无【待用户确认】残留、无虚构内容
- [ ] 若用户提出修改意见 → 生成 v2 + 修订说明，再次走本闸门，禁止直接跳到输出

**输出**：审核通过的终稿（v2+）或退回重做的修订需求
**验证标准**：用户明确确认——此步骤无任何绕过途径

### 步骤6：输出交付

**输入**：审核通过的终稿
**操作**：
- 输出终稿：`{用户指定目录}/{类型}_{标题}_{YYYYMMDD}_终版.docx`
- **修订痕迹模式**：如需留痕，同步输出 `_修订说明.docx`（初稿→终稿逐条变更对照），禁止覆盖初稿
- 汇报交付摘要：文档类型/使用模板/主要变更点/待用户补充事项（如有）

**输出**：终版 .docx + 交付摘要
**验证标准**：文件可打开、格式完整、命名符合规范；交付清单与用户审核确认一致；用户未确认的内容一律未出现

## 7. 修订痕迹模式说明

- **场景**：用户在初稿基础上提出修改意见 → 输出新版本，并用《修订说明》记录"修改前→修改后"逐条对照
- **禁止**：直接覆盖 v1 且无变更记录；把用户口头意见自行扩大范围（疑问时暂停确认）
- **多轮修订**：版本号递增（v1→v2→v3），每轮保留，终稿必须对应最后一轮用户确认
