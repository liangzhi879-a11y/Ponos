# 修复：知识库数据根错位（`~/.ponos` vs `~/.yfw`）+ 索引重建超时

- **日期**：2026-09-17
- **症状**：知识库面板"显示不出来"——面板内容其实是**另一个根里的旧数据**；把数据根修正后，又暴露出重建超时导致面板卡死。
- **关联**：与同日的 `docs/2026-09-17-打包版渲染层401修复.md` 是两条独立缺陷（一个在渲染层→桥，一个在桥→内核）。

## 1. 根因 A：知识库路由 spawn 内核时漏注 env，内核回落 `~/.ponos`

内核 CLI 的 `resolveConfigDir` 解析顺序是 `PONOS_CONFIG_DIR > PONOS_HOME > ~/.ponos`，**不认
`YFWORKING_HOME`**（`kernel/config.mjs`）。而 `server/bridge.mjs` 调 `handleKnowledgeRoute` 时
两个内核入口（`callKernel`/`spawnStream`）都没传 env，路由的默认实现是裸的
`kernelReadonly`/`spawnKernelStreaming` ⇒ `env = process.env`，而**桥进程里没有
`PONOS_CONFIG_DIR`**（它是 spawn 内核时逐个子进程注入的）⇒ 内核落到 `~/.ponos`。

对照实证（同一桥、同一时刻）：

| 端点 | 返回的根 |
|---|---|
| `GET /knowledge/spaces`（漏注，走内核默认） | `C:\Users\…\.ponos\memory\personal`（**旧根**） |
| `GET /workflows`（桥自己解析） | `C:/Users/…/.yfw/workflows`（正确） |
| `GET /usage/*`（显式传了 `buildChildEnv()`） | 正确 |

三处代码自证设计意图是**单根 `~/.yfw`**：`buildChildEnv()` 注释把 `~/.ponos` 称作"另一个根""写进
黑洞"；`kernel/knowledge.mjs` 注释写"用户的 `~/.yfw/memory/personal`"；用量聚合路径的注释称
"唯一影响聚合结果的是 `PONOS_CONFIG_DIR ← YFW_HOME`"。

**修复**（默认值层治本，而非只修调用点）：

- `server/knowledge-routes.mjs` 新增导出 `knowledgeKernelEnv(home)`，并把两个默认实现绑定到它：
  `callKernel = callKernel || ((args, opts = {}) => kernelReadonly(args, { ...opts, env: opts.env || env }))`
  （`spawnStream` 同理）。**为什么修默认值**：这个坑的成因就是"调用方忘了传"，只修调用点等于把
  地雷留给下一个调用方。
- `server/bridge.mjs` 调 `handleKnowledgeRoute` 时显式传 `kernelEnv: buildChildEnv()`（生产链路要
  完整注入，且 `kernel/knowledge-import.mjs` 的 python 解析读 `YFWORKING_PYTHON`——**扫描件导入
  的 OCR 依赖它**，缺了会退回系统 `python` 而失败）。同时改为只在 `pathname` 命中 `/knowledge`
  时构造（`loadConfig()` 每次读盘）。
- `server/knowledge-routes.mjs` 的 `handleImport` 显式把 env 交给 `startImportJob`
  （不依赖 `spawnStream` 的 wrapper 兜底；注意不能传 `null`——spawn 的 `env = process.env`
  默认值只在 `undefined` 时生效）。

## 2. 根因 B（修好 A 才暴露）：索引重建 104s > 60s 超时 ⇒ 永远建不完

改完 env 后实测：内核在 `~/.yfw` 根下 `--knowledge spaces` **挂住**（CPU 满载），而在 `~/.ponos`
下 1.6s 返回。逐层定位：

1. 进程 CPU 采样：Δ≈5.33s/5s（**单核满载**）⇒ 不是等锁/等网络，是算。
2. 最小复现：`config.json` 单独 → 正常；`+ knowledge` → 正常；`+ memory` → **挂**；`memory` 去掉
   `session` 仍挂 ⇒ 元凶在 `memory/personal`。
3. 文件级：`personal` 去掉 `workflow.md` → 正常；只放 `workflow.md` → 挂（**436 个条目块**）。
4. 放长跑：`reindex --force` 约 **104 秒**后**成功**完成（不是死循环，是太慢）。

而 `server/kernel-readonly.mjs` 的超时是 **60s** ⇒ 索引一过期，面板每次请求都在重建中途被 kill，
**索引永远建不完**（表现为知识库卡死/超时）。

**代码级根因**：`buildRelations`/`relateIncremental` 对每个条目遍历空间池（N×M 次
`relatedCandidates`），而 `relatedCandidates` 对池里**每个**成员都现算一次
`vectorizeText`（切 gram + 归一化）与 `cosine`（内部 `new Map(b)`）⇒ 耗时随库体积**平方**增长。
本模块校准注释里假设的库是"76 条 ≈ 5776 次"，实际已到 436 条（19 万次，33 倍）。

**修复**（纯等价变换，不改变任何判定）：

- `kernel/knowledge.mjs` 新增 `precomputeRelVecs(pool, idf)`：按**同一 idf**给池里每项各向量化
  一次（N 次而非 N² 次），挂到池对象的 `relVec`/`relVecMap`（`relatablePool()` 每次新建对象，不
  污染索引里的块），并在 `buildRelations` 与 `relateIncremental` 两条路径都调用。
- `shared/knowledge-core.mjs`：`relatedCandidates` 优先用 `block.relVec`/`p.relVecMap`（没有就现算，
  兼容检索/注入等调用方）；`cosine(a, b)` 支持 `b` 直接传 `Map`（此前每次 `new Map(b)` 复制一遍）。

**效果**：

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 74 文档 / 1124 块 全量重建 | 104s | **5s** |
| 221 文档 / 4636 块（含新迁入的「政策」148 篇） | 未测（外推 >600s） | **8s** |
| `--knowledge spaces`（索引新鲜） | — | **1s** |
| 回归护栏：430 条模拟库 | 同规模 ≈104s | **3.4s** |

## 6. 遗留 / 注意

1. **本次改动需重启应用生效**（`server/*` 与 `kernel/*` 均为进程启动时加载）——已于 2026-09-17 重启并核验通过。
2. `~/.ponos` 里的旧数据（8/21–8/25 的 149 篇旧会话记忆等）**未迁移**（用户选择只迁「政策」），
   面板切到新根后将不再显示那批旧记忆——属预期，原数据仍在原地。
3. 经验库单文件（个人记忆目录 `~/.yfw/memory/personal/` 下的 `workflow.md`）已 436 条 / 778KB。本次修复让重建不再超时，但该文件
   继续线性增长会推高重建耗时（现为平方项主导 → 优化后为"池向量 N 次 + N² 次点积"）。若将来条目
   数上千，建议按主题拆分文件（对重建成本**无帮助**，但利于人工维护与增量更新粒度）。
4. **【已知隐患，用户决定暂不处理】单文件块数上限截断**：重建索引时内核告警
   `memory/session/会话蒸馏/2026-09-11-执行技能-using-s-17891222.md` 共 **4128 块 / 614KB**，
   超 `MAX_BLOCKS_PER_DOC = 2000`（`kernel/knowledge.mjs:494`），**尾部 2128 块未索引 ⇒ 该文件
   后半部分检索不到**。内核设计注释假设"当前单文件最大 239 留 ~8× 余量"，实际语料已超出一个量级；
   机制本身是"截断必须出声"（`capBlocks`），故不属静默丢失。若将来需要检索该文件完整内容，
   出路是拆分该文件（或提高上限并评估重建成本）。
5. 建议在**面板首屏**再做一次耗时观察：本次实测 `spaces`/`tree` 均 1.5~1.8s（内核子进程冷启动为主），
   若后续觉得慢，可考虑给只读内核加常驻进程（属功能改造，不在本次范围）。
