## 摘要
本期视频讲解了上下文缓存（Context Caching）的工作原理：多轮对话中，前面已计算过的上下文可以被复用，只需重算新增部分，从而省时省钱。作者强调核心规则是"只往后追加"（append only），不改历史前缀。同时指出缓存命中率并非越高越好，它只是手段，真正重要的是智能体能否把活干完。


### 亮点
- 💡 每轮对话并非只发最新一句，而是带上全部上下文；缓存机制让之前算过的部分可直接复用，只需重算新增内容 [00:00]
- 📌 缓存最核心的规则：前面别动，只往后追加（append only）。这样命中率会越来越高，90% 并不稀奇，因为新内容本来占比就小
- ⚠️ 修改系统提示词、改变工具定义、重写历史、做上下文压缩都会让前缀对不上，导致缓存失效 [00:00]
- ⏰ 缓存不是永久免费的，需要占用显存、内存、硬盘；Claude Code 主对话默认一小时缓存，DeepSeek 官方说尽力而为，一般保存几小时到几天，Codex 未公开明确时长——规则会改，真正在意就看各家最新官方文档
- 🔍 缓存过期不等于上下文丢了，只是下次可能需要重新计算
- 📉 Claude Code 整体缓存命中率不高的一个重要原因：普通子智能体是全新隔离的上下文，会产生很多"冷"上下文（不过也有 fork 分叉可以直接继承完整上下文）
- 🧠 缓存命中率不代表智能体能力；开子智能体可以减少主上下文污染，把任务做得更好，少命中几个百分点无所谓
- 🎚️ 思考强度滑块若在长对话里高低来回切，可能破坏前缀缓存；Claude 和 DeepSeek 现在支持"往后追加"的方式调整——把新配置追加到末尾，而非回头改最前面
- ✨ "只往后追加"最漂亮的地方：状态可以变，但尽量不修改过去
- 🎯 缓存命中率重要（省钱、减少重复计算、降低延迟），但只是手段。99% 命中却没干完活没有意义；该开子智能体就开、该压缩就压缩、把任务解决掉更重要——缓存应服务于任务，而不是让任务服务于缓存

### 思考
1. **[缓存命中率高就代表智能体更强吗？](https://bibigpt.co/search?q=%E7%BC%93%E5%AD%98%E5%91%BD%E4%B8%AD%E7%8E%87%E9%AB%98%E5%B0%B1%E4%BB%A3%E8%A1%A8%E6%99%BA%E8%83%BD%E4%BD%93%E6%9B%B4%E5%BC%BA%E5%90%97%EF%BC%9F)**
  - 不代表。缓存命中率与智能体的干活水平不挂钩。子智能体会产生冷上下文从而降低命中率，但它能减少主上下文污染、把任务做得更好，所以少命中几个百分点无所谓。

2. **[缓存会永久保存吗？](https://bibigpt.co/search?q=%E7%BC%93%E5%AD%98%E4%BC%9A%E6%B0%B8%E4%B9%85%E4%BF%9D%E5%AD%98%E5%90%97%EF%BC%9F)**
  - 不会。算好的缓存需要占用显存、内存、硬盘，无法免费永久保留。Claude Code 主对话默认一小时缓存，DeepSeek 是"尽力而为"，一般几小时到几天，Codex 未公开明确时长，规则也会变，建议看官方最新文档。缓存过期也不代表上下文丢失，只是下次可能要重新计算。


### 术语解释
- **上下文缓存（Context Caching）**：多轮对话时复用之前已计算过的上下文部分，只重新计算新增内容，从而降低费用和延迟 [00:00]
- **Append Only（只往后追加）**：缓存的核心规则——不改动前面的历史前缀，只往末尾追加新内容，这样前面部分始终可复用
- **子智能体（Sub Agent）**：主智能体派出去独立执行任务的隔离上下文，自己去读文件、搜索、执行，最后把结果返回主线程
