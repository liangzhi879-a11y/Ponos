## 0. 结论摘要（先给判断，再给论证）

1. **本应用的缓存瓶颈不是"要不要开缓存标记"，而是"历史被事后原地改写"。** 视频最硬的一条原则是 append-only；本应用为省上下文，每个工具迭代都可能把历史**中段**的旧工具结果原地改写成占位标记（`kernel/compact.mjs:54-60`、`190-206`），且改写点随会话推进不断**前移**。这是命中率的头号杀手，量级大于任何参数调优。
2. **`cache_control` 在多端点下必须按端点分流**：Anthropic 官方**不打标记就是 0 命中**；DeepSeek 端点**明确忽略该字段**、缓存自动生效。当前 `PONOS_PROMPT_CACHE` 是全局手工 env（`kernel/api.mjs:1420`，**默认关**），在多端点混用下两头不讨好。
3. **优化排序**：① 先把观测口径修对（含端点用量字段别名）→ ② 把 system/tools 的易变内容移出前缀前部 → ③ 把工具结果的"压缩"从**事后改写**提前到**记录时限流** → ④ 才轮到断点分层与阈值参数。
4. **一条对已有计划的修正**：`2026-09-18-prefix-cache-observability.md`（worktree 备份态）的 **H2 假设方向疑似反了**（详见 §3.3 实测），实施前应先修正，否则会拿反向预期判实验；§3.4 另有与 v2 增补 A1/A4/A5/A6 的逐条交叉核对。
5. **不做**：不为提升命中率而禁用压缩、禁止子代理、把 `keepRecent` 调到 0，或容忍上下文溢出。缓存服务于任务，不是任务服务于缓存。

### 2.1 三条直接推论

1. **`PONOS_PROMPT_CACHE` 全局开关在多端点下是错的**。它应当由**端点能力**决定：Anthropic 端点必须开（否则 0 命中），DeepSeek 端点开了也无害但无意义，本地端点开了可能触发"去标记重发"的额外往返（`kernel/api.mjs` 的 `isCacheRejection` 兜底路径）。
2. **DeepSeek 的"缓存前缀单元"语义比 append-only 更严格**：中段一改，上一轮落盘的单元全部不匹配，只能退回更早的公共前缀；而"公共前缀"需要系统**观察到多轮重复**才落盘 ⇒ **改写点反复移动 = 落盘单元永远追不上**。这使 §4 的"老化"问题在 DeepSeek 上比在 Anthropic 上**更贵**。
3. **usage 字段别名必须补齐**（当前是盲区）：`kernel/api.mjs:117-124` 的 `normalizeUsage` 只认 `cache_read_input_tokens`。若某个端点回传 `prompt_cache_hit_tokens`，本应用的**缓存观测、成本统计、预算熔断会全部读成 0 命中**——所有优化都在黑箱里做。**注意**：DeepSeek 的 `/anthropic` 端点究竟回传哪种字段名，官方兼容表未明示，**属必须实测项**（§7 P0-1）。

## 3. 本应用现状实测

### 3.1 老化改写 × 缓存代价（探针实测，可复跑）

复跑命令：`node scratch/cache-age-probe.mjs`
场景：40 轮会话、每轮 1 次工具调用、每 3 轮混入 1 个不可重放的 `Edit` 结果（`Edit/Write` 不在 `REPLAYABLE_TOOLS` 白名单内，永不被清），从第 6 轮起每轮触发一次老化；口径见脚本头注（代价 = 改写点之后需重算的请求面 token，收益 = 本次清除掉的 token）。

| `keepRecent` | 单次改写省下 | 改写点之后需重算 | 净收益判定 | 末态尾部重算占比 |
|---|---|---|---|---|
| 1 | ≈1111 tok | ≈600 tok | **赚** | 27.6% |
| **2（当前默认）** | ≈1065 tok | ≈1211 tok | **亏 ≈1 倍** | 27.6% |
| 4 | ≈1026 tok | ≈2823 tok | 亏 ≈3 倍 | 54.1% |
| 8 | ≈983 tok | ≈5657 tok | 亏 ≈6 倍 | 68.0% |
| 20 | ≈983 tok | ≈14549 tok | 亏 ≈15 倍 | 89.9% |

> `keepRecent` 默认 2，来源 `kernel/compact.mjs:191-192`（env `PONOS_TOOL_RESULT_KEEP_RECENT`）。
> "触发老化轮次 23/35" 说明：**稳态下几乎每轮都在改写历史**（每新增 1 条可重放结果即改写 1 条）。

### 3.2 两个反直觉结论

- **`keepRecent` 越大，缓存代价越高**（尾部重算占比 27.6% → 89.9%）。机制：`cutoff = results.length - keep`（`kernel/compact.mjs:54-56`），keep 越小 ⇒ 最后被改写的位置越靠尾部 ⇒ 断裂点之后要重算的内容越少。"保留更多近期结果"换来的保真度，是用**成倍的缓存重算**买的。
- **当前默认 `keep=2` 在缓存维度上恰好接近临界最优**（≈1 倍）。所以：**不要指望调 `keepRecent` 提命中率**；调大它是纯粹的"保真度换缓存"，且换得越来越贵；`keep=1` 是唯一在纯缓存损益上为正的档位，但会明显削弱近期工作上下文（`compact.mjs` 有 `floor 1` 保护，说明设计者已权衡过），**不建议仅为省钱下调**。

### 3.3 对已有观测计划的修正（重要）

`docs/superpowers/plans/2026-09-18-prefix-cache-observability.md.preworktree`（**worktree 备份态**，合并回主线后恢复为 `.md`）的 **v2 增补 A3 假设表**中：

> **H2（新）**：前段原地改写的缓存损失**随 `keepRecent` 减小而增大**；**若损失随 keepRecent 增大而显著下降** ⇒ 证实"改写点越靠后越保前缀"

本实测给出**相反**的方向：损失随 `keepRecent` **增大**而增大。建议在实施 Task 6 前把 H2 改写为：

> **H2（修正）**：前段原地改写的缓存损失**随 `keepRecent` 增大而增大**（改写点前移 ⇒ 断裂点之后的重算量增大）。判据：比较各档 `ok` 占比与 `suspicious` 的 `drop` 总量，**若损失随 keepRecent 增大而下降**，则本模型（严格 LCP / 缓存前缀单元语义）不成立，需查明端点实际使用的匹配语义。

⚠️ **诚实标注**：本探针是**确定性模拟**（等长 payload、固定隔轮 Edit、假定严格 LCP 语义），不等于真实端点行为。它足以**证伪"keep 越大越省"的直觉**并提示 H2 方向存疑，但**不足以作为改默认值的依据**。真实裁决仍需观测层数据（§7）。

**附带发现（已更正，2026-09-18）**：`bumpContentEpoch` 是**进程级**模块变量（声明与导出 `kernel/context.mjs:143-146`），lane / 子代理的原地改写会让主会话的**进程内记忆化**（`requestFace` 记忆 + 估算 WeakMap，消费点 `kernel/request-face.mjs:196`）多失效一次。

⚠️ **更正原表述**：本条初稿写成"会**低估**主会话的实际命中率"，属**概念混淆**——`contentEpoch` 只作用于**本地计算缓存**，**不影响 API 侧前缀缓存**：后者由服务端按**请求字节**匹配，而 epoch 不改变任何一个字节（它不进请求体、也不改消息内容）。故：
- 它**不是**本议题（前缀缓存命中率）的优化点，收益仅为省一次本地重建（实测 `requestFace` 重建约 0.77ms/次，`request-face.mjs:162-165`）；
- 该保守设计是**有意为之**：`request-face.mjs:174-176` 明确写下"刻意不依赖'已证明无第三处改写点'这一结论，多一枚纪元即多一层保证（多失效一次只多算、不会错算）"⇒ **不动**；
- 由此推出一条读文档时的警示：**进程内记忆化指标不可与 API 前缀命中率混算**（前者是 CPU 视角、后者是计费视角，二者无因果关系）。

## 5. 多端点分流的策略矩阵（本次确认：多端点混用）

| 优化动作 | Anthropic 官方 | DeepSeek（含 `/anthropic`） | 本地 vLLM 类 | 冲突点 |
|---|---|---|---|---|
| 打 `cache_control` 标记 | **必做**（否则 0 命中） | 忽略（无害） | 可能触发"去标记重发" | 需按端点自动判定，而非全局 env |
| 断点数量 / 位置 | 最多 4 个，做分层 + 滚动（§6 P2-9） | 无意义 | 无意义 | 仅 Anthropic 分支生效 |

## 7. 验证设计（本方案的唯一成功判据）

**主口径**：`hitRatio = cache_read / (input + cache_read)`（与 `kernel/stats.mjs:61` 既有口径一致，全仓唯一），并**同时**记录每轮 `cache_read` **绝对值**与每轮成本——避免"命中率上去了但总额更贵"。

**A/B 对照**：同一批真实长会话、同一模型，变量逐项单独开启（① 工具清单下沉 ② tools 排序 ③ 老化冷却 ④ 事前限流），对照组保持现状。

**观测量**：per-request `hitRatio` 中位数、每轮 `cache_read`、每轮成本、`suspicious` 事件计数、**任务成功率**。

**判据**：
- 成本下降 **且** 任务成功率不下降 ⇒ 通过；
- 命中率上升但任务完成率下降 ⇒ **判为失败**（对应材料第 7 条：缓存服务于任务）；
- 若各端点表现相反（如 Anthropic 显著改善、DeepSeek 无变化）⇒ 说明该变量只在特定匹配语义下有效，**如实记录**，不要取平均。

**前置条件**：P0-1 未完成前，DeepSeek 端点的命中率数字**不可信**（可能是字段名不匹配导致的恒 0），不得据此做任何结论。

## 8. 明确不做（防止本末倒置）

1. 不为提升命中率而**禁用压缩**（会撞溢出，代价远大于缓存）。
2. 不**禁止开子代理**（减少主上下文污染的价值高于几个百分点命中率）。
3. 不把 `keepRecent` 调到 0/1 换命中率（§3.2：纯缓存损益为正，但上下文保真度损失明确）。
4. 不在**没有观测数据**前改任何压缩阈值或触发条件。
5. 不用 baseUrl 字符串猜测端点能力（换域名/走网关即失效）。
6. 不把"命中率 >90%"本身当作目标——材料明确指出 90% 在 append-only 的长期会话里是自然结果，不是成绩。

### 11.3 实施期发现（2 项，均属既有缺陷）

1. **usage 初值缺字段 → NaN 贯穿**（`api.mjs`）：`usage` 初值原为 `{input_tokens, output_tokens}` 两字段，若端点**不发** `message_start.message.usage`（部分兼容网关如此），`mergeCumulativeUsage` 会做 `Math.max(undefined, n)` ⇒ 命中数与写缓存数全为 NaN，且 NaN 参与的成本比较恒 false ⇒ **预算守卫静默失效**。Anthropic 官方与 DeepSeek `/anthropic` 都发该字段，掩盖了这条路径。已改为 `normalizeUsage({})` 取单一真源。
