一跳是跨进程网络连接，一跳是进程内管道；前端与内核之间没有任何直连。

内核那侧不是终端会话

无 PTY、无 TTY、无交互式 shell 语义，纯管道上的一行一 JSON。

只有「启动动作」借 cmd.exe

Windows 拉进程的实现细节（shell:true，args 逐项引号转义），cmd.exe 用完即退，与协议无关。

为什么这么设计

内核可替换（bridge 是唯一知情方）· 安全收敛（Origin/审批/提问都在桥）· 生命周期托管 · 多端复用 · 出网唯一出口。

5应用智控链路 本次新增章节

把「任意应用/网站」变成 AI 可调用工具：发现 → 生成 Spec → 用户确认落盘 → 进控制台绑定 → 内核动态注入工具 → 执行器落地执行。

发现（能力清单）：app-capability.cjs 输出「通道（channel：cli / script / file / http / chunk / web-ui）」清单 —— 通道是发现阶段的归类，driver 是执行阶段由谁跑，两者多对一。 app-profiler / app-http-probe / app-websearch 配合探测
登录态：app-login*.cjs 打开窗口让用户手登，分区键由 app-session-key.cjs（唯一真源）决定 —— 从「按 chat sessionId 分区」改为按应用分区，实现「登录一次、跨会话复用」。 app-login / page / wall / state
生成 Spec：app-generate.cjs 调 LLM 产出 Spec，最多 N 轮把上一轮错误回喂修正；只试跑 read 命令（≤2 条），write 绝不试跑；结果不落盘。 app-llm / app-agent / app-explore（只读 list_dir、read_file，路径白名单）
用户确认落盘：经界面确认后写 <home>/apps/<appId>/spec.json 与 registry.json，并留历史备份。 IPC app:write-spec / app:list / app:next-id / app:list-backups / app:restore-spec
质检：app-validator 校验 Spec 契约，app-profiler.checkApp 自检健康度（healthy / issues），可 app:repair；app:verify 逐命令试跑生成证据。 app:check-spec / app:verify / app:repair / app:mark-quality
进控制台（严格单开）：app-bindings.cjs 把 sessionId → appId（值是字符串而非数组，物理上不可能多开）写入 binding.json。 app:console-enter / app:console-leave / app:console-bound
动态注入工具：内核侧 app-tools.mjs 用视图函数每次求值读 binding.json ⇒ 进入即生效、离开即消失，零重启、零跨进程消息。工具名形如 app_<hash>_<action>。 kernel/app-spec · app-naming · app-permissions + dyntools.setDynamicTools
执行：内核发起 → 桥 app-routing.mjs → 主进程按 driver 分派执行器：app-runner-desktop（桌面 process/script/uia）、app-runner-http、app-runner-file、app-runner-route、app-runner（browser 驱动）。每次执行（含失败）追加一行到 <appId>/history/<YYYY-MM-DD>.jsonl 留痕。 read 直接执行；write 的审批在内核侧，控制台手工执行由 UI 二次确认
边界事实
为什么落盘而非内存内核是独立进程，主进程内存变量它读不到 ⇒ 绑定状态写 binding.json，由内核视图函数读文件
工具池规模严格单开 ⇒ 任意时刻最多挂一个应用的命令集；Spec 命令数上限 40（kernel/app-spec.mjs）
探索工具安全边界仅「目标程序目录 + 该应用用户数据目录」范围内（含路径穿越校验）、全只读、单文件字节上限、二进制拒绝
无 HTTP CRUD应用智控的增删改只在 Electron IPC 暴露（electron/app-ipc.cjs，22 个通道）；桥侧只有内核 → 执行器的 app:exec 路由

三道闸（2026-09-16 安全加固后）

D1 回环收窄

listen(PORT, '127.0.0.1')，只绑环回。加固前未指定 host，实测对局域网开放（0.0.0.0:51517）。
连带约束：前端基址必须写死 127.0.0.1（Windows 上 localhost 先解析 ::1，而桥已不监听它）。

D2 令牌闸门

无 Origin 又无令牌 → 一律 401（仅 /health 与 /api/auth/* 豁免）。令牌由主进程生成/复用，spawn 时经 env 注入桥。
打包版 file:// 跨源请求不带 Origin（Electron 43 行为），故由主进程 webRequest 统一注入令牌头。

D3 出网白名单

egress-policy（.cjs + .mjs 同源）：数据实体默认 local-only，未知实体一律拒绝；闸门落在桥请求入口、D2 之后。

Origin 与 CORS

Origin 仅允许 空 / file: / localhost / 127.0.0.1 / ::1 / null，其余 403；预检白名单方法含 PUT/PATCH/DELETE，头含 x-yfw-bridge-token。

凭据保护 vault

safeStorage 加密，fail-closed（加密不可用即拒读写，绝不回退明文）、损坏不覆盖、日志不落明文；列表只回键名不回值。解密只在主进程，明文不回渲染层（10 条 vault:* IPC）。

内核只读模式

kernel-readonly.mjs + readonly-cache.mjs：只读场景（聚合单飞、超时、限流）不进内核写路径。另有 redact.mjs 日志脱敏。

12已知风险与架构约束 审查要点

项事实（均经源码核对）
bridge.mjs 是巨石约 234KB / 3812 行单文件（server/bridge.mjs），内联 HTTP 路由仍集中在 2191-2807 段（if (url.pathname === …)；其余已外迁至 host-routes.mjs / auth-routes.mjs / readonly-routes.mjs）。新增路由必须放在令牌闸门（2178）之后。当前最大可维护性风险点。
「内核 ⊥ server」并非全局成立该纪律被测试钉住的只有部分模块；server/bridge.mjs 自身就 import 了 kernel/mcp.mjs、kernel/tag-store.mjs、kernel/team-store.mjs、kernel/file-collab.mjs、kernel/legacy-env-boot.mjs。不要把「完全解耦」当作既成事实。
打包产物不含 kernel/只发 dist/ electron/ server/ shared/ public/ bin/ node.exe + kernel-dist ⇒ server 侧模块不得 import kernel/*（electron-builder.yml:23-43 注释已承认此隐患，靠 shared/** 一并打包缓解）。
便携版树才是运行代码dev 形态下改源码不生效：运行代码真实来源是 release/YFWorking/，由 dev-source-sync.cjs 门控同步，失败只 warn 不报错（main.cjs:1682-1693）。
文档 / 图谱的口径关系docs/architecture.md 是文本真源（可 diff、可评审）；本 HTML 是它的可视化 / 汇报版，docs/architecture-graph.html 是逐模块图谱。三者的模块数 / 功能域数 / 边数 / 行数已由 scripts/check-doc-anchors.mjs 的「门禁 C」互校，不一致即 CI 失败。
