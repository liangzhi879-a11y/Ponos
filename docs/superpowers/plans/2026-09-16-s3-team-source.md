## 2. 设计

### 2.1 单一实现（`shared/`，纯函数优先）

| 模块 | 职责 | 关键点 |
|---|---|---|
| `shared/team-crypto.mjs` | 识别码/验证码生成、Ed25519 密钥对与指纹、scrypt（N=2^15）、AEAD 信封 编/解 | **验证码绝不作为加密根**：密钥 = `scrypt(code, salt)` 仅用于**解封团队密钥**；信封内是团队密钥（256 位随机），永不写 `team.json` |
| `shared/team-members.mjs` | 签名哈希链：追加、复算验证、多副本重放合并 | `hashRecord` **排除 `sig`** 字段；验证要能区分 **modify/delete/insert** 三类攻击并给出 `index+reason`（不笼统报"链坏了"） |
| `shared/team-source.mjs` | L1 共享目录实现 + 四行为对策 + 布局常量 + `.git` 警告 | `writeVerifiedSync`（`.tmp` → 校验 → `rename` → 回读）；`detectPlaceholderSync`；`scanTeamDirs` **按内容匹配**（#10）；`absorbConflictCopies` 只读不改名 |
| `kernel/team-store.mjs` | 本机团队配置（搜索根、已加入团队、本机密钥对）落 `<configDir>/team/`；创建/加入/邀请/撤销的编排 | 复用 `shared/atomic-write.mjs`；**私钥落本机**（§5.9 诚实边界：防的是改共享目录，不防拿到本机私钥的人） |
| `kernel/team-sync.mjs` | 团队知识空间 `team-<teamId>` + 团队经验**条目级并集** | 经验条目 id 已是内容寻址（`hashLine`）⇒ 合并 = 集合求并；知识空间**插在** `shared/knowledge-core.mjs:507` 的 `builtinSpaceSpecs`，下层检索/切分/关联/路由**零改动** |
| `server/bridge.mjs` | `GET /team/status`、`POST /team/create`、`POST /team/join`、`POST /team/invite`、`POST /team/revoke` | 全部落在 **D2 闸门之后**（自动受 token 保护），沿用 D3/D6 的做法 |

### 2.2 opt-in / 零回归原则（沿用 D6 的成功做法）

## 4. 验证（对齐 §9 的 S3 三项）

1. **加入机制**：识别码匹配 / 正确码解出**团队密钥**且与创建时一致 / 错误码拒绝 / 一次性（二次使用失败）/ 过期拒绝（可注入时钟）。
2. **清单防篡改**：改一行、删中间一行、插伪造行 ⇒ 各自 `verify` 失败且 reason 精确；**删掉整个日志文件**、其他成员副本仍在 ⇒ 重放后仍能复原完整成员集。
3. **同步盘对拍**：手工造 `log-x (1).jsonl`、`log-x - 副本.jsonl` ⇒ 重放结果与"单副本"**逐字一致**；且**不原地改名**（文件仍在，仅被读取）。
4. **占位符/脱水**：伪造占位符文件 ⇒ 被识别并跳过，不当作真实内容解析。
5. **`.git` 警告**：团队源位于 git 工作区内 ⇒ 返回警告（不阻断）。
6. **零回归**：未加入团队时既有路径行为逐字不变。
7. **真机**：起桥 → 无 token 401 / 带 token 创建 → 邀请 → 加入 → 状态可见 → 撤销。
8. **守门演练**：分别让（a）验证码校验恒真、（b）哈希链不校验 `prev`、（c）冲突副本不被吸收 ⇒ 回归网精准变红。

1. **不含 S3 的 UI**：模式开关 / 三层新建向导 / 加入流程 / 邀请界面小字 / 侧边栏筛选——属渲染层工作，本轮交付**内核 + 桥面**，UI 待后续（会明确报告）。

3. **L2 服务器源不实现**（S5 明确不做），只留接口形状。
4. **团队密钥保护的真实边界**：能读 `keys/` 的人本已被 ACL 授权；本机私钥不防"拿到本机者"。
5. **#6/#7/#8 的策略未定**（参数化 + 待终验），#10 已实现。
6. **S1（块模型/ops/三路合并）未做** ⇒ 团队**文件**协同（S4）与"ops-only 写入"仍不可用；本轮只解决"团队源 + 成员 + 知识/经验协同"。

### 实施中发现并修掉的**真缺陷**（均为实测，非推测）

1. **跨设备重放顺序错乱**（最严重）：`mergeMemberLogCopies` 原按 `(by, seq)` 排序 ⇒ 顺序由**指纹字典序**决定；
   B 设备的 `add` 若落在 A 设备的 `revoke` 之后，会把人**覆盖回 `active`**。
   证据：复现探针 40 次里 **24 次**判错；`server/team-routes.test.mjs` 3 轮 2 红。
   修法：以 `ts` 为主键、`(by, seq)` 兜底（同毫秒仍确定）。已补**对抗性顺序**回归用例（20 次循环 + 顺序无关断言）。
2. **经验同步静默丢条目**：`parseEntryLines` 收到**数组**时走 `String(arr)` 被逗号拼成一行（`total` 2→1）。
   修法：显式支持数组/字符串两种入参。
3. **`revokeMemberOp` 的 `scope` 未透传**：调用方按 `{memberId, scope:'invite'}` 写法会被丢掉 `scope`，
   于是"作废邀请"被重放理解成"移除成员" ⇒ **新成员在加入的同一步被自己写下 的记录踢出**。
   修法：`scope` 升为显式形参。
4. **`listCopies` 用 `localeCompare` 排序**：重放顺序依赖 ICU 区域/版本，破坏"对拍一致"的可复现性 ⇒ 改码元序。
