## 一、本次修复解决的问题

用户报告两件事：
1. 自动生成的 `001智控` 应用**质量差**（只有"打开页面看文本"类命令）；
2. **本地应用（desktop）封装失败**，报错：
   `specVersion 必须为 1；缺少 name；commands[4].steps[1].act 不合法：snapshot（desktop 只允许 cli / script / focus / type / key / wait）`

根因（实测复现，非推断）：**同一份 driver 契约存在两个判定口径**。

| 位置 | 判定写法 | 对 `driver='process'` 的结果 |
|---|---|---|
| 生成提示词（`electron/app-agent.cjs`） | `driver === 'desktop'` | 判为非桌面 → 下发 **web** act 清单（含 `goto`/`snapshot`） |
| 结构校验（`electron/app-generate.cjs`） | `target.type === 'desktop'` | 判为桌面 → 只允许 `cli`/`script`/`focus`/`type`/`key`/`wait` |

生产链路的 driver 实际只有 `browser` / `process` / `script` / `uia`（由 `app-profiler.detectDriver` 探测），**`'desktop'` 这个值在生产里从不出现** → 提示词侧永远走 web 分支。结果是：模型被明确要求写 `goto`/`snapshot`，校验又一律拒绝，本地应用**从设计上就生成不出来**（与模型能力无关）。

同链条另查出 4 个缺陷：试跑路径漏注入 driver（`不支持的 driver：undefined`）、uia 后端未接入却可能"生成成功"、提示词从不写顶层结构契约（"缺少 name" 由此而来）、失败时展示的是最早几轮的陈旧错误。

## 五、与 yfljsj-cli 的差距归因（对标实证）

对标对象：`C:\Users\T203-15\ponos-dev\release\yfljsj-cli-v0.5.0`（同一站点，535 条命令 / 31 模块）。

实证：该封装是**接口级**的 —— `apis.seed.json` 以 `services/modules/operations` 组织，命令形如 `asset.capitalization-queryById`、`asset.capitalization-list`（module + action），`explore-report.json` 还记录了哪些接口因 `dangerous`（删除类）被跳过。

**结论：差距不在模型能力，而在"是否把接口摸全"。**

| 维度 | yfljsj-cli | 应用智控（修复前 / 修复后） |
|---|---|---|
| 封装层次 | 接口级（直接调站点 REST） | 页面级（`goto+snapshot` 取文本）→ 修复后引导接口级（`js`+`fetch`，自带登录态） |
| 接口发现 | 人工梳理 + `discover` 代理**逐请求捕获**真实流量 | 仅靠页面素材推断；**没有**"已捕获请求"这一信息源 |
| 规模 | 535 条（无上限约束） | 受单应用上限（原 20 → 已放宽 40，且本轮修好"上限在生产不生效"）与探索预算（`maxTurns=24` / `maxToolCalls=20`）双重封顶 |

**后续可选增强（本次未做，建议单独排期）**：给探索环增一个 `list_requests` 工具，把浏览器执行器**已经捕获到的网络请求**作为素材喂给模型 —— 这等于把 yfljsj-cli 的 `discover` 能力搬进自动生成流程，是从"页面级"跨到"接口级规模"的关键一步。
