## 交付的语法集

```
foo bar            两个词都要命中（AND）
"foo bar"          短语整体匹配（内部空格不拆词）
foo OR bar         任一词命中（OR 必须大写独立成词）
-foo               排除含 foo 的块（也可用于算子：-tag:草稿）
tag:财务           文档级：文档标签（容忍 # 前缀；前缀匹配）
path:reports/      文档级：空间内相对路径包含
file:周报          文档级：文件名（basename）包含
section:背景       块级：所在标题包含（heading: 别名）
content:营收       块级：块正文包含（line: 别名）
block:^a1b2        块级：块 id 包含
/\d{4}-\d{2}/      正则（/…/ 包裹，大小写不敏感）
```

**不做**：`\` 转义、括号分组、`sort:` / `limit:` 之类指令算子。理由：越靠近正则的转义规则越容易造出
"用户以为自己写了 A、实际是 B" 的歧义，而收益有限；需要复杂逻辑时分几次搜即可。将来若加，必须先设计转义规则再实现。

## 四个"做错了也不会报错、只是结果不对"的决定

这批的风险不在实现难度，而在于**每一个错法都表现为"结果不对"而不是"报错"**。下面四条是全部实现里
最容易做错、且错了最难排查的点，每条都在代码里留了注释、在测试里钉了用例。

### ① 未知字段必须回落成普通文本

用户搜 `10:30`、`http://example.com`、`ratio 1:2` 时，形如 `x:y` 的 token 到处都是。若"任何 `x:y` 都当字段"，
这些查询会变成"字段 `10` 等于 `30`" → **搜不到任何东西且不报错**，用户只会觉得搜索坏了。
只有白名单字段（含别名 `tags`/`heading`/`line`/`filename`）才是算子；判据还包括"冒号不在首/末位"。
`shared/knowledge-query.mjs` 的 `splitFieldToken` 是唯一实现处，前端镜像 `splitOperator` 同判据。

### ② `OR` 必须一路贯彻到**过滤层**

最初把 `parsed.filters` 当成一个扁平 AND 列表 → `tag:财务 OR tag:技术` 会要求两个标签**同时存在** →
返回 0 条。用户写了 OR 却什么也搜不到，是明确的错误行为。
现在解析结果带 `orGroups`（组内 AND、组间 OR），文档级与块级匹配都按分组求值。
`OR` 必须**全大写**：正文里小写 `or` 太常见，当成算子会毁掉所有英文查询（`arm or leg` 变成两个分组）。

### ③ 纯否定查询统一"无结果"口径（而不是枚举全库）

实测踩到的不一致：`-tag:x`（否定**过滤**）一度会枚举出"全库里所有不带该标签的文档"（几千条，
看起来像过滤没生效），而 `-foo`（否定**词**）在打分链里必然返回空 —— 同一个"排除"意图两种结果。
统一为：**没有正向依据（正向词/短语/正向过滤/正向正则）就没有结果可给**，内核返回空、UI 说明原因。

### ④ `strict` 分界：只在用户显式写了布尔逻辑时启用严格语义

`parsed.strict = 有 OR || 有否定文本项`。没写时不启用 —— 既有打分链允许"部分命中也能召回"
（`季度 报告` 里只含"季度"的块也能进结果，按相关度排序）。无条件改成 AND 语义会让老查询的结果
突然变少而用户不知道为什么：**那是行为回退，不是修 bug**。这条是批次 3 最重要的兼容性防线。

## 关键实现细节

### 打分文本必须剥掉算子

`parsed.textQuery = terms + phrases`（不含算子、不含正则）。把 `tag:财务` 原样喂给 `vectorizeText`
会把整串切 gram，于是"搜 `tag:财务`"会命中一堆含 `tag` 的文档。**过滤器只负责过滤，不参与打分。**

### 枚举路径（`enumerateSearch`）

查询里**没有可打分的正向文本**时（`tag:财务`、`path:reports/`、`/\d+%/`），不能复用打分链：
`scoreBlock` 的每一路都需要文本证据（向量余弦 / 关键词命中 / 结构近似），没有词时全为 0 →
`isHit` 恒假 → **命中集恒空**，用户看到"库里明明有那个标签却搜不到"。

- 开关是 `parsed.enumerate`（`filterOnly` 的超集）。漏掉"只有正则"这一类就是实测到的
  `/\d+%/` **静默返回空**（既不报错也不给结果，用户无从判断是语法问题还是库里真没有）。
- 逐块谓词**两条缺一不可**：`matchBlockQuery`（文档级+块级过滤，含分组）+ `matchTextParts`（文本项）。
  枚举模式没有打分兜底，查询里的文本项（正则、否定词）就是谓词本身，必须**无条件**判
  （只靠非 strict 的 `matchBlockQuery`，纯正则查询会把每篇文档的第一个块都当成命中）。
- 每篇取第一个满足全部条件的块作代表（一篇出十条会淹没结果），排序按**文档路径** ——
  枚举结果之间没有相关度可言，用 mtime 会让"同样的查询两次顺序不同"，看起来像 bug。

### `section:` 要回溯所属标题

Markdown 里 `## 背景` 是**独立的一块**，紧接着的正文块文本里没有那行标题 → `section:背景 营收`
在正文块上恒不命中，最自然的查询返回 0 条。`enclosingHeading(doc, block)` 沿块顺序回溯到最近的前置标题。
前端镜像拿不到完整 doc 结构，退化为只看块自身 —— 方向是"提示不够乐观"，不会误导用户信任假阳性。

### 文档级判定何时下探到块

`matchDocQuery` 在"查询含块级条件（正向或否定）或处于严格模式"时验证到块才算命中，否则只看文档级字段。
这条规则来自一个实测出来的**过度排除**：最初规定"否定的块级过滤只要有一块命中就排除整篇"，
于是 `内容 -content:未定稿` 返回 0 条 —— 用户只想排掉"未定稿"那一块，同一篇里其它块也搜不到了。
既然块级匹配器已能精确表达"排掉哪一块"，文档级就该用同一套精确语义。

### 图扩展与标签直连也要遵守过滤条件

否则 `tag:财务` 会把命中文档的**链接目标**一并带出来（那些文档没有该标签）—— 用户看到的是"过滤没生效"，
比漏结果更糟：它让人不敢信任过滤。外链是"相关"的弱证据，不该突破用户显式给的约束。

### 元信息回传（`queryMeta`）

结果带回 `query.{filters,fields,terms,phrases,regexes,or,strict,filterOnly,enumerate}`，GUI 据此回显
"哪些算子真的生效了"（结果变少时这是用户唯一能看到的解释）。**正则实例不进元信息**：
`RegExp` 经 JSON 序列化会变成 `{}`，调用方拿到空对象只能猜"正则到底生效没"，故展开成字符串。
