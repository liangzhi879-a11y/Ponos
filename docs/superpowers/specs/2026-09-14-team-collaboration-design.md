# Spec：团队协同（S1–S5）—— 单机协同设计与文档协同模型改造（2026-09-14）

## 0. 本文档定位

"团队协同"是**一个功能模块、五个可独立交付的子项目**：

| # | 子项目 | 交付物 | 验收方式 | 本文覆盖 |
|---|---|---|---|---|
| **S1** | **文档协同模型** | docx/xlsx 的稳定块模型 + 结构化写入语义 | 单测 + 三路合并对拍 | ✅ 详设（§6.1） |
| **S2** | **协同地基** | bridge 收窄监听与鉴权 + 数据出网闸 + authorId 落盘 + 标签实体化 | 单测 + 安全回归 | ✅ 详设（§6.2） |
| S3 | 团队源与内容协同 | Team Source 抽象 + `team-<id>` 知识空间 + 经验条目集合 + **团队工作区 UI（新建/加入/成员）** | 端到端（共享目录） | 🔶 仅约定边界（§7、§13）+ **UI 形态（§5.9）** |
| S4 | 文件协同 | 草稿/版本/交付 + 软占用 + 冲突处置 + 角色（软权限）+ **文件模态分层** + **协同编辑器 UI** | 人工验收 + 并发对拍 | 🔶 仅约定需求（§5.1–§5.8） |
| S5 | 企业版 | 服务端 Team Source 后端 + admin 监管后台 | — | 🔶 仅约定边界（§13） |

**S1 与 S2 相互独立、可并行开工**，且都不依赖协同产品决策——它们是地基，本身就该做。
S3–S5 的详细设计各自另开 spec。

### 批注约定与决策闸门（用户定案 2026-09-14）

**未决点一律以批注形式就地下沉到其影响处**，而不是只集中在 §14 表里。批注形如：

> 📌 **批注 #2** · 推进前置确认 —— 一句话说明待决内容。索引见 §14。

**闸门规则**：**推进到任何批注点前，必须先与用户确认；确认后方可落码。**
不得以"先按 §14 的倾向实现、后续再改"的方式绕过——**§14 的「倾向」只是建议，不构成授权。**

各子项目的**开工前置批注**汇总见 §13 闸门表。

> **本文最重要的三条实证**：① 块级三路合并在算法上**已验证可行**（§2.2 T5–T7、T9）；
> ② 但现有 `docx_edit.py` / `sheet_edit.py` 是**"原地覆盖"写入语义**，直接加合并算法会导致**静默数据丢失**（§2.2 B1）——**结论：不要在现有接口上加合并，先补 S1**；
> ③ 技术栈对 docx/xlsx/文本**可结构化回写**，对 pdf/图片**可提取不可写**，对 pptx 等**无解析器**（§2.3）——**结论：文件模态必须分层治理，不能一刀切**。

### §2.2 实验实证（2026-09-14 实测，脚本见 `scratch/collab-experiment/`）

环境：Word 2016 (Office16 x86) + 内置 Python（python-docx 1.2.0 / openpyxl 3.1.5）。
测试语料：受控 docx（15 段 + 2 表格，含标题层级与混合 run 格式）+ 真实高新申报 xlsx（21 行 × 18 列）。

**✅ 正面结论（协同所需能力底层是通的）**

| # | 测试 | 结果 |
|---|---|---|
| T1 | docx 幂等：同文件读 3 次 | 输出完全一致（MD5 相同） |
| T2 | docx 经 Word 重存（内容不变） | **块序列完全一致**（37,781→40,192 字节，确已重序列化） |
| T3 | docx 经 Word **外部编辑**一段 | 精确定位（16/17 同序一致，仅 1 块变化） |
| **T4** | **外部 Word 编辑 vs 应用内编辑** | **两条路径行为一致** ⇒ 定案 11「混合入口」顾虑解除 |
| T5 | 三路合并·两人改不同正文段 | **0 冲突** |
| T6 | 三路合并·一人改段 + 一人**插入段** | **0 冲突**（内容对齐成功吸收插入） |
| T7 | 三路合并·两人改同一段 | 正确报出 1 冲突 |
| T8 | xlsx 经 Excel 重存 | **0 单元格差异、0 公式标记变化** |
| T9 | xlsx·两人改**不同单元格** | **0 冲突，两处改动都保住** |

> **T4 的方法论意义**：三路合并不依赖编辑入口，只依赖"三个版本都能解析成块"。
> **T9**：xlsx 语义单元（`(row,col)`→值）极强，并发合并成功率显著高于 docx ⇒ **建议 xlsx 先行验证**。

**🔴 阻断与缺陷（必须先修，按严重度）**

| # | 问题 | 实测证据 | 严重度 |
|---|---|---|---|
| **B1** | `write_docx` 的 `zip` 按位置覆盖，**块数多于文档时静默丢弃尾部块**，仍返回 `{"ok":true}` | 16 段合并结果写回 15 段文档 → **末段永久丢失**，返回 ok | 🔴 阻断 |
| **B2** | **表格是原子块**（`rows` 二维数组），合并粒度 = 整表 | 甲改单元格(1,1)、乙改(1,2) → 误判 1 冲突（正确结果应为自动合成 `["数据采集","王五","7"]`） | 🔴 阻断 |

| **B5** | **序号不可作对齐依据** | 插入 1 段 → 同序一致率 **17/17 → 2/17**（内容对齐视角仍精确：仅 1 块新增） | 🟠 高 |

| **B7** | `write_xlsx` **不支持插入/删除行列** | 源码 `:41-56` 仅单元格赋值 | 🟡 中 |
| **B8** | xlsx **公式格只读且静默跳过**（`:50` `continue`） | 源码核对；协作中公式修改被无声丢弃 | 🟡 中 |

## 3. 关键结论（决定本设计）

1. **块级三路合并在算法上可行且已验证**（T5–T7、T9）——协同的核心算法不需要 CRDT/OT。
2. **"原地覆盖"写入语义是 S1 的改造核心**（B1）：协同的本质动作是**增/删/改**，与 update-only 不匹配。
3. **表格必须降维**（B2、B3）：docx 内嵌表格需拆成行/单元格子块，否则大多数真实并发场景会被误判为冲突。
4. **稳定块 id 是必要条件，不是优化**（B5）：序号对齐实测崩坏（2/17）。同理 xlsx 行对齐必须用**行内容指纹**（B6）。
5. **格式必须进入块模型**（B4）：否则格式修改会被静默丢弃，对"方案/报告"类文档不可接受。
6. **"共享意图与知识，绝不共享执行"**（定案 6）：agent 永远本地跑；团队只交换声明式的、可被本机重新解释并重新审批的内容。
7. **协同问题被降级为"内容分发问题"**：因执行永在本地，**不需要实时协议、分布式锁、CRDT**。
8. **锁不得参与正确性**：共享目录的锁语义不可靠 ⇒ 正确性只能建立在**内容哈希 + 乐观并发**上（与知识包 `kept-user-modified` 同范式）。
9. **作者字段必须先落盘**（§6.2）：它是共享、审计、企业版 admin 三者的共同前提，且**后补 = 全量数据迁移**，历史数据补不回来。
10. **文件模态必须分层治理**（§2.3）：技术栈对 docx/xlsx/文本可结构化回写，对 pdf/图片可提取不可写，对 pptx 等无解析器 ⇒ 协同能力**不能一刀切**，须按「可合并 / 可提取 / 可转换 / 不可解析」四层分别定策略（§5.1）。
11. **同步网盘 ≠ 普通共享目录**（§7.1）：其**冲突副本、同步延迟、占位符脱水、CldFlt 驱动拦截**四个行为直接冲击"共享可写索引"的假设 ⇒ 团队源必须设计成**只追加日志 + 内容寻址**，而不是共享数据库。
12. **未覆盖格式不需要"读懂"也能协同**（§5.1 L-D）：降级为**检出/检入**即可——冲突面从"内容冲突"退化为"占用冲突"，而占用冲突有解（租约 + 超时）。
13. **已有先例必须复用**（§2.3 ④）：OneDrive 检测与写入校验、CldFlt 规避、哈希链审计均已存在 ⇒ 不新造机制（P7）。

## 4. 设计原则

| # | 原则 | 落地约束 |
|---|---|---|
| P1 | **热/冷分离** | 热状态（运行中会话/审批/浏览器/工具执行/凭据）纯本地、永不参与同步；冷数据（知识/经验/工作流定义/文件版本/标签）才走团队源 |
| P2 | **默认不外发** | 出网闸为**白名单式**：数据实体默认 `local-only`，显式标记才可外发。黑名单式屏蔽必漏 |
| P3 | **草稿 ≠ 版本** | 并行编辑产生**草稿**（合并后销毁），只有**定稿**进版本链 ⇒ 每文件一条线性主干，版本数只随交付次数增长 |
| P4 | **乐观并发** | 锁只是性能优化与信息透明，**不是正确性来源** |
| P5 | **内容寻址** | 版本、经验条目、块指纹一律用内容哈希（既有先例：pack 指纹、`hashLine`、`TEXT_EXTS` 行尾归一） |
| P6 | **软权限（单机版）** | 角色定义进数据模型，但单机版**只有声明 + 应用内约束 + 越权留痕**，无强制力（共享目录写权由 OS ACL 决定） |
| P7 | **不造平行体系** | 复用 pack 的安全模型、工作流的哈希链审计、知识空间抽象；不新造分发协议 |

## 5. 需求设计（产品层）

> 本节对应定案 3/7/8/9/10/12，是 S4 的需求输入；S3 只需其中的 §5.1、§5.2、§5.7。

### §5.1 共享边界

| 类别 | 内容 | 是否过团队源 |
|---|---|---|
| 冷·内容 | 知识、经验、工作流定义、文件版本、标签 | ✅ 双向 |
| 冷·遥测 | 消耗量、会话**元数据**、运行审计 | ⬆️ 单向上行（供企业版 admin 聚合） |
| 冷·敏感 | transcript 全文、绝对路径、命令 | ❌ 默认不同步；显式分享时**必须过 `kernel/redact.mjs`** |
| 热 | 运行中会话、审批决策、浏览器、工具执行、provider 凭据、审批档位 | ❌ 永不 |

#### 文件模态分层（定案 17；依据 §2.3）

**协同能力不是文件类型的函数，而是"是否存在稳定寻址单元且可回写"的函数。** 据此分四层：

| 层 | 判据 | 代表格式 | 协同策略 | 冲突面 |
|---|---|---|---|---|
| **L-A 可合并** | 有稳定寻址单元 + 可回写 | **xlsx（单元格）**、docx（块，需 S1 改造）、文本/md/代码（`TEXT_EXTS`） | 三路合并（§5.4） | 内容冲突 |
| **L-B 可提取** | 能读不能写 | **pdf**（文本层/表格/OCR）、**图片**（PIL/OCR/Vision）、doc（win32com 读）、xls（xlrd 读） | **只追加版本，永不原地改**；提取物入知识空间 | 无（不可变） |
| **L-C 可转换** | 经转换归入 L-A/L-B | `.doc→.docx`、`.xls→.xlsx`、CSV/HTML、邮件 | 转换后按其归属层处理 | 随转换结果 |
| **L-D 不可解析** | 无解析器 | **pptx**、psd/dwg/ai/sketch、音视频、压缩包 | **检出 / 检入**（check-out / check-in） | 占用冲突 |

**L-B 的要点：图片/PDF 不是"协作对象"，而是"内容源"。**
它们的价值不在被编辑，而在**被提取后被引用**：OCR/文本提取 → 进 `team-<id>` 知识空间 → 可检索、可被 docx/xlsx 引用。
引用**锚定版本 id 而非路径** ⇒ 源文件出更新版本不会破坏既有引用（复用 §5.7 的 versionId = 内容哈希）。

**L-D 的要点：不读懂文件也能协同。**
- 二进制整体作为 **CAS 对象**（文件名 = 内容哈希）⇒ 同名必同内容，**天然免疫同步盘冲突副本**
- 因无法合并 ⇒ 软占用在此**升级为硬串行**：同一时刻仅一人可检出，他人只读
- 用户在本机用原生软件编辑，"检入"时生成新版本
- **冲突面从"内容冲突"降为"占用冲突"**，而占用冲突有解（§5.3 租约 + 超时 + 可接管）

**三层兜底（应对"未覆盖格式"，依次尝试，不新增机制）**：

1. **先转换** — `doc_toolkit.py convert`：凡能转成 docx/xlsx 的，自动升到 L-A
2. **再提取** — 能读就提取成文本入知识空间（pdf/图片已是此模式）
3. **最后降级** — 都不行 ⇒ L-D 检出式，独占 + 快照

🛑 **明确不做**：不为了"可合并"而把 docx 降维成 markdown（§12-7）。

> 📌 **批注 #9** · 推进前置确认 —— **L-D 检出/检入的 UX 细节**（如何提示"某人正在编辑此 pptx，你目前只读"、如何引导"检入"）。影响 S4；索引见 §14-9。

> **对定案 3「版本管理不能乱」的补充**：L-B/L-D 的一切变更都是**追加**，不产生"同目录多份近似文件"。
> 这是与既有 `output_version_manager.py` 的 `.bak` 式备份的**根本区别**——后者会产生文件膨胀，本设计不会。

### §5.2 草稿 / 版本 / 交付

| 概念 | 定义 | 生命周期 |
|---|---|---|
| **草稿 draft** | 进行中的编辑（本机隔离副本） | 合并后**销毁** |
| **版本 version** | 已定稿的不可变快照，有版本号 | 永久保留 |
| **交付批次 release** | **一组**文件版本的快照（如"方案包 v3"） | 永久保留 |

**关键约束：主干线性。** 每个文件一条主干；合并产出的副本一律降级为草稿，绝不生成"第二个版本"。
这是定案 3「版本管理不能乱」的机制保证——由结构强制，不靠人自觉。

### §5.3 并发模型（渐进式）

| 时段 | 机制 | 用户感受 |
|---|---|---|
| 平时（时序并发，**主场景**） | 乐观并发 + 块级/单元格级合并 | 零锁、零阻塞 |
| 高峰（真并发，**少数时段**） | **按需启用**软占用（advisory claim + 租约 + 心跳 + 可接管） | 提示"某人正在改"，**不硬阻断** |

**软占用绝不参与正确性**（P4）：崩溃/断网靠**租约超时**自动释放，不产生死锁。

> 📌 **批注 #3** · 推进前置确认 —— **软占用的默认启用策略**（全局关闭+按目录开启 / 按文件热度自动）。影响 S4 的 UX 与 §5.8 策略对象；索引见 §14-3。

### §5.4 冲突处置

判定唯一依据：**提交时基线（base version）是否仍等于团队源当前版本**。

| 情况 | 处理 |
|---|---|
| 无冲突（含不同块/不同单元格） | **自动三路合并**，成为新版本 |
| 同块冲突 | **不自动二选一**，进入处置 |

处置动作（四选一）：**接受我的 / 接受他的 / 逐条选择（文本与 xlsx 可用） / 另存为新草稿**。
无论选哪个，**主干只有一条推进，副本降级为草稿**。

### §5.5 角色与权限

五角色为**终态**（定案 7，大团队权限继承树交企业版）：

| 角色 | 权限 |
|---|---|
| owner（发起人） | 增删成员、指定 admin、解散空间 |
| admin | 管成员与目录结构、强制接管占用、处置冲突、**发布定稿** |
| editor | 读写、建草稿、提交合并 |
| commenter | 只读 + 批注（批注锚定**版本**，不锚草稿） |
| viewer | 只读 |

**"发布定稿"上收至 admin/owner**——定稿不可变，是团队对外承诺。

⚠️ **单机版是软权限**（P6）：应用拦不住直接改文件的用户。故单机版角色 = 声明式记录 + 应用内约束 + 越权留痕。

### §5.6 分工表示

最小集，不做 Jira：文件/目录的**责任人**（可继承）+ **状态**（进行中/待审/已定稿）。
角色标签复用 §6.2 的标签体系，不另造。

### §5.7 ID 体系

| 对象 | 方案 | 理由 |
|---|---|---|
| userId | 本机生成 UUID（企业版可绑密钥对指纹），团队源注册 | 离线可生成、跨机稳定 |
| **fileId** | **与路径解耦的稳定 id** | **关键**：文件会改名/移动，若 id=路径则版本链断裂。须保留**路径变更历史** |
| versionId | 内容哈希 | P5 |
| draftId | UUID | 临时 |
| releaseId | `v<日期>-<序号>` | 可读、可引用 |
| **blockId** | 内容指纹 + 结构位置（§6.1） | B5 |

### §5.8 审批与交付策略

收敛为**挂在目录上、向下继承、批次可覆盖**的策略对象（不做散落开关）：

```js
deliveryPolicy: {
  unit: 'file' | 'batch',        // 交付粒度（定案 8）
  requireApproval: boolean,      // 是否需要他人审批（定案 9）
  approvers: [userId | role],
  inheritFrom: <父目录>,
}
```

"小改动单文件直接定稿"与"对外交付走批次+审批"是**同一机制的两个配置**，不是两条代码路径。

### §5.9 团队工作区的 UI/UX 形态

**用户定案**：① **两级形态**——header 一级「个人 / 团队」模式开关，团队态下二级选择具体团队工作区；
② 成员登记**同时支持邀请包与加入码**；③ UI 用「邀请」，配小字提示权限限制。

#### 一级：模式开关（header）

位置：应用主界面 header（`AppShell`）。语义是"我正在做**哪一类**工作"，**不是数据隔离开关**（见下"关键约束"）。

#### 二级：团队工作区选择

团队态下 header 显示「当前团队」下拉（多团队切换）；未加入任何团队时显示空态引导（创建 / 加入二选一）。

#### 两条进入路径

| 路径 | 流程 |
|---|---|
| **新建团队**（发起人） | 3 步向导：① 团队名 + 本机身份（自动生成密钥对，显示身份指纹）② 团队源（共享目录 / 服务器地址）③ 应用初始化团队源，**生成团队识别码**并停留在"邀请成员"页 |
| **加入团队**（成员） | **输入「识别码 + 验证码」两个数字 → 完成**（见下）。兜底：拖入 `.yfwteam` 邀请包，或手动选择目录 |

**顺序要点**：必须**先有团队工作区实体，再配置团队源**（团队源是工作区的属性，不是前置条件）。
初始化时应用自动完成：写 `team.json` manifest + 成员清单 + 目录结构，并**构建 `team-<id>` 知识空间**（§7）。

> **加入者路径必须极简**——普通用户不应手工配置目录路径。这是决定采用率的一步。

#### 加入机制：识别码 + 验证码（定案 15）

对齐向日葵的心智模型：**两个短数字，可口头传**。

| 概念 | 形式 | 作用 | 生命周期 |
|---|---|---|---|
| **团队识别码** | **9 位数字**（如 `483 920 517`） | **定位 + 确认**团队源 | 团队级，固定，写在 `team.json` 明文 |
| **成员验证码** | **6 位数字**（如 `739 204`） | **认证 + 解封团队密钥** | **每成员一个、一次性、默认 7 天有效** |

**加入步骤（成员侧，两步）**：

1. 输入 **9 位识别码 + 6 位验证码**
2. 应用在**团队目录搜索根**下扫描 `team.json` → 按识别码匹配到目录 → 解信封 → 加入完成

**「团队目录搜索根」= 一次设置、长期复用的关键。**
首次加入时应用请用户指定一次"我放团队目录的地方"（如网盘同步根 `~/Nutstore/`），**之后加入任何团队都只需两个数字**。
未找到匹配时给出**可操作**的提示，并提供"手动选择目录"兜底。

> 📌 **批注 #6** · 推进前置确认 —— **搜索根的扫描深度与性能**（深度上限、缓存策略、首次扫描耗时提示）。这是"两个数字加入"体验的**成本所在**；索引见 §14-6。

> 📌 **批注 #10** · 推进前置确认 —— **团队源目录被网盘客户端改名后的容错**：须按 `team.json` **内容**而非目录名匹配（设计已隐含，S3 须显式实现）；索引见 §14-10。

> 📌 **批注 #7** · 推进前置确认 —— **验证码的传递与呈现方式**（复制按钮 / 二维码 / 系统分享）。影响"可口头传"这一目标的实际达成度；索引见 §14-7。

> **与向日葵的关键差异（必须诚实标注）**：向日葵有中心服务器做注册表，其识别码**自带寻址能力**。
> 本设计**无服务器** ⇒ 识别码**不能寻址**，寻址由"搜索根扫描"承担，识别码只做**匹配与确认**。
> 因此**首次**需指定搜索根；但这是**一次性**成本，换取此后全部团队的"两个数字"加入体验。

⚠️ **保留 `.yfwteam` 邀请包，但降级为兜底**：当搜索根不可用（跨网段直连、服务器源、对方网盘根结构未知）时使用。
仍与 `.yfwflow`、知识包**同族格式**，复用 manifest + 内容指纹 + 校验安全模型（§7）。

#### 验证码的安全设计（为何 6 位数字够用）

**6 位数字 = 10⁶ 空间，离线可爆破 ⇒ 绝不能作为加密根。** 故密钥与验证码**分离**：

```
创建团队：生成 团队密钥（256 位随机）—— 高熵，永不写入 team.json
邀请成员：为该成员生成 验证码（6 位随机）
          信封 = AEAD_encrypt(团队密钥, key = scrypt(验证码, salt, N=2^15))
          写入 keys/<memberId>.env
成员加入：scrypt(输入的验证码, salt) → 解密得团队密钥 → 加入
```

| 防护 | 手段 |
|---|---|
| 离线爆破 | 验证码**一次性**——加入成功即作废（追加 `revoked` 记录）；默认 **7 天有效** |
| 爆破成本 | `scrypt N=2^15`（每次约百毫秒级）⇒ 10⁶ 空间在有效期内不可行 |
| 撤销粒度 | **每成员一码** ⇒ 撤销某人 = 作废其信封，**不影响他人**；泄露一码不牵连全队 |
| **真实边界** | **共享目录的访问控制（网盘 ACL）** —— 能读到 `keys/` 的人本已被授权访问该目录 |

🛑 **明确不做「团队统一验证码」**：虽然更省事，但泄露即全队失守、且无法单独撤销某人。

> **UI 必须同步明示**（与 §5.9 末尾的措辞约束一致）：验证码**不是**"数据加密的钥匙"，
> 它只负责**成员登记**；数据的可读性最终由**网盘/目录权限**决定。

#### 成员清单防篡改（定案 16）

**问题**：共享目录下**谁都能改** `members.json` ⇒ 成员清单本身不可信。

**方案：每设备一条「签名哈希链」的追加日志**（`members/log-<deviceId>.jsonl`）：

```jsonl
{"seq":0,"op":"create","teamId":"…","by":"<owner指纹>","ts":…,"prev":null,"sig":"…"}
{"seq":1,"op":"add","memberId":"u_7f3a","role":"editor","by":"<owner指纹>","ts":…,"prev":"<上一行哈希>","sig":"…"}
{"seq":2,"op":"revoke","memberId":"u_9c21","by":"<admin指纹>","ts":…,"prev":"…","sig":"…"}
```

- `prev` = 上一行哈希 ⇒ **哈希链**，**直接复用** `kernel/workflow-engine.mjs:39-56` 的既有模式与 `verifyRun` 复算思路
- `sig` = 操作者**私钥签名**（Ed25519，密钥对在 §5.9 新建团队第①步已生成）
- 任一成员可本地复算全链验证

| 攻击 | 为何失败 |
|---|---|
| 改某行内容 | 该行哈希变化 ⇒ 链断，且签名失配 |
| 删中间一行 | `prev` 失配 ⇒ 链断 |
| 插入伪造行 | 无对应私钥 ⇒ 签名验证失败 |
| 删掉整个日志文件 | **其他成员的副本仍在**（网盘各自持有一份）⇒ 多副本互为见证 |

**追加式同时解决同步盘问题**：append-only 不修改历史 ⇒ 网盘不产生"同一文件两端改"的冲突（§7.1）。

⚠️ **单机版的诚实边界**：私钥以本地文件形式存在 ⇒ **防的是"改共享目录上的文件"，不防"拿到你本机私钥的人"**。
但这正是要防的：**共享目录被攻破 ≠ 能伪造签名**。企业版接 OS 密钥链 / TPM（§13 S5）。

⚠️ **单机版的「邀请」没有强制力**：团队源为共享目录 / 同步网盘时，读取权限由 **OS ACL / 网盘权限**决定，应用无权干涉。
"邀请"仅为**应用层登记**，不阻止任何有该目录权限的人读取全部内容。

因此邀请界面**必须**以**小字明示**：

> 「访问权限由共享目录 / 网盘的操作系统权限控制，请另行设置。」

且**不得使用任何暗示"数据已加密"或"仅受邀者可读"的措辞**（验证码亦须说明其**仅为成员登记**，见上）。
这是 §11「UI 措辞风险」的直接收敛项。

#### 模式切换的数据语义（关键约束）

| 受模式影响 | **不受**模式影响 |
|---|---|
| 侧边栏默认列表（会话 / 工作流 / 知识）的**筛选范围** | **知识检索范围**——默认**跨全部空间**，结果**标注来源** |
| 新建内容的**默认归属** | 已有会话 / 文档的**可见性** |

**为什么检索不做隔离**：知识空间本就是并列模型（`shared/knowledge-core.mjs:507`），搜索天然跨空间。
一旦按模式隔离，用户会反复遇到"我明明存过怎么搜不到"。

**为什么必须明说"模式 ≠ 隔离"**：若 UI 让用户以为"切到个人模式 ⇒ 团队数据不可见 ⇒ 安全"，
而数据实际就在本地磁盘上，就是在制造**虚假安全感**——这比不提供该功能更危险。

> 📌 **批注 #5** · 推进前置确认 —— **模式开关对"新建内容归属"是否有例外**（个人模式下想直接建团队会话时，是否需二次选择）。影响本节交互细节；索引见 §14-5。

#### 数据模型影响（S2 必须一并落地）

模式开关决定了**内容归属** ⇒ 须在 S2 与 `authorId` **同批**落盘 **`workspaceId`**（见 §6.2 D4）。

会话、知识条目、经验、工作流均需带归属工作区；个人工作区用固定值 `personal`。

#### 写入契约（批注 #2 定案，S1 落地）

**决策**：① 旧的全量 `blocks` 写法**不保留**；② 改由 **GUI 发 `ops`**（精确，无歧义）。

```json
POST /write-docx
{ "path": "方案.docx",
  "baseVersion": "<读取时返回的基线版本>",
  "ops": [ {"op":"update","blockId":"…","text":"…"},
           {"op":"insert","after":"…","block":{"kind":"p","text":"…"}},
           {"op":"delete","blockId":"…"},
           {"op":"move","blockId":"…","after":"…"} ] }
```

| 定案项 | 内容 |
|---|---|
| 旧路径 | **不保留**。收到只带 `blocks` 的请求 ⇒ **显式报错**，不得静默降级到旧逻辑 |
| `zip()` | **删除**（B1 根除） |

| 上线方式 | 后端与 GUI **同版本一起改**（已核 §2.1：无第三方消费者） |
| 安全保障 | 依靠 §9 的**回归测试网**，**不依靠保留旧代码** |

> **S1 阶段**无版本链 ⇒ `baseVersion` = **文件内容哈希**（读取时算出）；

| 性质 | 要求 | 实测依据 |

| 归一化 | 比对前抹平样式/run 切分差异 | 既有先例 `TEXT_EXTS` 行尾归一 |

### §7.1 同步网盘专节（定案 13）

**定案 13 明确：团队源可能是带同步客户端的网盘（OneDrive / 坚果云类），不是"普通共享盘"。**
这不是同一类东西——同步网盘的下列**四个行为**会直接击穿"共享可写索引"的朴素假设：

| # | 同步网盘的行为 | 朴素方案的后果 | 本设计的对策 |
|---|---|---|---|
| 1 | **冲突副本**：两端同改一个文件 → 生成 `x-副本.docx` / `x (1).docx` / `x.conflict-…` | 共享的 `manifest.json` 必然反复冲突，索引失去权威 | **索引一律不共享**：改为**每设备一条 append-only 日志**，本地重放得当前状态 |
| 2 | **同步延迟**：非实时，窗口期可达分钟~小时 | 基于"读到最新"的乐观并发判定失准 | **本地重放（事件溯源）**：延迟只影响"看到的新鲜度"，**不影响一致性**；且**禁用 `fs.watch`**（网盘文件事件不可靠）⇒ 改**轮询扫描** |
| 3 | **占位符脱水**：OneDrive Files On-Demand 的 reparse point，读时触发下载 | 读到占位符或读到空文件 | **复用 `_common/onedrive_utils.py`**：`detect_placeholder_file` 识别 + `pin_file` 钉选防脱水 |
| 4 | **`CldFlt.sys` 驱动拦截**：OneDrive.exe 未运行时仍拦截写入 ⇒ **"写入成功但文件随后被清空"** | 团队源静默丢数据 | **复用 `safe_workspace.py`** 的安全区模式；写入后必须 `verified_write` 校验，**不得假定写成功** |

此外两条硬约束：

- **网络盘无原子 rename** ⇒ 写对象一律：**写 `.tmp` → 校验内容哈希 → rename 为最终名**。即使 rename 失败，残留的 `.tmp` 可辨识、可清理，不会污染 CAS。
- 🛑 **团队源目录内禁止存放 git 仓库**。网盘同步 `.git` 会损坏仓库且性能灾难。应用**检测到 `.git` 落在同步根内须告警**。

**核心架构决策：团队源 = 只追加日志 + 内容寻址存储，不是共享数据库。**

```
<team-source>/
├── team.json                    # 明文：teamId、9 位识别码、算法参数、salt（★不含团队密钥）
├── members/
│   └── log-<deviceId>.jsonl     # 每设备一条追加日志 · 签名哈希链（§5.9 防篡改）
├── keys/
│   └── <memberId>.env           # 邀请信封（验证码保护的团队密钥；加入后作废）
├── cas/
│   └── <hash[0:2]>/<hash>       # 内容寻址对象：不可变、永不原地改 ⇒ 免疫冲突副本
├── versions/
│   └── <fileId>.jsonl           # 版本链（追加式）
└── claims/
    └── <fileId>.jsonl           # 软占用：claim / renew / release / takeover（追加式）
```

**为什么"全 `.jsonl` 追加式"是正解**：网盘的冲突只发生在"**同一文件被两端同时修改**"。
- **不可变对象（`cas/`）**：文件名 = 内容哈希 ⇒ 同名即同内容 ⇒ **根本不冲突**（这是内容寻址在网盘上的天然优势）
- **追加日志（`*.jsonl`）**：即使两端同时 append 触发网盘冲突副本，**本地重放时把冲突副本一并扫入**，按记录 id 去重即可还原完整日志

> **冲突副本的自动吸收**：扫描器须识别 `log-<id>.jsonl`、`log-<id> (1).jsonl`、`log-<id>-副本.jsonl` 等变体，
> 全部读入 → 按记录 id 去重 → 得到完整日志。**网盘的"缺陷"在此变成"分片"**。
> 这是 **G-Set / OR-Set 语义用文件系统实现**——零协议、零服务端。

### §7.2 团队源目录布局

见 §7.1 的目录树，即 S3 的交付布局契约。要点：

| 原则 | 说明 |
|---|---|
| **不可变优先** | 能用内容寻址表达的，一律不落地为可变文件 |
| **可变者必追加** | 成员、版本、占用三类状态全部 append-only，**永不原地改** |
| **密钥不落明文** | 团队密钥只存在于 `keys/` 的信封内（验证码保护）与成员本机 |
| **单设备单日志** | 每设备写自己的 `log-<deviceId>.jsonl` ⇒ **多设备并发写互不冲突**（这是网盘上唯一安全的并发写形态） |

> 📌 **批注 #8** · 推进前置确认 —— **团队源体积上限策略**：网盘多有配额，大文件（L-D 类设计稿/视频）是否进团队源、有无单文件上限。
> 可复用 pack 的 `PACK_LIMITS` 思路（`shared/knowledge-pack.mjs:27-32`）；索引见 §14-8。

**内容同步的插入点**：知识空间加 `team-<id>`（插在 `shared/knowledge-core.mjs:507` 的 `builtinSpaceSpecs`），下层检索/切分/关联/路由**零改动**（下游只认 `spaceId` 与 `source`）。

**经验同步**：经验条目 id 已是内容寻址（`hashLine`）⇒ **团队经验库 = 条目集合，合并 = 集合求并，零冲突、无需 CRDT**。
⚠️ 两个障碍：作者位硬编码（D4）；一主题一文件（`memory/personal/<theme>.md`）——解法是**合并单位从"文件"下沉到"条目"**。

**安全先例照抄**：下载 URL 强制与清单**同源**（`server/knowledge-pack-install.mjs:744`）；复用 pack 的 manifest/指纹/台账与可执行文件黑名单。

## 10. 验收标准

**S1**
1. `read` 输出的块序**等于文档真实顺序**（表格穿插正确）——以 §2.2 的受控 docx 为基准用例。
2. 每块有**稳定 blockId**：同一文件多次读一致；经 Word 重存（内容不变）后仍一致。
3. `write` 支持 insert/delete/update/move；**块数不匹配时显式报错**，绝不静默丢弃。
4. 三路合并：T5、T6、T9 场景 0 冲突；T7 场景正确报冲突；**B2 场景（同表不同单元格）0 冲突**。
5. 格式变更**不再被判定为"无变化"**。
6. xlsx 插入 1 行后，按行内容指纹对齐能正确识别为"1 行插入 + 0 处修改"（B6 回归）。
7. 上述脚本**测试覆盖从 0 起步**，S1 交付时核心路径均有回归测试。

**S2**
1. `netstat` 确认 bridge **仅监听 127.0.0.1**。
2. 无 Origin 头且无 token 的请求返回 **401**；携带正确 token 的本地客户端全通。
3. 出网闸：默认配置下，transcript/config 等敏感数据**无任何出网路径**。
4. transcript、记忆、工作流定义三处均落 `authorId`；`stats` 能按 author 聚合。
5. 标签为独立实体，支持别名合并与个人/团队作用域。
6. 会话、知识条目、经验、工作流均带 `workspaceId`；个人工作区为 `personal`。

**S3 / S4（UI 形态与协同行为，随各自 spec 细化）**
1. header 模式开关可切换个人 / 团队；团队态下可切换具体团队工作区；无团队时显示空态引导。
2. **新建团队**向导 3 步可完成，且**先建工作区实体、再配团队源**（§5.9 顺序要求）；结束时显示 9 位识别码。
3. **加入团队只需两个数字**：输入 9 位识别码 + 6 位验证码即完成，**无需输入任何路径**（搜索根已设置的前提下）。
4. 首次加入可设置「团队目录搜索根」并**被记住**；未匹配到团队时给出可操作提示 + "手动选择目录"兜底。
5. `.yfwteam` 邀请包仍可用（兜底路径），拖入即完成配置。
6. **验证码一次性**：同一验证码二次加入失败；过期验证码失败；错误验证码被拒并计入限速。
7. **成员清单防篡改可验证**：手工篡改 `members/log-*.jsonl`（改 / 删 / 插一行）后，任一成员的应用均能**验签失败并告警**。
8. **同步网盘行为**：在同步盘上制造冲突副本（`log-x (1).jsonl`）后，应用**自动吸收**，状态与无副本时一致。
9. **同步延迟不破坏一致性**：断网编辑 → 恢复同步 → 两端最终收敛，且**无内容丢失**。
10. **文件模态分层生效**：L-B（pdf / 图片）只追加版本、无原地写；L-D（pptx 等）为独占检出 / 检入。
11. **邀请界面含小字明示**："访问权限由共享目录/网盘的操作系统权限控制，请另行设置"。
12. **全 UI 措辞审查**：不得出现暗示"已加密""仅受邀者可读""模式即隔离"的表述；验证码界面须说明其**仅为成员登记**，非数据加密。
13. 切换模式后，知识检索仍跨全部空间且**结果标注来源**（不出现"搜不到已存内容"）。

## 11. 风险与缓解

| 风险 | 缓解 |
|---|---|
| **S1 改造破坏现有应用内 Office 编辑** | **先补回归测试锁住现有语义**——这是本项**唯一的保险**（批注 #2 已定：不靠保留旧代码路径）；后端与 GUI **同版本上线** |
| **blockId 引入格式指纹后，Word 重存导致 id 漂移** | §6.1 的联调验收项：C2+C4 完成后**必须重跑 T2** |
| **软权限被误认为强权限** | UI 明示"单机版权限为协作约定"；越权操作留痕 |
| **UI 措辞制造虚假安全感**：「邀请」被理解为"已授权"、「模式」被理解为"已隔离"，而实际都无强制力 | §5.9 强制小字明示权限来源；**禁止任何暗示加密/隔离的措辞**；列为 §10 验收项 |
| **共享目录上的并发写（非应用引起）** | 不依赖锁（P4）；以内容哈希判定，冲突进处置 |
| **企业版 admin 后台数据为空** | D4/D5 现在落盘；否则历史数据永远补不回 |
| **误以为 git 已集成** | §2.1 已注明 `/worktrees` `/branches` 是**只读展示** |
| **协同范围蔓延到实时协同** | §12 明确列为非目标；定案 10 已确认真并发只占少数时段 |
| **把同步网盘当本地盘用**：依赖 `fs.watch` / 文件锁 / 原子 rename | §7.1 明令改为轮询扫描、无锁、写 `.tmp`→校验→改名；`file_lock.py` 明确不可移植（§2.3 ④） |
| **同步盘的冲突副本被当成"普通文件"而漏读或误判为新版本** | §7.1 要求扫描器显式识别副本命名变体并吸收；列为 §10 验收 8 |
| **团队源落在网盘"按需文件"区，读到占位符 / 写入被 CldFlt 拦截后清空** | 复用 `onedrive_utils.py` 的 `detect_placeholder_file` / `pin_file`；写入后 `verified_write` 校验（§7.1） |
| **团队源目录内混入 `.git`** | §7.1 硬约束：检测到即告警 |
| **6 位验证码被离线爆破** | 一次性 + 默认 7 天有效 + `scrypt N=2^15`；真实边界为网盘 ACL（§5.9） |
| **把 `output_version_manager.py` 的 `.bak` 备份习惯带进团队协同**，造成文件膨胀 | §5.1 末明确不采用备份式版本管理；一切变更走**追加版本链** |
| **未覆盖格式被"硬凑"成可合并**（如 docx→md 降维） | §5.1 三层兜底明确规定降级路径；§12-7 已列为非目标 |

## 12. 非目标（YAGNI）

1. **实时协同编辑（CRDT/OT）**——定案 10 确认真并发集中在少数时段，收益撑不起成本。
2. **多人共用同一 agent 会话**——`kernel/session.mjs:180` 明载"同会话同时只有一个内核 writer"是未支持状态；且违反 P1 红线。
3. **服务端沙箱执行**——定案 6 明确当前不考虑。
4. **自建账号体系**——企业版建议对接外部身份（AD/LDAP/OIDC），不自建。
5. **网页端/移动端**——定案 5，应用只在桌面端。
6. **大团队权限继承树、审批工作流引擎**——定案 7，交企业版。
7. **docx→markdown 降维以求可合并**——格式保真度损失不可接受。
8. **git 作为文件版本层**——当前仅有只读展示，且 Office 二进制在 git 下需 LFS，模型冲突。留待单独评估。

## 13. 子项目边界与实施顺序

```
S2（地基：安全 + authorId）──┬── 独立，建议最先（D1/D2 是现存安全暴露）
                             │
S1（文档协同模型）──────────┴── 独立，可与 S2 并行
        │
        └──▶ S3（团队源与内容协同）──▶ S4（文件协同）──▶ S5（企业版）
                 依赖 S2 的出网闸与 authorId        依赖 S1 的合并能力
```

| 边界 | 约定 |
|---|---|
| S1 → S4 | S1 只交付**块模型 + 写入语义 + 合并原语**（纯函数，无 UI、无同步）；S4 消费 |
| S2 → S3 | S3 只依赖 `syncPolicy` 闸门、`authorId` 与 `workspaceId`；不依赖 D3 的内部实现 |
| **UI 归属** | 工作区/模式开关/新建/加入/成员管理 UI → **S3 自带**；协同编辑器与冲突处置 UI → **S4 自带**；S1/S2 均**不含 UI**（§0） |
| S3 → S4 | S3 提供 Team Source 抽象与草稿存取原语；S4 在其上实现并发/冲突/交付 |
| S3 → S5 | S5 只替换 Team Source 后端实现，**上层零改动**（§7 的表即契约）。**定案 14：当前只做个人版**——S3/S4 **不得**为 L2 预埋实现（预留服务端字段、写死协议等），只保证抽象边界干净 |
| S2/S5 → admin | admin 是**只读聚合**消费者；其数据形状由 D4/D5 在 S2 定好 |

**建议实施顺序**：S2 的 D1/D2（安全修复，最紧急）→ S2 的 D3/D4/D5/D6 → S1 → S3 → S4 → S5。
