# 应用智控·通用接入技术路线 设计方案

日期：2026-09-14
状态：待评审（未实现）
关联：`docs/superpowers/specs/2026-09-14-应用智控-登录态-design.md`

## 1. 为什么做这件事

用户诉求（原话）：

> 不是要接（Aseprite），而是要形成一套可以自动化接入的技术路线，使用户可以尝试接入并自动化控制其他应用。
> 一般来说要让 LLM 尽可能去获取接口 / chunk 等任何类型的可控制路径，然后根据统一格式规范要求封装，
> 在控制面板内用户控制或给 agent 提要求，agent 实现自动化。
> 有很多原生应用是有开源的 CLI 工具的，LLM 执行时需要联网确认。如果评估明确无法形成 CLI，可以先告知无法接入。
> 条数尽可能多，不要硬性要求；质量控制阈值建议 LLM 评估，不要写死条数，质量是根据实际应用/网站决定的。

一句话目标：**把"接入一个新应用"从"靠探测结果碰运气"变成一条可复现的流水线**——
穷尽可控路径（Discovery）→ 按统一格式封装（Packing）→ 面板控制与 Agent 自动化（Automation）。

非目标（本设计明确不做）：
- 不做通用 GUI 录制/回放引擎，不引入原生 UIA 依赖（用户已选"用现有工具替代"）。
- 不做"任意应用都能自动接入"的承诺：**探不到可控路径时就如实说不能接入**，并给出下一步建议。
- 不追求命令条数指标：条数由模型按应用实际决定。

## 2. 现状与缺口（均已核实）

### 2.1 已有的骨架（可复用，勿重造）

| 能力 | 位置 | 说明 |
|---|---|---|
| 生成循环 | `electron/app-agent.cjs` `runAgentLoop` | 工具驱动的多轮：探索 → 提交草稿 → 真实试跑 → 按报错调试；预算 24 轮 / 20 次工具调用 / 10 分钟 |
| 提示词工厂 | 同上 `buildAgentSystem` / `buildAgentSeed` | 已含"优先做接口级封装"等探索教义、硬约束、输出格式 |
| 统一格式校验 | `electron/app-generate.cjs` | `SPEC_SHAPE_LINE` / `validateSpecBasic` / `actContractLines` / `actsFor` / `driverOf` |
| 执行后端 | `electron/browser-executor.cjs`、`electron/app-runner-desktop.cjs` | web：goto/click/type/select/scroll/hover/js/wait/snapshot（`js` 支持 await）；桌面：cli/script/uia |
| 命令即工具 | `kernel/app-tools.mjs` | Spec 命令 → 工具（description 取 title，schema 取 params） |
| 联网能力 | `kernel/tools.mjs` `WebFetch` / `WebSearch` | 走端点原生 `web_search_20250305`，**零新依赖** |

### 2.2 四个真实缺口

**① 桌面侧 LLM 几乎没有探索工具。** `electron/app-ipc.cjs` 的 `runTool` 里，web 有
`fetch_page / list_pages / browse / click / back / request_login / run_command / submit_spec`；
桌面**只有 `run_command` + `submit_spec`**。用户要"尽可能获取接口/chunk 等任何可控路径"，
但模型没有读帮助、列目录、看数据格式、翻配置文件、查网络的手段——只能凭训练记忆猜。

**② 探测产出的是"一个级别"，不是"可控路径清单"。** `electron/app-profiler.cjs` 的
`probeDesktop` 按 `process → script → uia` 命中即停，返回 `{level, evidence}`；全不中则
**直接拒绝生成**（`stoppedBy: 'uia-unsupported'`）。而"清单 + 每条路径的证据与可信度"
才是封装所需的东西。此外旧实现只回一句笼统结论（本轮已修为带真实原因，见 §7）。

**③ 统一格式的通道面太窄。** `ACTS_BY_DRIVER` 只有 browser / process / script / uia。
HTTP 接口（可脱离浏览器直调）、数据文件（读写/查询本地工程文件）、配置、扩展插件、IPC
这些通道**在格式里没有位置**——即便 LLM 探到了，也无处安放。

**④ 质量校验是静态规则，且需求从未进入生成链路。**
`checkSpecQuality` 用 `minCommands`（有素材 3 条 / 无素材 1 条）等阈值，且只是警告；
生成提示词里只有 `目标：{"type":"web","url":"…"}`——**应用名称、描述、用户需求一条都没传下去**
（用户填的"描述"只在保存时写进 registry）。这解释了"001 只生成 4 条、不满足要求"。

## 3. 设计总览

三层流水线 + 一个横切的证据账本：

```
         ┌────────────── Evidence Ledger（证据账本，全程可追溯）──────────────┐
         │  每条"可控路径"都带：来源、原始证据片段、可信度、验证方式与结果      │
         └────────────────────────────────────────────────────────────────┘
   Discovery                     Packing                        Automation
 穷尽可控路径                  统一格式封装                      面板/Agent
 ─────────────                 ────────────                     ──────────
 · 通道探测器（多通道）    →   · Spec 扩展：driver + step.act  →  · 面板：能力清单/试跑/改造
 · LLM 工具集（含联网）         · 需求字段贯通                    · Agent：命令即工具（已有）
 · 能力清单（Capability         · 质量为 LLM 评估（不写死条数）     · 失败可回喂重生成
   Surface）输出                  · 兼容既有 Spec                  · 无法接入→如实告知
```

**关键设计决策：`driver` 表示"谁来执行"，不是"怎么发现的"。**
现有 `driver` 取值 browser/process/script/uia 语义是执行后端，保持不变；
新增 `http`、`file` 两个后端。通道（channel）是**发现阶段的归类**，与 driver 多对一：
例如"发现一个 JSON 接口"→ 既可用 `browser` + `js` 步骤执行（自带登录态），
也可用 `http` + `request` 步骤执行（快、无需浏览器）。

## 4. Discovery 层

### 4.1 能力清单（Capability Surface）：新的中间产物

取代"单级判定"，探测输出一份清单，每条一个 `capability`：

```jsonc
{
  "channel": "cli",              // cli | http | chunk | file | extension | web-ui | cli-external | unusable
  "driver": "process",           // 建议的执行后端
  "confidence": "verified",      // verified（本机实测通过）| probable（有迹象未验证）| unusable（明确不成立）
  "evidence": "aseprite.exe --help → 5823 字节，含 --batch/--sheet 等开关",
  "probe": { "how": "execFile --help", "exitCode": 0, "outLen": 5823 },
  "next": "可直接包装 CLI 命令"   // 给 LLM 的下一步指引
}
```

清单是**报告的输入，不是判定的替身**：即使只有 `probable`，也照样把清单交给 LLM 继续探索
（而不是像现在这样判不出 process/script 就整体拒绝）。

### 4.2 通道探测矩阵

| 通道 | 探测手段（全部只读、无副作用） | 判定 | 目标 |
|---|---|---|---|
| cli | 多开关帮助探测（`--help/-h/--version//?`）、目录解析主程序、`.bat/.cmd` 走 shell | verified | 已有（本轮增强） |
| cli-external | **联网检索**「<应用名> CLI / command line / headless」+ WebFetch 官方文档 | probable | **新增（用户明确要求）** |
| script | 同级 `scripts/`、`plugins/`、`extensions/`、`*.lua/js/py` | verified | 已有 |
| file | 工程/数据文件与配置：`*.json/ini/xml/csv/sqlite`、用户数据目录 | probable | **新增** |
| http | 站点接口：从首屏 HTML 的内联脚本/表单 action、以及 **JS chunk** 里反解路径与参数 | probable | **新增（用户点名的 chunk）** |
| web-ui | 页面可达性与入口结构（已有 fetch_page/browse 能力） | verified | 已有 |
| unusable | 以上全不成立 | unusable | 如实告知 |

### 4.3 LLM 工具集扩展（`electron/app-ipc.cjs` 的 `runTool`）

新增（桌面路径缺失最严重，web 补 chunk 与联网）：

| 工具 | 作用 | 复用 |
|---|---|---|
| `list_dir` | 列安装目录 / 用户数据目录 | 新（只读、白名单范围） |
| `read_file` | 读文本/配置/脚本（截断上限、二进制拒绝） | 新 |
| `run_command` | 已有；补 `cwd` 与超时/输出上限的显式约束 | 有 |
| `web_search` | 联网确认是否存在开源 CLI、官方是否提供 headless/API | 复用 `kernel/tools.mjs` 实现 |
| `fetch_page`/`browse` | web 侧已有 | 有 |
| `list_requests` | 列出浏览会话中观察到的网络请求（接口线索） | 新（基于浏览器执行器网络事件） |

安全边界：`list_dir/read_file` 限定在"目标程序所在目录及其子目录 + 该应用的用户数据目录"，
拒绝系统目录；沿用现有 `isSystemPath` 守卫。只读，不写不改。

### 4.4 探索教义（写入 `buildAgentSystem`）

桌面侧补齐与 web 对称的探索教义（现状桌面只有两句"写草稿/调试"，等于没教）：

1. 先跑 `run_command` 读帮助（`--help`；无输出就试 `-h`/`--version`/`/?`）。
2. 帮助不足时：列目录看有无 `scripts/`/插件目录/数据文件；读配置与文档文件。
3. **联网确认**：`web_search` 查"<应用名> CLI/headless/API"，有开源 CLI 就 `fetch_page` 读用法。
4. 找到接口线索（表单 action、内联脚本、JS chunk、已观察请求）→ 优先做**接口级**命令。
5. 探不到就**如实收手**：提交"无法接入"结论与理由，不要硬凑。

## 5. Packing 层

### 5.1 统一格式扩展（兼容既有 Spec）

`driver` 新增两个值，`step.act` 对应扩展：

```jsonc
// http：脱离浏览器直调接口
{ "act": "request", "method": "GET", "url": "https://api.example.com/items",
  "headers": { "Accept": "application/json" }, "query": { "page": "${page}" },
  "body": { "…": "${参数名}" }, "save": "items" }

// file：本地工程/数据文件
{ "act": "read",  "path": "${filePath}", "format": "json|text|csv|ini", "save": "doc" }
{ "act": "write", "path": "${outPath}", "format": "json", "from": "doc" }
{ "act": "query", "path": "${filePath}", "format": "json", "select": "$.frames[*].name", "save": "names" }
```

- 校验：`actContractLines` / `actsFor` / `ACTS_BY_DRIVER` 同步扩展；**既有 Spec 不受影响**（只增不改）。
- 执行后端：`app-runner-desktop.cjs` 增 `request`（node fetch，超时/大小上限）与 `file`（只读为主，
  write 需 kind=write 且路径在允许范围）。
- 参数插值规则不变（`${参数名}`）。

### 5.2 需求字段贯通（修 001 类问题的根）

- UI 的"描述"旁**新增独立「需求」字段**：描述供人看，需求进提示词。
- 链路：`app:generate` 入参带 `requirement` → `buildAgentSystem` 增加
  「【用户需求】…（作为覆盖度硬约束：需求里点到的能力都必须有对应命令）」段 →
  `buildAgentSeed` 同步。
- 兼容：无需求时该段省略（不改变既有行为）。

### 5.3 质量控制：改由 LLM 评估

- **保留硬校验**（必须能跑）：结构完整、act 合法、ref 来源合法、参数插值合法——这是安全网。
- **移除写死的条数阈值**：`minCommands = 3` 之类不再作为质量结论。
- **新增 LLM 质量评估轮**：全部试跑通过后，用同一次会话追加一次"评审"调用，让模型给出
  结构化结论：`{coverage, gaps[], verdict: 'ok'|'thin', suggestions[]}`，
  并按 `suggestions` 决定是否再来一轮补全（受既有预算约束）。
- 理由（采纳用户意见 + 现有作者顾虑）：条数与应用规模强相关，写死条数会逼模型凑数或永远交不出东西；
  让模型对着"用户需求 + 已探明能力清单"评判覆盖度，才是与实际应用匹配的标准。

## 6. Automation 层

### 6.1 控制面板（`src/components/apps/AppConsole.tsx`）

- **能力清单可视化**：展示 Discovery 产出的每条通道（含 evidence 与可信度）——
  用户能一眼看到"这个应用为什么这么接、还有哪些路没走通"。
- **命令试跑**：逐条运行并回显真实输出（已有执行链路，补 UI）。
- **提要求 → Agent 改造**：用户用自然语言提需求（"再加个导出全部图层的命令"），
  走既有的 repair 链路（`electron/app-validator.cjs`）增量改造 Spec，而不是整份重生成。

### 6.2 Agent 自动化

- 命令即工具已具备（`kernel/app-tools.mjs`）；本设计只要求：
  title / params[].desc 的质量（已在校验里强调）直接决定工具可用性。
- 面板里"试跑通过"的命令才允许被 Agent 调用（沿用现有暴露策略）。

## 7. 错误处理与"无法接入"文案协议

分三种结论，措辞不得混用（旧实现把三者都写成"未发现 CLI/脚本接口"，把用户误导成"功能坏了"）：

| 结论 | 触发 | 文案要点 |
|---|---|---|
| 可接入 | 至少一条 verified/probable 通道 | 正常生成；面板展示通道清单 |
| 证据不足 | 有 probable 但试跑全失败 | 列出已试路径 + 真实报错 + 建议（补路径/装 CLI/改 web 接入） |
| 无法接入 | 全部 unusable | **明确说"无法接入"** + 已排查的通道与证据 + 下一步建议（找开源 CLI / 官方 API） |

本轮已落地的部分（作为协议的先行实现）：探测失败时回传 `evidence.attempts`，
拒绝文案附「探测详情：CLI：…；脚本接口：…」，并支持安装目录与 `.bat/.cmd`（见 §9 M0）。

## 8. 测试策略

- 探测层：纯函数 + 注入假依赖（已用 `deps.processProbe` 模式）；真实文件系统用临时目录。
- 格式层：`actContractLines`/`actsFor` 的新 act 用例；**回归断言既有 Spec 仍合法**（只增不改）。
- LLM 层：假 LLM（既有 `kernel-tests/app-generate-ipc.test.mjs` 夹具）验证
  ①需求进了 system prompt ②质量评估轮在期望时机被调用 ③无需求时行为不变。
- 端到端：以 Aseprite（有 CLI）与本次的 yfljsj（有接口/需登录）为**两个基准样本**，
  同时覆盖桌面与 web 两侧（用户要求首版两侧同时）。

## 9. 分期实施（每期可独立验收）

| 期 | 内容 | 验收 |
|---|---|---|
| **M0**（已完成） | 探测回显真实原因、安装目录解析、`.bat/.cmd` 走 shell、多开关探测 | 单测全绿；Aseprite 目录输入不再误报 |
| **M1** | 需求字段贯通（UI + IPC + 提示词） | 001 类："需求"进入 prompt，命令覆盖需求点 |
| **M2** | 统一能力清单（Capability Surface）+ 探测输出改造 + 桌面探索工具（`list_dir`/`read_file`）+ 联网确认（`web_search`） | Aseprite：能列出 cli/script/file 通道；无 CLI 应用能查到开源 CLI |
| **M3** | 格式扩展 `http`/`file` 驱动与执行后端 | 新 act 试跑通过；既有 Spec 回归不受影响 |
| **M4** | 质量改 LLM 评估（去写死条数 + 评审轮） | 001 类：评审给出 gaps 并触发补全 |
| **M5** | 面板：能力清单可视化 + 试跑 + 提要求改造 | 用户可在面板看到通道与证据并试跑 |

## 10. 风险与取舍

- **探索成本**：新增工具会拉长生成时间/轮次。对策：沿用现有预算（24 轮/20 调用/10 分钟）
  并在提示词里按"帮助→目录→联网"优先级引导；预算耗尽的处理保持现状（交付已试跑通过的部分）。
- **联网检索的可靠性**：可能存在开源 CLI 但检索不到。定位为 `probable` 而非 `verified`，
  必须本机实测才升级为 verified。
- **接口直调（http）的鉴权**：脱离浏览器后拿不到登录态。定位：`http` 适合公开/带密钥接口；
  需要登录态的场景**继续用 `browser` + `js`**（自带登录态）。此取舍写入契约说明。
- **安全**：新增只读工具一律限定目录范围 + 拒绝系统路径；`file.write` / `request` 的
  破坏性使用（写文件、非 GET 请求）要求 `kind: "write"` 并沿用现有确认链路。

## 11. 待评审确认点

1. M1~M5 的优先级与是否合批（用户倾向"两侧同时"，则 M2 需同时覆盖桌面与 web）。
2. `http` / `file` 两个新驱动的取值与命名是否符合预期。
3. 质量评审轮的形态：追加一次模型调用（本设计）vs 独立评审 Agent。
4. 面板改动范围：仅可视化 + 试跑，还是本轮就要"提要求改造"闭环。
