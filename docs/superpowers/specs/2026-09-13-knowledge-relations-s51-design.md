# S5.1 增量设计：条目级图谱层级 + 引用接入（ref 类型）+ 伪链接修复

> 前序：`2026-09-13-knowledge-relations-design.md`（S5，已交付并合并 main `69e149e`）
> 本文档记录 **S5.1** 的三项增量，均为**用户实测反馈驱动**（"进到文档内部没有关联吗，还是没有做图谱"）。
> 日期：2026-09-13

## 1. 用户实测反馈 → 实证结论

用户提两个问题，实测后**结论与直觉相反**：

| 用户问题 | 实测结论 | 缺口 |
|---|---|---|
| 能否**关联索引到其他经验**（引用一条经验时） | ❌ 显式引用**不参与关联**；且全语料唯一 1 条链接是**误解析垃圾** | 需接入 + 修解析 |
| 颗粒度能否细化到**文档内条目** | ✅ **本来就是条目级**（`related.jsonl` 两端是 `docId#块号`，含同文档内条目互连） | **图谱只画文档节点**，条目级数据没有视图 |

### 1.1 关键实测数据（真实库）

```
related.jsonl 边两端形态（条目级，已验证）：
  experience/communication.md#0 → experience/workflow.md#48     (跨文档条目)
  experience/communication.md#0 → experience/communication.md#1 (同文档内条目)

links.jsonl：全库仅 1 行，且是垃圾：
  {"from":"experience/workflow.md","to":"'a','b'","target":null}
  来源：workflow.md 正文讲 JS 写法时写的  anyOf:[['a','b']]
  → wiki 链接正则 /\[\[([^\]|]+)(?:\|([^\]]+))?\]\]/ 把 **JS 嵌套数组当成了 [[wiki 引用]]**

getGraph：节点 kind='doc'，7 个；关联边被**聚合到文档对**
  → 真实库 74/76 条条目在 workflow.md **同一文件内** ⇒ 条目间 290 条关联在文档级
    **全部塌成自环被过滤** ⇒ `graph --related` 只剩 1 条跨文档边
```

即：**文档粒度的图谱对这个库几乎没有信息量**——这正是用户感觉"没有做图谱"的根因。

## 2. 本次范围（用户已定）

1. **图谱增「层级」开关**（文档 / 条目）
2. **显式引用接入为独立 `ref` 类型关联** + **修伪链接**

## 3. 变更 A：修伪链接（`extractLinks`）

**两道防护**（缺一不可，各自拦住不同的误判）：

1. **排除代码跨度**：匹配落在反引号（`` ` ``）内的跳过。
   依据：`anyOf:[['a','b']]` 出现在行内代码里；这是**通用**防护，
   能挡住未来各种"示例代码含 [[ ]]"（如文档里教人写 wiki 链接的段落）。
   实现：统计匹配位置之前的反引号数量，**奇数 = 位于代码内** → 跳过。
2. **目标形状校验**：wiki / md 链接的目标含 `'"()[]{}<>\s,;` 任一时跳过。
   依据：这些不是路径字符。`'a','b'` 含引号与逗号 → 被拦。

`extractLinks` 返回值增 `index`（匹配在原文中的字符下标），供变更 B 定位块。

## 4. 变更 B：`ref` 类型关联

### 4.1 links 记录增块定位

`links.jsonl` 每行增 `fromLine`（链接所在行号）与 `fromBlock`（该行所属块号，可空）：

- 定位方式：`extractLinks` 给的 `index` → 换算行号（数其之前的 `\n`）→
  在该文档块的 `[line, nextLine)` 区间里找所属块
- 定位不到 → `fromBlock = null`（不丢链接，只是退化为文档级）

### 4.2 ref 边生成规则

对每条 **`target` 非 null**（即 `resolveLinkTarget` 成功）的链接：

- **源**：`fromBlock`（单条条目）；`fromBlock` 为空时取**该文档的所有条目**
- **目标**：被引文档的条目，按 `cos(源条目, 目标条目)` 降序取前 `MAX_REF_RELATED`（**3**）
- `why = { kind: 'ref', to: '<被引文档 docId>', score }`
- `MAX_REF_RELATED=3` 的理由：`workflow.md` 有 57 条条目，引用整篇文档若不设上限会
  一次产生 57 条边（物化膨胀 + 挤占锚点预算）；按**内容相似度**取 top-3，
  "引用一篇文档时最相关的 3 条条目"才是真正值得继续读的

**`target` 为 null（断链/解析失败）→ 不产生任何 ref 边**。
这条同时是**修伪链接的兜底**：即便形状校验漏了某种伪链接，它也 resolve 不到真实文档 → 无边。

### 4.3 优先级与预算

锚点优先级：**tag（结构）× ref（手写意图）× content（派生）**。
三类**合计**受 `MAX_RELATED=8` 约束；`duplicate` 依旧**不占**预算（S5 §5.5）。
裁剪顺序：先保 tag，再保 ref，最后 content（手写意图优先于自动派生）。

### 4.4 可解释性

`why` 必须能展示：ref 边显示"引用：<被引文档标题>"+ 相似度（若按相似度选目标）。

### 4.5 读时校验

`validateRelation` 增 `ref` 分支：**只校验两端块存在**（+ 被引文档仍在）。

**不按内容指纹校验**，理由：引用是**用户手写的意图**，"这条经验引用了那篇文档"这件事
不因文档内容被编辑而失效；若按指纹校验，改一个字就会让引用锚点凭空消失，与用户预期相反。

### 4.6 与「反链」的关系（不混）

- **反链**（S2 既有）：**文档级**显式引用，回答"谁引用了我"，在 Inspector 单独一段
- **ref 关联**：**条目级**，回答"这条经验引用了哪篇文档的哪几条经验"，进「关联」段
- 两者**来源同一份 links、但粒度与用途不同** → GUI 仍分栏（S5 §4.1 的原则不破）

## 5. 变更 C：图谱「层级」开关

### 5.1 内核 `getGraph({ level })`

`level: 'doc'`（**默认**，行为与现状完全一致）/ `'entry'`：

- **entry 级节点**：`{ id: '<docId>#<n>', label: <条目摘要前 40 字>, docId, line, tag, kind:'entry' }`
- **entry 级边**：`related.jsonl` 的 **tag / content / ref** 三类（**排除 duplicate**）
- **显式链接边（doc→doc）不在条目级显示**：它是文档级关系，硬映射到条目会**造假**
  （链接不隶属某一条条目）。条目级的"引用"由 **ref 边**表达，语义更准。

### 5.2 GUI

- 顶部增**层级切换**（文档 / 条目），与既有「关联图层」开关并列
- 条目节点：label = 摘要前 40 字；点节点 → 打开该文档并**定位到该块**（用块 `line`）
- 三类边视觉可区分（禁裸 hex，全部走既有 token）：
  - 显式链接（文档级）：实线 + `--border-default`
  - tag 关联：细实线 + `--border-strong`
  - content 关联：虚线 + `--border-strong`（S5 既有）
  - ref 引用：点线（`strokeDasharray: '1 3'`）+ `--accent` 系
- 条目级节点较多（真实库 76 个）：`fitView` 后允许缩放；不额外做聚类（YAGNI）

# S5.1 第二轮：未关联条目的可视化 + 捕获规则修正

> 触发：用户实测反馈「知识图谱好像只有上部的条目连接了，下边的全都没有连呢，是预期内的情况吗」。
> 用户决策：① 布局改善：**孤岛独立成区 + 图例标注**；② **修捕获规则 + 清存量**（对话碎片）。

## 8. 诊断：两个独立成因叠加

### 8.1 数据层：21% 条目客观无关联（预期内）

条目级图 72 节点中 **15 个度数为 0**（21%），成因两类：

| 成因 | 条数 | 说明 |
|---|---|---|
| **无 tag 的对话碎片** | 7 | memory 自动捕获的**对话原文**（"不太符合我的要求…"、"还是没有，你先自己检查下再交付"） |
| **单例 tag 条目** | 8 | `编辑工具陷阱` `配置修复` `子Agent驱动开发` … 都是**真经验**，但该 tag 全库只出现 1 次 ⇒ 骨架层无邻居 |

**关键量化**（`calib-orphans.mjs`）：孤立条目与**最近邻**的 cosine 全部落在 **0.067~0.148**
（12 条 ≥0.10，**无一条 <0.05**）⇒ 它们不是"真无关"，而是**贴着阈值**。

阈值扫描（无同 tag 关系条目对）：

| T | content 候选对 | 剩余孤立 |
|---|---|---|
| 0.15（现行） | 30 | 15 |
| 0.13 | 62 | 10 |
| 0.12 | 78 | 9 |
| 0.10 | 178 | 3 |
| 0.08 | 376 | 2 |
| 0.05 | 951 | 0 |

⇒ 0.10 是收益/噪声的临界点（再降收益骤减、噪声翻倍）。**本轮不动阈值**（用户选了布局改善路线），
把这份数据留给后续决策。

### 8.2 呈现层：布局把孤岛堆成一堆（不预期 —— 真正的观感问题）

`layoutGraph` 原实现把节点**按度数降序混排**进一个 `MAX_COLS=6` 的网格：

```js
const ordered = [...list].sort((a, b) => deg(b) - deg(a))   // 度数降序
return ordered.map((n, i) => ({ x: (i % cols) * COL_W, y: floor(i / cols) * ROW_H }))
```

⇒ 零度节点**必然连续沉到最底部若干行**。72 节点 = 12 行，15 个孤立 = 底部 2.5 行。
这是 S2 就有的布局，文档级 7 节点时不显眼；条目级 72 节点 + 21% 孤立率才暴露成"像坏了"。

## 9. 改动 A：布局分区（孤岛独立成区 + 画布分区标签 + 顶部图例）

- `layoutSections(nodes, edges)` 新导出：返回 `{ positions, isolatedTopY, isolatedCount, connectedCount }`；
  **关联区与孤立区分别排网格**，两区之间留 `ISOLATED_GAP_ROWS = 1` 个空行
- `layoutGraph` 保留数组签名（既有单测与调用点不动），改为 `layoutSections(...).positions`
- 视图：孤立区上方插一个 `type='kbSection'` 的**纯展示节点**（`SectionLabel`），
  渲染"未关联 N · 主题唯一或内容独特" + 向右虚线；`selectable/connectable/draggable` 全 false
- 顶部**图例**：`未关联 N`（文档级/条目级都显示），带 `title` 解释
- **零度节点不删不隐藏**："这条经验暂时没有关联"本身是信息（那 8 条多是主题唯一的真经验）

## 10. 改动 B：捕获规则修正 + 清存量

### 10.1 根因（`calib-capture-precision.mjs` 定量）

`captureMemoryCandidates` 的 workflow 分支原为：

```js
const workflow = (m.workflow || []).find(x => t.includes(x))   // 含 '先' | '再' | '最后'
if (workflow && !fact && (strongFlow || t.length > 30)) push(...)
```

**弱信号词是单字 `先 / 再 / 最后`**（全库最高频汉字），配"长度 > 30"门槛（几乎任何用户消息都满足）
⇒ **任何较长消息都被当成"流程经验"**。

真实库实测（81 条条目）：

| 来源 | 条数 | 质量 |
|---|---|---|
| agent **主动沉淀**（`[会话\|tag]`） | 63 | ✅ 全部有 tag、零协议文本 |
| **capture 自动产出** | 18 | ❌ **17 条是垃圾**（16「流程要点」+ 1「业务要点」） |

16 条「流程要点」里**含强信号词的 = 0 条** —— 全是弱信号误触发：
对话原文 7 条、协议块 2 条（`执行技能 using-superpowers…`、`【上下文锚定…】`）、空模板 7 条（`用户回答：`）。

### 10.2 修法（两条，缺一仍漏）

1. `DEFAULT_MARKERS.workflow` **删掉单字弱信号**，只留明确声明式强信号：
   `流程是 / 步骤是 / 标准做法 / 推荐做法`；分支去掉"长度 > 30"的宽口径
2. `push` 统一出口加 `PROTOCOL_TEXT_RE = /^(?:【|执行技能\s|用户回答：|用户插话)/` 协议文本闸
   —— 四个分支共用同一套"该不该入库"标准

**判据是起始匹配，不是"包含即拦"**（故意取舍）：真实库垃圾的 `full` 都以协议标记**开头**，
起始判据已足够；而"含【就拦"会**错杀真经验**（用户可能说"用【】标出待确认项"）。
漏拦一条 = 少拦一点噪声；错杀一条 = 用户真经验永久丢失 ⇒ 按不可逆性取小（同 S5 读时校验原则）。

**能力未被阉割**：用户仍可在配置 `memory.markers.workflow` 里自定义放开（有专门用例钉住）。

### 10.3 清存量（真实库，已执行）

备份：`release/_backup_memory_cleanup_<ts>/workflow.md`（可回滚）

| 类别 | 条数 | 形态 |
|---|---|---|
| 无 tag 的 capture 垃圾 | 17 | 7 对话原文 + 2 协议块 + 7 空模板 + 1「业务要点（请注意）：【用户插话…】」 |
| 问答作答的**截断重复行** | 6 | `- 问题 "…（截断） -- 用户回答：` —— 其 `full` 恰是 `用户回答：` 空模板，且相邻行有完整版 |
| **合计删除** | **23** | 61 条有 tag 真经验**完好无损** |

第二类是新发现的同类问题：`server/bridge.mjs:3091` 把问答卡作答
（`用户回答：\n- 问题 "…": 选择了 "…"`）作为用户消息回传，被 memory 捕获后**截断重复**入库。
新规则的两道闸都能拦住它（起始 `用户回答：` → 协议闸；`full = 用户回答：` → 空模板判据④）。

### 10.4 清理效果（实测）

| 指标 | 清理前 | 清理后 |
|---|---|---|
| 条目总数 | 72 | **64** |
| 孤立条目 | 15（21%） | **8（13%）** |
| 其中无 tag | 7 | **0** |
| 剩余孤立 | — | 全部是单例 tag 的**真经验** |

布局（清理后真实数据）：关联区 56 → 6 列 10 行（y 0~828）→ 空 1 行 → 孤立区 8 → 3 列 3 行（y 1012 起）。
