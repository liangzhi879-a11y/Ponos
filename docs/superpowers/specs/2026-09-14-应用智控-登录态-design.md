> 前序：`docs/应用智控-设计方案.md`（v1.1）、`docs/plans/2026-09-13-应用智控-实施计划.md`（第一~五轮）、
> 提交 `e5a5953`（放开点击/翻页探索 + 登录态探索 + 登录入口）。
> 日期：2026-09-14
> 本文档所有"现状"结论均来自**代码实读**（附 file:line），不含推测。

## 1. 问题（用户诉求 + 代码级证据）

用户诉求（原文）：

> 应用智控功能，很多应用或网站需要登录才能暴露所有端口，允许在获取的过程中提示用户登录，
> 要确保用户手动登陆后，LLM 可以获取到登录状态。

大量站点（SaaS、后台系统、企业应用）把主要功能放在登录墙之后。当前实现在这类站点上**只能拿到
登录前的页面**，生成的命令因此又少又空。代码级证据（4 个缺口）：

| # | 缺口 | 证据 | 后果 |
|---|---|---|---|
| 1 | **素材抓取不带登录态** | `app-http-probe.cjs` 的 `fetchPageMaterial` 只带 UA/Accept，无 Cookie；`harvestSite` 全部走它 | 首页永远是"登录前"的页面；`probeMode=http/http-thin` 素材贫瘠 |
| 2 | **生成过程没有登录提示/暂停点** | `app:generate`（`app-ipc.cjs:190` 起）从取素材 → `runAgentLoop` → 试跑，全程无任何人工交互点；`app-agent.cjs` 的工具集只有 fetch_page/list_pages/browse/click/back/run_command/submit_spec | 用户不知道"该去登录了"；模型只能自己硬猜或反复 browse 同一页 |
| 3 | **登录态按会话分区** | `browser-executor.cjs:588` `partition = 'persist:automation-' + sessionId`；`app:login`/`app:run`/生成探索分别传 chat sessionId 或 `PROBE_SESSION` | 换个会话、新开会话就要重新登录；新增应用（还没有 appId）与保存后执行可能不是同一分区 |
| 4 | **没有"登录完成"的确认与续跑** | 全仓无 `app:login-done`；模型无 `request_login`；`page.logged_in`（`browser-executor.cjs:334`）已有信号但**只被用于"登录过期"提示**，未参与生成流程 | 登录完成后不会自动带登录态重抓，模型拿不到登录后内容 |

**关键观察**：`browse/click/back` 已经能带登录态看到登录后页面（第五轮交付，真机验收通过：
登录后读到受保护内容、命令执行复用登录态、全程无可见窗口）。缺的不是"能力"，而是
**"让用户知道要登录" + "登录后把登录态喂回素材/模型"** 这两段闭环。

## 2. 目标与非目标

**目标**
1. 生成/探测过程中**自动发现登录墙**，高置信度时**自动打开可见登录窗口**；用户手动登录后，
   系统**检测到登录成功并自动继续**（无需用户再点一次"生成"）。
2. 登录成功后**带 Cookie 重新抓取素材**，并把登录后的内容喂给模型 → LLM 确实"拿到登录状态"。
3. 登录态**跨会话复用**：同一应用/站点登录一次，生成期探索、命令执行、任意会话均可复用。
4. 给模型一个 `request_login` 工具：模型自己发现"抓到的是登录页"时可**主动请求用户登录**，
   登录完成后把"已登录 + 重抓内容"回喂给它继续探索。
5. 全程**如实**：登录是否成功、素材是否在登录态下取得，必须如实告知用户与模型，不假装。

**非目标（YAGNI / 明确不做）**
- ❌ 不替用户输入账号密码 / 不存任何站点凭据（密码仍由用户在自己看得见的窗口里输入）
- ❌ 不破解验证码、不做验证码打码（验证码仍由用户在可见窗口里人工处理）
- ❌ 不改 `.yfworking/browser-whitelist.json` 的默认白名单，不新增落盘白名单
- ❌ 桌面应用（driver=desktop）无浏览器概念，不适用本次登录能力（`request_login` 会**明确拒绝**）
- ❌ 不做多窗口并行自动化（沿用 v1 单窗口，见 §7 副作用）

## 3. 已决策项（用户拍板）

| 项 | 决策 | 含义 |
|---|---|---|
| 触发方式 | **检测到就直接弹出登录窗口，检测到成功自动继续** | 命中高置信度登录墙 → 直接 `show()` 可见窗口；轮询 cookie/页面变化判定成功 → 自动重抓素材并继续生成 |
| 登录态范围 | **应用级持久分区，跨会话复用** | 分区键不再用 chat sessionId |
| 模型能力 | **要 `request_login` 工具** | 模型可主动暂停并请求登录，完成后回喂 |
| 等待时限 | **5 分钟超时，仍继续生成但明确警示** | 超时不判失败、不丢弃已探索成果；预览区明确标注"未在登录态下验证" |
| 误判保护 | **仅高置信度自动弹窗，中/弱信号只提示** | 密码框 / `logged_in=false` / URL 命中登录页 → 自动开窗；标题含「登录」等模糊信号 → 只提示 |

### 3.1 设计期的一处细化（需用户知悉）

用户批准的是"应用级分区 `app-<appId>`"。实现时会再加一层优先序：

**web 目标：`app-site-<host>`（按站点主机名）；desktop 目标：`app-<appId>`。**

理由（两条，都是实读代码得出）：
1. **cookie 本身就是按域名存的**——同一站点的两个应用卡片共享登录态，等价于用户在真实浏览器里
   登录一次，符合直觉；反过来"同一站点两卡片各自登录"才是反常。
2. **消除"新增应用"阶段的分区漂移**：新增应用对话框里 ID 可能还没填（ID 是保存时才必需的），
   若键按 appId 取，用户在**生成过程中登录**后保存成正式应用，键就变了 → 登录态"凭空丢失"，
   用户会看到"刚登录过却又要登录"。按 host 取键则从填网址那一刻起就稳定。

对 desktop 目标，键只影响下载目录与事件标签（无 cookie 语义），按 appId 取更贴切。

## 4. 设计总览

```
                      ┌──────────────────────────── app:generate ─────────────────────────────┐
用户填网址 ──► ① 归一网址 + 授权域名                                                          │
                      │                                                                      │
                      ├─► ② 带 Cookie 抓素材 harvestSite(cookieProvider)                      │
                      │        │                                                             │
                      │        ├─► ③ 登录墙检测 detectLoginWall(material)                      │
                      │        │      ├─ 高置信度 ─► ④ ensureLoggedIn（开窗→等成功→重抓）──┐   │
                      │        │      ├─ 中/弱信号 ─► 面板提示（不阻塞）                  │   │
                      │        │      └─ 无信号 ─► 直接继续                              │   │
                      │        │                                                        │   │
                      │        └────────────────────────────────────────────────────────┘   │
                      │                                 素材（登录后）                        │
                      ├─► ⑤ runAgentLoop（模型自主探索）                                     │
                      │       └─ request_login ─► ensureLoggedIn ─► 回喂"已登录+重抓内容"      │
                      │            （等待时间**不计入** 10 分钟探索预算）                     │
                      └─► ⑥ 试跑 read 命令（同一分区，带登录态）                             │
                                                                                            │
渲染层：进度事件 phase:'login' + 等待卡（〔我已完成登录〕〔取消等待〕）+ 登录结果如实展示 ◄────┘
```

关键转场：
- **登录窗口就是执行窗口**：`openWindow(key)` 显示的就是自动化窗口本身（同一分区、同一 session），
  用户登录后关不关窗都无所谓——cookie 已在分区里。
- **成功判定三路信号**（任一成立即算成功，见 §6.3）：cookie 指纹变化 / 快照 `logged_in===true`
  或密码框消失 / 用户点「我已完成登录」。
- **素材重抓是替换而非追加**：登录后重抓的素材**替换** `probeMaterial` 与 `visited`，避免把
  登录前的空壳页当作有效线索喂给模型。

## 5. 组件设计

### 5.1 分区键唯一真源 — `electron/app-session-key.cjs`（新增，纯函数）

```js
appSessionKey({ appId, target })  // → 'app-site-kimi.com' | 'app-my-app' | 'app-probe'(兜底)
partitionFor(key)                 // → 'persist:automation-' + key   ← 分区字符串唯一出处
```

- `browser-executor.cjs` 的 `ensureWindow` 改用 `partitionFor(key)`（不再自己拼字符串）。
- 所有 app 路径统一传该键：`app:generate` / `app:probe` / `app:login` / `app:run` /
  内核桥 `runAppCommand` / `exploreBrowse` / 试跑，**不再传 chat sessionId**。
- 副作用（如实告知）：① 此前按 chat session 存的登录态不通用，需重登一次；
  ② 键在 `app-site-*` 与其它 session 键之间切换时会重建窗口（既有单窗口行为，非新增）。

### 5.2 带 Cookie 抓取 — `electron/app-http-probe.cjs`（改）

- `fetchPageMaterial({ url, cookieProvider, ... })`：`cookieProvider(url)` 返回该 URL 的 Cookie 头
  （或 null）。**只在已注入且该 URL 属授权站点时才带**。
- **手动跟随重定向（≤5 跳）**：每跳**重新**向 `cookieProvider` 索取该跳 host 的 cookie；
  非授权 host（跨站跳转）**不带 cookie**，并停止跟随（避免把登录态发给第三方）。
  这是把 `redirect:'follow'` 换成显式循环的唯一理由。
- `harvestSite({ ..., cookieProvider })`：透传给每一页。
- **不以"是否带 cookie"改变素材解析逻辑**——登录后的页面就是普通页面，解析口径不变。

### 5.3 登录墙检测 — `electron/app-login-wall.cjs`（新增，纯函数，node 可测）

```js
detectLoginWall({ material, page, url }) → {
  needed: boolean,
  confidence: 'high' | 'medium' | 'low' | 'none',
  reasons: string[],
  loginUrl: string | null,
}
```

信号表（**只有 high 会自动开窗**）：

| 级别 | 信号 | 判据 |
|---|---|---|
| **high** | 密码框 | `material.forms[].fields[]` 或 `snapshot.interactives[]` 中存在 `type=password` |
| **high** | 明确的未登录态 | `page.logged_in === false`（引擎已给出，`browser-executor.cjs:334`） |
| **high** | 登录页 URL | path 命中 `/login|/signin|/sign-in|/auth/login|/user/login` 或 query 有 `redirect_uri` |
| medium | 标题/正文含登录词 | `请登录/立即登录/登录已过期/未登录/sign in/log in` |
| low | 疑似空壳 | `looksLikeSpaShell` 且 `interactives` 极少（<3） |
| none | 无信号 | 以上都不命中 |

`loginUrl`：优先取表单里的 `action`（同源才算），其次取 URL 自身（若已在登录页）。

### 5.4 登录编排 — `electron/app-login.cjs`（新增）

```js
ensureLoggedIn({ key, url, executor, deps, emit, waitMs = 5*60*1000, manual = false })
  → { ok, reason: 'cookie-changed'|'logged-in'|'user-confirmed'|'timeout'|'cancelled'|'failed',
      elapsedMs, snapshotHint }
```

流程：
1. `executor.openWindow(key)`（显式 `show()+focus()`，这是**用户主动/系统判定触发**的工具窗口，
   不是莫名弹窗）→ `executor.exec(key,'goto',{url})`。
2. `emit({ phase:'login', waiting:true, key, url, detail })` → 渲染层显示等待卡。
3. **轮询（1.5s 一次，最长 `waitMs`）**三路信号：
   - a) cookie 指纹（`executor.getCookieFingerprint(key, url)`）与开窗前基线相比发生变化 → `cookie-changed`
   - b) `executor.exec(key,'snapshot')` 的 `page.logged_in === true`，或原登录页 URL 已离开且无密码框 → `logged-in`
   - c) 外部信号：用户点「我已完成登录」→ `resolveLoginWait(key)` → `user-confirmed`
4. 成功 → 返回 `ok:true`，调用方**带 Cookie 重抓素材**（§5.2）并继续。
5. 超时/取消/失败 → `ok:false` + **真实 reason**，调用方继续生成但标注"未在登录态下验证"。

**挂起等待的注册表**：模块级 `Map<key, {resolve}>`，配 `resolveLoginWait(key)` / `cancelLoginWait(key)`
两个导出（供 `app:login-done` / `app:login-cancel` 通道调用）。同一 key 重复进入时复用同一个等待。

**可注入**：`executor` 与 `deps.now/sleep/getCookieFingerprint/getCookies` 均可注入，
于是"已登录/自动成功/超时/取消/执行器未就绪"全都能用假执行器单测（不启 Electron、不联网）。

### 5.5 浏览器执行器新增只读能力 — `electron/browser-executor.cjs`（改，最小）

```js
async getCookies(key, url)            // → [{name,value,domain,...}]（该分区、该 URL 可见的 cookie）
async getCookieFingerprint(key, url)  // → 稳定短哈希（无 cookie 时 'empty'）
async getCookieHeader(key, url)       // → 'a=1; b=2' 或 null（供 HTTP 抓取注入）
```

- 实现走 `session.fromPartition(partitionFor(key)).cookies.get({ url })`，**不需要窗口存活**。
- 只读、不改任何既有语义（既有动作表、白名单复检、快照逻辑均不动）。
- 分区字符串来自 §5.1 的 `partitionFor`（唯一真源，不与 `ensureWindow` 重复拼接）。

### 5.6 模型侧 `request_login` — `electron/app-agent.cjs` + `electron/app-ipc.cjs`（改）

- `app-agent.cjs`：
  - `agentToolDocs` 增一条：`{"thought":"…","tool":"request_login","args":{"reason":"…"}}`，
    说明"发现是登录页/内容明显不全、且已知该站点需要登录时用它；用户登录后系统会把登录后的内容回给你"。
  - 探索策略补一句：**不要**反复抓同一个登录页；确属登录墙就 `request_login`。
  - `runAgentLoop` 支持工具结果里的 `pauseMs`：**等待人工的时间不计入 `timeBudgetMs`**
    （否则用户登录 5 分钟会直接把 10 分钟探索预算撞掉，等于"一登录就超时"）。
- `app-ipc.cjs` 的 `runTool` 增 `request_login` 分支：
  - driver 非 browser → 明确拒绝（"桌面应用没有浏览器登录概念"）。
  - 调 `ensureLoggedIn` → 成功后**重抓该应用首页素材**并回喂摘要（`ok:true, pauseMs`）；
  - 失败/超时 → 如实回喂真实原因（`ok:false`），让模型自己决定改走 `browse` 还是继续。

### 5.7 Spec 与自检

- Spec 增**可选**字段 `auth: { needsLogin?: boolean, loginUrl?: string }`：
  `kernel/app-spec.mjs` 的 `validateSpec` 与 `app-generate.validateSpecBasic` 都**不校验未知字段**，
  故向后兼容（老 Spec 照常工作）。**不加就不写**——只有检测到登录墙才写入。
- `app:check` 在 IPC 层叠加一条**运行时**结论（`app-profiler.checkApp` 保持纯 node，不引 Electron）：
  web 目标 + `auth.needsLogin` + 当前分区无 cookie → `status:'drifted'`、
  `issues:['该应用需要登录，当前会话未检测到登录态（AI 调用会被登录墙挡住）；可点「登录此应用」']`。
  这是"如实告知"而非装饰：不提示的话，AI 调用会一直拿到登录页并把失败归因到别处。

### 5.8 IPC 与渲染层

| 通道 | 变化 |
|---|---|
| `app:login` | 改用 §5.1 键；返回值增加 `key`、`opened`；行为仍是"打开可见窗口"（人工入口，保留） |
| `app:login-done` | **新增**：`{ key }` → `resolveLoginWait(key)`，让等待中的生成立即继续 |
| `app:login-cancel` | **新增**：`{ key }` → `cancelLoginWait(key)`，停止等待（**保留已抓素材**继续生成） |

- `electron/preload.cjs` + `src/types/index.ts` 同步（`appLoginDone` / `appLoginCancel`）。
- 进度事件新增 `phase:'login'`（`waiting:true|false`、`key`、`url`、`detail`）。
- `src/components/apps/AddAppDialog.tsx`（生成中）与 `AppConsole.tsx`（登录入口）：
  - 等待卡：「**请在打开的窗口中登录**」+ `〔我已完成登录〕`（手动加速）+ `〔取消等待〕`；
  - 超时/取消后如实展示"本次未在登录态下验证"；
  - 自动成功时展示"已检测到登录（cookie 已更新），正在带登录态重新获取页面…"。
- i18n：`src/i18n/translations/zh-CN.ts` 的 `apps.*` 增键（中英同一套键，英文缺失回退中文既有机制）。

## 6. 时序（正常路径）

```
用户点「生成命令」
  → app:generate
  → harvestSite(with cookies)：拿登录前素材（若有 cookie 则直接是登录后）
  → detectLoginWall → high（密码框 / 登录页 URL）
  → emit phase:'login' waiting:true；openWindow + goto
  ┌ 用户在弹出的窗口里手动登录 ────────────────────────────┐
  │  轮询 1.5s：cookie 指纹变化 → 成功（不等用户点任何按钮）│
  └──────────────────────────────────────────────────────┘
  → emit phase:'login' waiting:false（成功 + 依据）
  → 带 cookie 重抓素材（首页 + 同源主要页）→ 替换 probeMaterial/visited
  → runAgentLoop（模型看到的是**登录后**的素材；预算里扣掉等待时间）
  → 试跑 read 命令（同一分区 → 带登录态）→ 预览 → 用户确认保存
```

超时路径：5 分钟无信号 → `emit phase:'login' waiting:false, detail:'等待登录超时（5 分钟）'`
→ 继续用现有素材生成 → 预览区红字"**未在登录态下验证**：命令可能缺少登录后才能看到的入口"。

## 7. 安全边界

| 项 | 约束 |
|---|---|
| 凭据 | 不读取、不存储、不代填账号密码；窗口由用户自己操作 |
| Cookie 出站 | 只发给**已授权站点**（`authorizeAppTarget` 授权过的 host 及其 www/apex 变体）；跨站跳转不带 cookie 且停止跟随 |
| 白名单 | 不改默认白名单、不新增落盘文件；生成期授权仍走进程内 `isWhitelisted.allow`（既有机制） |
| 破坏性动作 | `isDestructiveLabel` 闸门不变（登录流程不会自动点任何按钮） |
| 单窗口 | 沿用 v1 单窗口；键切换会重建窗口（既有行为）。**不会**在用户已有浏览器会话打开时静默劫持——重建即销毁旧窗 |
| 桌面 | 不适用，`request_login` 明确拒绝 |

## 8. 错误与降级（如实原则）

| 情形 | 行为 |
|---|---|
| 执行器未就绪 | `ok:false` + "浏览器执行器未就绪"，继续生成并标注未验证 |
| 导航被白名单拦下 | 如实回传原因（授权逻辑同现有 `authorizeAppTarget`） |
| 窗口被用户关闭 | 轮询容错（快照/snapshot 取不到不算失败）；cookie 仍在 → 可能直接判成功 |
| 指纹读取异常 | 记日志、跳过该轮判据，其它两路信号继续（**绝不**因读 cookie 失败而判"未登录"） |
| 用户取消等待 | 保留已抓素材继续生成，预览区标注未验证 |
| 登录后素材仍贫瘠 | 照常生成，走既有 `probeMode=http-thin/none` 的"需人工核对"提示 |

## 9. 测试策略

| 层 | 内容 |
|---|---|
| 纯函数单测 | `app-session-key`（键取值/优先级/兜底）、`app-login-wall`（各信号与置信度）、`app-http-probe` 的 cookie 注入与**跨站不带 cookie**、重定向跟随上限 |

| IPC 集成 | `app-ipc-integration`：`app:login-done/-cancel` 两条通道 + `app:login` 键切换 + 自检 drifted；`app-generate-ipc`：登录墙 → 自动开窗 → cookie 变化 → 重抓素材进 agent seed、`request_login` 路径、桌面拒绝 |

## 10. 兼容与迁移

- **旧 Spec**：无 `auth` 字段照常工作（不改校验、不加必填）。
- **旧登录态**：既有 `persist:automation-<chatSessionId>` 分区文件保留在盘上但不被新路径读取；
  首次使用需重新登录一次。文档明确写出（§11 限制）。
- **旧测试**：`app-ipc-integration` 等既有断言若依赖"传 chat sessionId 即分区"需同步更新——
  这是**预期内的契约变更**，不是回归。

## 11. 已知限制（如实说）

1. 登录成功判定依赖 cookie 变化或页面信号；极少数**仅靠 localStorage/sessionStorage 记登录态**的站点，
   登录后 cookie 可能不变 → 仍可由 `logged_in`/密码框消失/用户点「我已完成登录」判定成功。
2. 验证码、短信验证仍在登录窗口内由用户人工完成（本设计不做打码）。
3. 同一站点两个应用卡片共享登录态（§3.1 的预期行为）。
4. 桌面应用不支持（无浏览器登录概念）。
5. 真机端到端（真实登录站点 + 真实模型）在实施阶段需用户配合验收，**未验收前不声称已通过**。

## 12. 实施顺序（给实施计划）

1. 纯函数层：`app-session-key` + 单测 → 2. 执行器 cookie 只读能力 + 单测 →
3. 抓取层 cookie 注入与重定向隔离 + 单测 → 4. `app-login-wall` + 单测 →
5. `app-login` 编排 + 单测 → 6. `app-ipc` 接线（键统一 / 登录编排 / request_login / 两条通道 / 自检）→
7. `app-agent`（工具文档 + pauseMs 预算）→ 8. 渲染层（preload/types/i18n/两个组件）→
9. 守卫与集成测试 → 10. 文档更新（使用说明）+ 真机验收。
