### 四个**否定结果**（本轮最有价值的部分：证明"哪些改动不该做"）

对着量尺试了四类改动，三类被数据否决、一类被证明是量尺自身的偏差。全部留档，避免后人重复走：

| # | 假设 | 实验 | 结果 | 处置 |
|---|---|---|---|---|
| 1 | 候选池太小（正确文档没进 20 篇） | `candTopN` 20 → 80 → 320（覆盖全库） | recall **恒定 0.833** | 否决；`candTopN` 保留为参数，缺省沿用原公式 |
| 2 | 每篇文档只出 best 块（文档内路由丢失） | `perDoc` 1 → 2 → 3 → 5 | 0.833 / 0.833 / 0.817 / 0.817，**只让回执从 1207B 涨到 1518B** | 否决；缺省改回 **1**（无收益的默认值就是净负债） |
| 3 | 字段加权（BM25F）能改善排序 | `fw` (1,1,1) → (20,8,4) | recall **恒定** | 否决——但**先确认了实现正确**（见下），缺省不启用 |
| 4 | 剩余 miss 是引擎缺陷 | 期望块长度画像 | 19/19 miss **全是 noisy 用例**，首词清一色跨词边界假 bigram（`env中`/`团自`/`与法`/`spec确`/`release沉`/`48022010照`） | **是量尺的样本偏差**，已修（`minDf=2`） |

**第 3 项的"否决"必须配一句限定**：字段加权**确实生效**，只是整体分布上不足以改变指标。
直接构造"词落在标签里"的查询时它是有效的（分数 0.565→0.583、排名 3→2）；
40 例样本上 BM25F 还是 31/40 → 33/40，但**样本翻倍到 80 例后四组权重配置一模一样（0.738 恒定）**
—— 那 2 例改善是排名抖动，不是系统性改善。故：实现保留（可显式开 `bm25f`）、**缺省不启用**。

### 量尺的两处修正（比引擎改动更值得记）

1. **金标词加 `minDf=2`**：`df=1` 的 gram 在中文语料里几乎必然是"两个词被切开后拼在一起"的噪音片段
   （真实的词/编号会在语料里重复出现）。原判据"越稀有越好"恰好优先挑中它们，
   于是量尺把"检索对跨界噪音不敏感"误报成"引擎召回不足"。修正后 60 例样本 recall 0.833 → **0.900**。
2. **补 `field` 用例类（40 例）**：原用例集的词几乎全部出自正文，**测不到任何字段加权改动**
   ——一个测不到被改特性的量尺会给出"无收益"的错误结论。故补"从 tag/heading 取词、正解=该块"这一类。

## 1. 来源材料的技术主张（提炼，附原数据）

1. **智能体检索 = agent 循环内部的检索**，需要三件套：强模型 + **harness**（怎么把检索暴露给模型）+ 能扛规模的检索引擎。
2. **变的不是 BM25，是用户**。模型有通识、打字快、**会用搜索算子**（`site:`、精确短语），且能把内化知识用于检索；BM25 便宜、工具链成熟、**对模型可解释**（字面匹配让模型能理解"为什么返回这条"并据此改写查询）。
3. **瓶颈是检索与导航，不是推理**：把证据直接塞进上下文，连 GPT-4 都能答对（BrowseComp-Plus 830 题 / 10 万文档）；改成走带检索工具的 harness 就掉下来。
4. **经典单查询评估（NDCG 那一套）基本失效**，改为看端到端任务完成度。
5. **"你说的到底是哪个 BM25"**：不同实现/参数差异很大，BrowseComp-Plus 官方 BM25 基线因参数不适配长文档而"烂得不行"。
6. **动态工作区扩展（Jimmy Lin 组）**：检索结果组织成文件系统 + 渐进式披露 + 代码模式 + 沙箱 + bash，是当前最有效的一条路；并把 grep/rg 与 BM25 视为一套组合范式。

**外部量化证据（仅在其设定下成立，勿直接外推）**：

| 来源 | 关键数字 |
|---|---|
| Revisiting Text Ranking in Deep Research（SIGIR'26） | 长文档（均值 >5,000 词）场景，默认 k1=0.9/b=0.4 明显次优；文档级调至 **k1=10, b=1** 大幅提升；**passage 级**分块后参数敏感性大幅下降、上下文受限的 agent 准确率与完成率上升；agent 查询是"网页搜索式"（关键词/引号精确匹配），利于词法检索；重排深度到 50 时小模型也能追平大模型 |
| Pi-Serini（Waterloo） | BM25 调参相比默认：答案准确率 **+18.0%**、surfaced recall **+11.1%**；检索深度加大：surfaced recall **+25.3%**（深度 1000 时 94.7%）；**瓶颈转移到"看到但没读"**；82–90% token 命中前缀缓存，成本约 1/4 |
| DR-DCI（Toronto/Waterloo） | `pull(query, topK)` 物化工作区：71.2%（Raw-DCI 62.9%，+8.3 点）且调用/耗时/成本同时下降；**屏蔽跨文档 grep 后 82→40**（最大单项）；rank-aware 目录结构反而降低最终准确率（root-flat 最好，rank 走工具反馈而非路径） |
| Is Grep All You Need?（PwC） | LongMemEval 上 **grep 普遍优于向量检索**（inline 投递、跨 harness）；改成"结果落文件、再二次读"时部分配置反转；**harness 自带归纳偏置**（换 harness 不可即插即用） |
| Codex 仓库内实现（`scratch/agents-ref/.../fielded_bm25.rs`） | 技能选择用 **fielded BM25**：K1=1.2、B=0.75、字段权重 **[8,4,1]**（name / short-desc / description），零依赖、可解释 |

## 2. 本应用现状（读代码得到的事实，非推测）

| # | 事实 | 位置 |
|---|---|---|
| 1 | 检索**已是纯词法**：CJK 字符 bigram + 英文/数字词元，`(1+√tf)×IDF` 加权，块级向量 **L2 归一化**，倒排 postings 存块权重 | `shared/knowledge-core.mjs`、`kernel/knowledge.mjs` |
| 2 | 融合分 = `0.60×cos + 0.25×min(kw/8,1) + 0.15×struct`（图扩展 ×0.9）；**kw 只对显式 `keywords` 参数计算**（query 词不产生 kw） | `shared/knowledge-core.mjs` |
| 3 | **字段信号被三重计数**：`tagBoost=3` + `keywordScore` 标签命中 +3 再 /8 + `structBoostOf` 标签 0.67 | `shared/knowledge-core.mjs` |
| 4 | **预筛与终评不同源**：候选文档由 **doc 级 postings 点积**（未做长度归一化，多块长文档天然占优）取 top-20，终评再对候选文档**逐块现算 cosine** | `kernel/knowledge.mjs`（候选累加 → 终评） |
| 5 | **IDF 与 df 口径不一致**：idf 按**块**统计，df 按**文档**统计且只用于剪枝 | `kernel/knowledge.mjs` |
| 6 | **无位置信息** → 无法做短语/邻近度约束；`keywords` 走 `includes` 子串匹配，拆分号型编号会被切成多段 | `shared/knowledge-core.mjs` |
| 7 | 检索单位是**块级（passage-like）**，块种类 heading/para/list/table/entry/code 分明 —— 这一点**天生踩中了论文的最佳实践** | `shared/knowledge-core.mjs` `splitBlocks` |
| 8 | 超长文档尾部有块数上限截断（有告警，不静默） | `kernel/knowledge.mjs` `MAX_BLOCKS_PER_DOC` |
| 9 | 工具层已有**查询语法层**（`tag:`/`path:`/`file:`/`section:`/`content:`/`block:` + 布尔 + 否定） | `shared/knowledge-query.mjs`（`parseSearchQuery`；**注意在 `shared/` 而非 `kernel/`**） |
| 10 | 回执**原本只有一个分数**：无命中词、无命中字段、无更多候选获取途径（`total` 有但不含续看手段）→ P2 已修 | `kernel/knowledge-search.mjs` |
| 11 | **Read/Grep 边界原本不含知识空间**：`allowDirs=[cwd,...addDirs]` 只额外放行记忆根 → 任务模式下非 experience 空间既不能 Read 也不能 Grep，而回执却叫模型"用 Read 读全文" → **P3 已修** | `kernel/tools.mjs`、`kernel/cli.mjs` |
| 12 | 真实规模（本机）：238 篇 / 6918 块 / 倒排 11MB；含「政策」空间 147 篇；个人经验库 `workflow.md` 近 1MB | `.yfw/knowledge/.index/` |
| 13 | 关联层已成熟（一跳 related、tag/content/duplicate 三类锚点、按文档 idf 校准） | `kernel/knowledge.mjs` |
| 14 | legacy `MemorySearch` 仍每次全量读文件 + 现算向量（O(N)），与 KnowledgeSearch 能力重叠 | `kernel/memory-search.mjs` |

**关键判断**：本应用**不是**"用向量检索、该改用 BM25"的场景；它是"**已经用词法、但把 BM25 的两件核心工艺（tf 饱和 + 部分长度归一化）省掉了，用三套手调权重硬凑**"。所以来源材料对我们不是"换方向"，而是"补课 + 改交互"。（**后被 P0 基线证实**：para 14/24 vs heading 21/22 的落差就是长度归一化缺陷的指纹。）

## 3. 逐条对照评估

| 来源主张 | 本应用现状 | 判断 | 事后验证 |
|---|---|---|---|
| tf 饱和 + 部分长度归一化 | `(1+√tf)×idf` + **完全** L2 归一化（等价 b=1）；预筛路**完全无归一化** | ✅ **有提升** | **已证实**：+9.1 点 recall、+14.3 点 top1 |
| 字段建模（BM25F，Codex 的 [8,4,1]） | 标签/主题/摘要/正文四处信号，被 3 套权重重复加权 | ✅ 有提升（当时判断） | **未证实**：80 例样本上零收益 → 未启用（见"四个否定结果"） |
| 可解释性 → 让模型改写查询 | 回执只有一个数字 | ✅ **有提升** | 已落地（命中词 + 分页）；legacy 下逐字不变 |
| 精确匹配/短语（实体、编号） | 有 `keywords` 子串路，无位置信息；编号被切碎 | ✅ 有提升（业务相关） | 未做（归属 P1-full 的短语算子） |
| 检索深度要够 | topK 硬上限 10；`total` 无续看 | ✅ 改造后适用 | **改造后适用**：实测扩大候选池**无效**（20→320 recall 恒定），真正需要的是**回执分页**而非一次多给 |
| 动态工作区扩展 | 知识空间文件在磁盘上但**模型够不着** | ✅ **有提升（体感最大）** | 已落地（只读边界 + 提示词能力可见性）；DR-DCI 消融 82→40 是依据 |
| passage/等长分块 | 已是块级（✅），但块长方差大 + 顶部截断 | ✅ 顺带修缺陷 | **未做**（P3b） |
| "经典评估已死，改看端到端" | 只有不变量测试，无排序质量基线 | ✅ **必须补（前置）** | **已补**，且它立刻否决了三项改动 —— 这是本轮最划算的投入 |
| 大规模 QPS / 亿级文档吞吐 | 238 篇、11MB 索引 | ❌ **不适用** | 量级差 5 个数量级 |
| 引入嵌入/混合检索 | **零嵌入基建**（全仓库无 embedding 调用），离线/私有化是硬约束 | ❌ **不适用（且不建议）** | Grep 论文在"记忆+实体精确"任务上 grep 普遍优于向量 |
| 照搬 k1=25、b=1 | 检索单位已是块级/passage | ❌ **不适用** | **已实证**：top1 从 0.767 掉到 0.617 |
| Q2Q 查询改写 | 纯词法打分 | ❌ **不适用** | 论文明确指出 Q2Q 对 BM25 **有害** |
| LLM/推理式重排作主路径 | 本地小模型 + 成本敏感 | ❌ **不作主路径** | 未做；可留作可选"深检"模式 |

## 5. 升级方案

### 5.0 为什么 P0 必须先行 —— ✅ 已完成，且**立刻回本**

来源材料结论第二条就是"**你说的到底是哪个 BM25**"，SIGIR'26 也证明**同一公式不同参数能让准确率差十几个点**。
本应用当时**只有不变量测试，没有一条"排序质量"断言**。在这种状态下改公式，无法区分"变好"与"变样本"。

**P0 的投入在两个层面回本**：
1. 它让 P1 的收益**可量化**（+9.1 点，而非"感觉快了"）；
2. 它**否决了三项"看起来该有效"的改动**（候选池扩大、每篇多块、字段加权），
   并暴露了**自己的样本偏差**（df=1 的跨界噪音 gram）—— 没有它，这三项会被当成优化上线。

### 基线暴露的 6 个事实（**此前全部未知**，均改变了对方案的判断）

1. **瓶颈在"块级定位"，不在"文档召回"**：块级 0.720 vs 文档级 0.866 —— 14.6 个点是"找对了文档但正确块没进 top5"。这**精确落在 P1 的射程内**（P1 改的正是块级排序）。
2. **"短块好、长块差"是长度归一化缺陷的直接指纹**：heading 94% / code 92% vs table 52% / para 58% / entry 58%。现实现是**完全 L2 归一化**（等价 `b=1` 的硬归一化）+ 预筛路**完全无归一化**（文档级累加，多块文档占优）—— 两头都不是 BM25 的"部分归一化"，长块被系统性压制。**这不是推测，是分布证据。**
3. **真实话术 0.93 反而高于自动集 0.72**：修正了原方案的先验（原以为"用户话术更难"）。真实查询短、含点名实体（"新能源汽车 车船税 优惠"），词法检索天然擅长；难的是"在长文档里精确定位到块"。**故 P2（可解释回执 + 分页）的价值被上调**：真实场景下模型多半已找对文档，缺的是"看到是哪些词命中、如何翻页深入"。
4. **检索热路径就慢**：P50 = 430ms / P95 = 923ms —— 原方案写的"~1s（其中主要是内核进程冷启动）"**是错的**。这是稳定热路径成本，来源是终评阶段对候选文档**逐块现算向量**（20 篇 × 平均 29 块，每块重新分词+tf+归一化）。P1 让每块分数只依赖块级 postings，**顺带把这个成本砍掉**（`miss` 率 0.0% 降级说明慢不是降级路造成的）。
5. **噪声词代价 25 个点**（precise 0.82 → noisy 0.57）：排序对无关高频词敏感 —— 这正是"字段建模"（标签/标题/摘要加权）要解决的：正确块的稀有词若命中在**高权字段**上，就不会被噪声词稀释。
6. **两个最该好的空间反而最差**：`experience`（个人经验库，用户最在意）块级仅 **48%**，`政策` 65%；而 session-memory 88%。原因同上（经验条目是长 entry 块），但影响面更实际。

> 反向验证：量尺自检里"小库金标必须全中"（recall=1）通过 —— 说明上述 miss 是**引擎的真实表现**，不是量尺构造偏差。负例假阳性 0/12 也说明"降级路乱捞"这个老问题目前不存在（P1 后必须保持 0）。

### 5.1 P1：打分内核 → 块级 BM25F（2–3 天）

**改什么**
- 索引侧：postings 由"域内 L2 归一化权重的桶"改为可重算 BM25 的形态 —— `gram → [{blockRef, tf}]` + 每块 `dl`（按字段）+ 全局 `avgdl`（按字段）。块内字段 = 标签 / 标题(heading·title) / 摘要(entry summary·段落) / 正文(full)。
- 打分侧：
  `score(block,q) = Σ_t IDF(t) · (f̃(t,b)·(k1+1)) / (f̃(t,b) + k1·(1−b+b·dl_b/avgdl))`
  其中 `f̃(t,b) = Σ_fields w_f · tf_f / (1 − b_f + b_f · dl_f/avgdl_f)`（BM25F 形态）。
- 候选生成与终评**同一函数**：直接由块级 postings 出 top-k 块，删掉"先 doc 点积选 20 篇、再逐块现算向量"的两段式（同时消掉事实 4 的两个偏差）。
- 参数：`k1`、`b`、字段权重 `w_f` 全部走配置（默认取 `k1=1.2, b=0.75`、字段权重参考 Codex 的 [8,4,1] 思路按 4 字段起手），**最终值以 P0 量尺网格搜选定**。
- 融合层收敛：`struct` 的标签/标题命中职责并入 `w_f`；`keywordScore` 保留但仅承担"字面精确命中"（与 BM25 的 tf 项互补，权重重新按量尺标定）。**不引入第二套长度归一化**。
- 剪枝口径统一：idf 与 df 同为块级（或同为文档级，二选一后全局一致）。

**为什么值得**
- 一个打分函数取代两个不同源分数 + 三套字段权重（事实 2/3/4/5 一并解决）；
- 每块分数只依赖该块 postings → 复杂度从"候选文档 × 全部块现算向量"变成"命中量"，顺带提速（现在每次查询对 ~20 篇 × 平均 29 块做全量重切词+向量化）；
- 分数可分解：为 P2 的"命中词/命中字段"直接提供数据。

**验收**
- P0 量尺：`Recall@5` 与 `MRR` **不下降**（目标提升幅度由基线 diff 定，不预填数字）；无命中集不出现"凭空捞回"（`degraded` 行为不变）。
- 性能：查询 P95 不快于现状即视为不合格（应更快）。
- 回归：既有 `kernel-tests/knowledge-*`、`shared/knowledge-core.test.mjs` 全绿；查询语法层（`tag:`/`path:`/布尔/`related`）行为逐字节不变。
- **回退**：灰度开关 `PONOS_KNOWLEDGE_SCORER=bm25f|legacy`（缺省 **legacy**，与既有 `PONOS_KNOWLEDGE_INJECT_MODE` 同款纪律：老用户行为不突变）；索引格式变更需能由 `--knowledge reindex --force` 单向重建，不做双格式长期共存。

**风险**
- 索引格式变更 → 首次重建耗时（现基线：221 文档/4636 块 ≈ 8s，可控）；
- 分字段 `dl` 会放大索引体积（当前 `inverted.jsonl` 11MB），需在 P1 内测体积增幅，设 <+50% 的闸门；超则退回"仅标签/标题/摘要分字段、正文单字段"。

### 5.2 P2：检索回执可解释化 + 分页（1–2 天，体感最直接）

**改什么**
- 回执每条增加：**命中词**（BM25 天然给出）、**命中字段**（标签/标题/摘要/正文）、**同文档命中数**；
- 增加 **offset/分页**：`topK` 仍 ≤10，深度靠 `offset` 续看（回执给 `nextOffset`），对应 Pi-Serini 的 `read_search_results`；
- 增加**命中地图**一行：如 `命中分布：政策 12 篇/38 处 · 经验 3 条`，让模型先决定"换空间还是换词"；
- 修 **文案与边界不一致**（事实 11）：在 P3 落地前，回执不再无条件说"需全文用 Read"，改为按空间是否可读给出不同引导（可读 → Read 行号；不可读 → `mode='full'` 或 `related` 展开）。
- 注入层（`knowledge-inject.mjs`）**不动**：它是每次请求的固定成本，`INJECT_RELATED_TOPN=3` 那套预算纪律保持。

**验收**
- 单条回执字节数增幅 ≤ +10%（含分页说明）；
- 在 5 个真实任务（政策条款查找、历史经验复用、编号逐字核对等）上，"找到正确块所需工具调用数"下降或持平，且**不出现**"为了拿命中词多调一次工具"的新开销。

### 5.3 P3：工作区扩展（DR-DCI 的最小可用版，1–3 天）

两条路，建议先 A 后 B（A 成本低、B 面向重任务）：

**A. 打通只读边界（最小改动，直击最大单项）**
- 把"本会话知识范围内的空间根"加入 **只读**白名单（`readAllowDirs` 与 Grep 的 `resolveScanScope` 同源），使模型能在知识空间内做跨文档 `Grep`/`Read`；
- 保持写入侧完全不变（Write/Edit 仍不可越界），并在系统提示的知识区块里说明"这些目录只读可用"；
- 依据：DR-DCI 的 inter-document DCI 消融 82→40；Grep 论文 grep ≥ vector。
**B. `KnowledgeWorkspace`（pull 语义，可选）**
- 把 top-N 候选**文档**物化到会话已有的 `toolResultsDir`（`engine.mjs` 已在 addDirs 中），返回 ranked preview + 工作区统计，模型在受限工作区内用 Grep/Read 核验；
- **必须遵守 DR-DCI 的接口教训**：**root-flat 工作区、rank 走工具反馈而非目录/文件名**（rank-aware 目录结构实测降低最终准确率）；
- 物化用硬链接或只读复制，退出时显式清理；**绝不改动用户文件**。

**验收**
- 5 个跨文档核验任务（例：同一金额在「政策」多处出现是否一致、某编号在正文与附件是否对齐）在 A/B 下成功率高、调用数低；
- 边界回归：越界写操作仍被拒（`kernel-tests` 的边界测试全绿）；
- 无新增"用户文件被改动"路径（`git status` 级证据）。

### 5.4 P3b：超长段落定长分块（1 天）

- 对超长 `para`/`table` 块按定长（起手 ~400 字 / 1200 字符）+ 少量重叠切窗，块序号稳定、可回溯行号；
- 收益：①块长方差收敛 → BM25 参数不敏感（论文结论）②4128 块文件的尾部从"被截断丢弃"变为"分页可覆盖"③`MAX_BLOCKS_PER_DOC` 不再是可达上限；
- **验收**：为该文件构造回归用例（尾部内容可被检索命中）；索引体积增幅 <+30%；展示层片段不出现"从半个词开头"（切窗按标点/换行优先）。

### 5.5 里程碑与依赖

```
P0 量尺 ──→ P1 打分内核 ──→ P2 回执/分页 ──→ P3 工作区扩展
                    └────→ P3b 分块（可与 P2 并行）
```

- P1 依赖 P0 的基线；P2 的"命中词/字段"数据来自 P1 的分数分解，但**不强依赖**（可在 legacy 打分下先给"命中词汇总"）。
- P3 与 P1/P2 相互独立，可并行；但 P3 的文案与引导需与 P2 一同收口，否则又出现"回执说的和边界做的不一致"。

## 6. 风险与"不做什么"

**风险**
1. 索引格式变更（P1）是本方案唯一有破坏性的改动 → 用灰度开关 + `reindex --force` 单向重建 + P0 量尺三重护栏。
2. P1 的收益**可能只是中低幅度**（本应用已是词法 + 块级 + IDF，BM25 的增量主要在"长度归一化更合适"与"字段建模更干净"）→ 若 P0 量尺显示 `Recall@5/MRR` 无实质改善，**P1 应当只保留"候选与终评同源 + 字段收敛"两项结构性修正，参数化那部分回退**，不要为了"上了 BM25"而上。
3. P3 涉及边界放宽 → 只放宽**读**，且限定在会话已授权的空间集合内；写路径一行不动。
4. P2 的回执膨胀 → 有硬上限（bytes 闸门 + 与注入层相同的"预算先行"纪律）。

**明确不做**
- 不引入嵌入/向量检索或以向量为主路径（离线私有化 + Grep 论文结论 + 语料量级）。
- 不照搬 k1=25 / b=1 / 深度 1000 / Q2Q；参数一律在本应用自有量尺上定。
- 不做亿级文档 QPS 与分布式索引优化。
- 不把 LLM reranker 作为默认主路径；若要，做成显式"深检"模式并默认关闭。
- 不动关联层（`related`）的 idf 口径与阈值（已在 2026-09-17 二次校准，改动会连带影响注入层质量）。

## §7 未做项与遗留观察（2026-09-18）

### 7.1 P3b（超长段落定长分块）未做 —— 诚实记录

**未做的理由**：P1/P2/P3 三项已覆盖"确有提升"的全部结论，而 P3b 触碰**索引与分块**——
按本方案自己的纪律（§0 "实施顺序不可颠倒"、§6 风险 2），在量尺尚未显示"分块是瓶颈"之前
动它属于"为了完整性而扩大改动面"。且当前量尺已能测出它该带来的收益
（`invertedCoverage = 89.3%`、构造期"660 块无候选"就是分块/剪枝可观测的口子）。

**什么时候该做**：若后续出现"文件里明明有、检索就是找不到"的实例（尤其长文档尾部），
或 `MAX_BLOCKS_PER_DOC` 截断再次被触发（已有 4128 块文件撞过 2000 上限）——
那时先用量尺跑一次"命中位置 vs 块序"的分布，确认瓶颈在分块再动手。

### 7.2 entry 块未改善（7/12 → 7/12）

BM25 修好了 para/table/list（长块），但 **entry 块纹丝不动**。entry 是结构化条目块
（`[会话|标签] 摘要 -- 全文`），三件事混在一个块里。下一步该做的不是继续调 BM25 参数，
而是**字段建模（BM25F）**：entry 的 `标签`/`摘要`/`正文` 分开算 tf 与字段权重
（这正是方案 §5.1 里"字段建模收敛三重计数"的部分，本轮未做）。
仓库内可对照实现：`scratch/agents-ref/.../fielded_bm25.rs`（字段权重 [8,4,1]）。

### 7.3 待观察的副作用（需真实使用一段时间）

1. **平均回执字节 905 → 1265（+40%）**：长块现在能排上来，单条更长。在 `maxBytes=2048`
   的真实预算下条数会略减。P2 的分页已给了应对手段（翻页而非加 topK），但要观察实际体感。
2. **Grep 默认遍历面变大**（P3）：无 `path` 的 Grep 现在会遍历已授权空间（本机约 +240 文件）。
   已授权范围内容忍；若某会话关联了超大库，需复查预算。
3. **`hits` 字段只在 bm25 模式出现**：legacy 下为 null（零回归的代价）。若长期停留在
   legacy，P2 的命中词价值就只兑现一半 —— 这构成"何时把缺省翻到 bm25"的决策输入。
4. **`total` 语义**：它是"截断前候选数"（非全库命中数），P2 的分页提示基于它 ——
   若后续改候选池大小，回执里的"共 N 条"含义会随之变化，需一并复核。

### 7.4 一个必须记住的工程教训：并行子代理写同一文件会互相覆盖

本轮 P3 由后台子代理实施、P1/P2 由主代理实施。P3 收尾时用**它自己的旧快照**对
`kernel/knowledge-search.mjs` 的 `searchKnowledge` 做 Edit，把主代理在该函数内的 P2 改动
（`offset`/`hits`/分页尾行）**整段抹掉**——因为 Edit 的 `old_string` 来自旧快照，替换范围覆盖了新内容。
发现方式：测试红了 + grep 标记缺失（不是靠肉眼）。

**预防**：并行派活时，把"同一文件的不同函数"也视为冲突区；要么按文件分派，要么在子代理
交付后**逐文件 grep 关键标记**验证自己的改动还在（本轮就是这么发现的）。
