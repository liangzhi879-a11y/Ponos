| ⑤ 同工具重复提醒 `REPEAT_REMIND_AT` | [3,5] | ✅ |
| ⑥ 无进展停滞 `LOOP_STALL_MS` | 600,000 | ✅ |
| 溢出重试 / 空闲看门狗 / 首字节窗口 | 12 / 300,000 / 300,000 | ✅ |
| 一键全关 `PONOS_LOOP_GUARD=0` | 所有常量定义行均引用 | ✅ 一等特性 |

**健壮性亮点（代码可证）**：`compact.mjs landSummary` 有**硬契约校验** —— 压缩遮蔽区间 seq 反查失败时 `throw`（不静默提交空/残缺 coveredSeqs），杜绝「看似成功后实则丢消息」。

## 3. 三大能力维度的客观排序

### 3.1 安全（唯一有内核级隔离的只有 codex）

| 层 | codex | claude-code | dsh | pi | ponos |
|---|---|---|---|---|---|
| 内核级隔离 | ✅ 三层 + **三重拦截 + 测试** | 包装 sandbox-runtime | 4 后端 seam | ❌ | ❌ |
| 二级审查 | ✅ Guardian 真接线（3 工具/可 0/fail-closed） | AI 分类器 | — | — | ❌ |
| 应用层审批 | `UnlessTrusted/OnRequest/Granular/Never` + Starlark | 5 档运行时 | approval service | ❌（仅 trust 加载） | **4 档 + 灾难硬黑名单** |
| 默认姿态 | 沙箱内 | 未验证 | 未验证 | 无 | **loose：write/net/agent 放行** |

**ponos 的应用层审批在「可审计性」上最清晰**（token 级黑名单 + wrapper 穿透 + 幂等谓词），但**默认档覆盖面窄**，且**无内核隔离**——一旦审批意图被绕过，没有第二道防线。

| 机制 | claude-code | codex | pi | **ponos** |
|---|---|---|---|---|

| 失真检测 | — | — | — | ⚠️ 有实现（**无闭环**） |

**结论**：ponos 的上下文治理**实现密度确实最高**（免模型收缩 + 切点纪律 + 保真审计 + CJK 计价 + 估算缓存 + 失真检测，六项都有代码），但其中**两项只有观测没有闭环**（保真审计后置、失真检测不注入）。claude-code 的「7 层」实为 4 层且首层默认空操作，**不应再被当作标杆**。

### 3.3 「能放心跑长任务」的真实依据

| 依据 | 代码证据 | 谁有 |

| 跨轮预算硬停 | `loop.mjs` + `cli.mjs:1149` 接线 | **仅 ponos** |

## 4. 五条技术路径（基于实现而非宣称）

| | 实际选择（代码可证） | 代价（代码可证） |
|---|---|---|

| **codex** | 安全与一致性优先：三重沙箱拦截 + `StepContext` 同源 + Guardian；`core` 之外 155K 行测试 | 1.7M 行；`chat_composer.rs` 13,083 行；**142 条 feature 注册表 + 大量 `default_enabled:false`**，实际可达路径需逐条验证（如 apply_patch 增量路径默认关） |
| **dsh** | 一切皆插件（219 包）；断言机制**存在但可插拔** | 6 项核心声称**无代码级证据**（重试顺序/loop 插件化/并行池/压缩阈值/token 算法/覆盖率门）；Host/Client 必须拆两个 aggregate |

## 5. 改进建议（基于验证后的事实重新排序）

### P0 — 把「有实现」变成「有闭环」

1. **失真检测接闭环**（当前最大落差）：`fidelity.mjs`/`health.mjs` 已有完整检测（实体/约束/矛盾/目标漂移），但产物只发 GUI。最小改动：让内核在失真为 red 时把 `anchorText` 作为**注入项**加入下一轮（而非等 GUI 回传）。代码位置明确（`health.mjs:147/163` 生成处 → `engine.mjs:961` 之前的消息装配处），**不需要新模块**。
2. **保真审计前置**：`compact.mjs:653` 的 `auditSummaryFidelity` 目前**在 landSummary 之后**。把它移到写入决策之前（确定性审计零成本），审计不通过则换切点重压 —— 把「后置观测」变成「前置门禁」。
3. **审批不可绕过化**（对齐 codex 的验证过的做法）：codex 的做法是 `orchestrator.rs:387-389` **升权重试也硬拒**。ponos 目前 `decideToolPermission` 是纯谓词，没有「同一动作重试」的拦截层。低成本补法：对 `hard:true` 的灾难判定，在同一 turn 内记录已问过的命令指纹，**重试不重复询问、直接拒**。
4. **默认档提高一档**：`DEFAULT_APPROVAL_MODE = 'loose'` 使 `write/net/agent` 默认放行。若产品定位是「长任务无人值守」，建议默认 `auto`（写文件询问）或至少在 GUI 显式提示当前档位。

### P1 — 补齐被验证为真实差距的能力

5. **MCP 客户端**：cc/codex/dsh 三家均有且**都有真实实现**（codex `rmcp` 在 crate 依赖里可查）。ponos 的 `unknown` 工具类已预留（默认档放行），接入成本主要在协议层（可复用 `protocol.mjs` 的 NDJSON 经验）。
6. **拆 `engine.mjs`（2,885 行）与消除双份守卫**：主循环（约 1,065–1,712 行）与 lane（约 2,092–2,350 行）各有一份守卫实现，这是**同一逻辑两处维护**，是 v2 核查中最实在的技术债。
7. **补最小基准门禁**：ponos 已能用「合成 2.5MB / 1,482 条历史」夹具定位热点（`context.mjs` 相关），把它固化为 `kernel-tests` 里的耗时断言即可（无需引入基准框架）。

### 建议不做

- ❌ **不追 claude-code 的多层压缩**：其 7 层中 3 层模块根本不存在 —— 分层数量不是能力。
- ❌ **不引入 dsh 的「100% 覆盖率门」作为目标**：该门在 dsh 自身只有 6 项中的 0 项得到验证；ponos 当前测试量已是五家中最健康的比例之一。
- ❌ **不为「跨轮/去重/自愈」再加机制**：这三项已是五家唯一，应把精力放在 P0 的闭环上。

## 6. 总结（严格限定在代码能证明的范围）

| 结论 | 依据 |
|---|---|
| **codex 的安全架构最扎实**，且是唯一「宣称与实现一致」的（三重拦截有测试、Guardian 有 6 处真实调用点、StepContext 同源可读代码验证） | codex 2.2 全部 ✅ |
| **claude-code 的实测能力显著低于其文档**：3 个压缩层模块缺失、缓存检测恒 false、8 个测试文件 | `bun-bundle.ts` 白名单 + 模块存在性 + `tests/` 计数 |
| **dsh 的 6 项核心声称无法证实**，评估时应视作未知 | dsh 2.3 ⏸ |
| **pi 的「No X」宣称需逐条打折**（trust 弹窗存在、串行降级内置不触发、harness 是桩） | pi 2.4 |
| **ponos 的实现密度最高、但闭环率最低**：六项上下文治理全有代码，其中两项只有观测 | ponos 2.5 |
| **ponos 的跨轮 loop + 无进展去重 + 无感自愈是五家唯一**，但墙钟与迭代上限默认关闭 | 守卫默认值表 |

**一句话**：v1 的「ponos 赢在四家都没做的事」这个方向判断成立，但强度需下调——**它的优势是「把抗失控做成了控制流上的真代码」（这一点经代码验证为五家唯一），劣势是「检测能力没有接上闭环」（这一点也经代码验证），而不是笼统的「无 MCP / 无沙箱」**。
