① 前端 → bridge

  • 形态：跨进程网络连接（TCP 环回）
  • 协议：WebSocket ws://localhost:51517 + HTTP REST 同端口
  • 代码：src/lib/config.ts:14 · server/bridge.mjs:2314

② bridge → 内核

  • 形态：进程内管道 stdio: ['pipe','pipe','pipe']
  • 协议：NDJSON 双向流（一行一个 JSON）
  • 代码：server/bridge.mjs:1145 · kernel/cli.mjs

进程归属

  • 内核是 bridge 的子进程，不是 Electron 的子进程
  • GUI · 桌面宠物 · 浏览器执行器 · Electron 主进程
    四者都只是 bridge 的 WS 客户端

三点澄清（非「壳到壳」）

  • 前端那侧没有壳：浏览器沙箱只能走网络协议
  • 内核那侧不是终端会话：无 PTY / TTY / 回显
  • 仅「启动动作」借 cmd.exe（shell:true，server/bridge.mjs:1158）拉起后即退，与协议无关

为什么设计成这样

内核可替换：bridge 是唯一知晓内核协议的一侧，GUI 零改动即可换内核 安全收敛：Origin 白名单（外部 403）· 审批弹窗 · 浏览器请求由 bridge 直连执行器不转发 GUI 生命周期托管：空闲 10min 回收 · --resume 重启 · 6s 超时 taskkill，前端只持 sessionId 多端复用：宠物 / 执行器 / 独立小窗共享同一中枢 出网唯一出口：模型调用发生在内核侧，前端永不直连 LLM

三层协议契约（bridge 是唯一中枢）

通道语义
GUI ⇄ bridge WSsend / cancel / answer / approval-response / approval-mode ⇄ event / approval / question / milestones
GUI → bridge HTTP文件、Office、transcript、config、skills、workflows、logs、diag
bridge ⇄ 内核 NDJSON替换内核时必须逐条保持的契约边界

审批四档（--approval-mode）

档位skip-perms仍会问
manual否普通 Bash 也问
auto否写文件 / 联网 / 子 Agent
loose 默认是高危 Bash + 灾难命令
bypass是仅灾难命令

硬黑名单四档都不放开：rm -rf / · mkfs* · format X: · diskpart · dd of=/dev/… · shutdown/reboot；弹窗仅「本次放行」，无「总是允许」记忆。

一轮消息的主链路

  1. GUI WS send → bridge（无会话则 spawn 内核并注入系统提示词文件）
  2. bridge 写内核 stdin user → engine Agent 循环 → 模型流式返回
  3. 工具调用经权限判定；需人工时 can_use_tool ⇄ GUI 弹窗回执
  4. 内核 stdout 事件 → bridge 提取里程碑 / 提问卡片 / 审批 → GUI 渲染
  5. result 事件闭轮；空闲 10min 回收进程，续聊走 --resume
