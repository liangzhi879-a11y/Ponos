# 审批档默认值（P0-4）影响面分析

- 日期：2026-09-16
- 目的：为「默认审批档提高一档」提供代码级依据与影响面判断，供决策（**本文不含改动**）
- 来源条目：`docs/2026-09-15-五引擎架构性能对比分析.md` §5 P0-4

## 1. 当前默认值：`loose`（四处常量 + 存量用户已固化）

| # | 位置 | 作用 |
|---|---|---|
| 1 | `kernel/approval-mode.mjs` `DEFAULT_APPROVAL_MODE` | 内核**派生兜底**（不传档位时按旧 flag 推导的最后落点） |
| 2 | `server/approval-mode.mjs` `DEFAULT_APPROVAL_MODE` | 桥侧默认；**写进新装 `config.json`**；非法值钳制目标 |
| 3 | `server/bridge.mjs` `defaultConfig.approvalMode` | 首次生成配置文件时的写入值 |
| 4 | `src/lib/approvalModeUi.ts` `DEFAULT_APPROVAL_MODE` | 渲染层默认（含一条断言测试钉住该值等于 `'loose'`） |

**存量用户实测（本机，2026-09-16）**：

```
~/.yfworking/config.json    → "approvalMode": "loose"   ← 桥侧全局持久化
~/.yfworking/settings.json  → "approvalMode": "loose"   ← 内核侧
```

### ⚠️ 结论一：只改常量**不会**影响任何存量用户

`loadConfig()` 读到的 `approvalMode` 已是 `'loose'`，`normalizeApprovalMode('loose')` 返回 `'loose'` —— 常量根本不参与计算。且桥在 spawn 内核时会**显式传 `--approval-mode <当前生效档>`**（内核侧 flag 优先级最高），所以连内核 `settings.json` 的值也会被桥的持久化值覆盖。

⇒ 要影响存量用户，**必须做一次性迁移**（改写 `config.json`）——那属改变既有用户安全姿态的**显式动作**，需单独决策（见 §4）。

## 2. 四档语义矩阵（`kernel/approval-mode.mjs` 唯一真源）

| 工具类 | manual | auto | **loose（当前默认）** | bypass |
|---|---|---|---|---|
| 只读（Read/Glob/Grep…） | allow | allow | allow | allow |
| 普通 Bash | **ask** | allow | allow | allow |
| 写文件（Edit/Write…） | **ask** | **ask** | allow | allow |
| 出网/浏览器 | **ask** | **ask** | allow | allow |
| 子 agent/技能/工作流 | **ask** | **ask** | allow | allow |
| 未识别（MCP 等） | **ask** | **ask** | allow | allow |
| 应用智控（`app_*`） | **ask** | **ask** | **ask** | allow |
| 高危 Bash（`highrisk.mjs`） | **ask** | **ask** | **ask** | allow |
| **灾难命令（硬黑名单）** | **ask(硬)** | **ask(硬)** | **ask(硬)** | **ask(硬)** |

（`ask(硬)` = 任何档位都必须用户确认，永不自动放行；加粗 = 该档位下需要用户确认。）

## 3. 调档影响面（相对当前 `loose` 的**增量**弹窗）

### 提到 `auto`（严一档）

新变为「需确认」的是：**写文件、出网/浏览器、子 agent/技能/工作流、未识别(MCP) 工具**。

体感量级：这几类正是**日常最高频操作**——每改一个文件（Edit/Write/MultiEdit）、每次联网检索、每次派发子代理，都要点一次「允许」。对 coding agent 的工作流而言，弹窗数会从"偶发"变成"每步"。

### 提到 `manual`（严两档）

在 `auto` 基础上再加**普通 Bash**（`ls`、`git status`、`npm run build`…）也要确认 —— 实际接近不可用，仅适合极端审查场景。

### 保持不变（`loose`）

**现状并非"无防护"**：应用智控工具、高危 Bash、灾难命令**三类已经会询问**，且灾难命令是任何档位都拦的硬黑名单。`loose` 的定位是"信任本地只读+常规读写与常规 Bash，但对高危/智控/毁灭性操作仍设卡"。

## 4. 三个可选方案与代价

| 方案 | 改什么 | 影响存量用户 | 代价 / 风险 |
|---|---|---|---|
| **A. 只改新装默认**（推荐） | 4 处常量 → 目标档 | ❌ 不影响（老用户保持 `loose`） | 新用户一到手弹窗就变多；需同步改 1 条测试断言 |
| **B. 改默认 + 迁移存量用户** | A + 一次性改写 `config.json` | ✅ 全部升档 | 属**改变既有用户安全姿态**：用户没做任何操作，行为却变了；若目标档是 `auto`，会让正在用的人**突然每步都被问**——须用户明确授权 |
| **C. 保持 `loose` + 强化引导** | 不改默认；在设置/引导里让用户主动选 | ❌ 不影响 | 安全性取决于用户是否主动设置；收益依赖引导的触达率 |

### 现有改档入口（用户可自救）

设置 → 权限面板（`src/components/settings/PermissionsPanel.tsx`）：四档带描述、**切换有确认对话框**，写入全局 `config.json`。即"改默认值"影响的是**没进过设置页的人**，不是"没有能力改的人"。

## 5. 建议

1. **若目标是"提高基准安全性"** → 选 **A（只改新装默认）**，且目标档建议 **`auto`**（`manual` 对日常工作流不可用）。
2. **若目标是"让所有用户都到某档"** → 必须走 **B**，且因涉及既有用户行为变更，**需要你在知情下明确授权**，我建议同时提供"回退到 `loose`"的一键入口。
3. **若目标是"让用户按自己习惯选"** → 选 **C**，与本条 P0-4 的"提高默认档"字面意图不同，需你确认是否改判条目方向。
