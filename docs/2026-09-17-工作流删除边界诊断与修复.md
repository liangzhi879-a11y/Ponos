# 工作流「删除后仍可用」诊断与修复

- 日期：2026-09-17
- 现象：面板里删除工作流后，agent 仍能获取到它；重启应用、开新对话也一样。被删对象为内置 `spec-dev`。
- 结论：**本体从未被删除**（删除请求没落盘），而「删了还能用」另有三个独立机制。已修四处缺陷。

---

## 一、先看结论：三个独立机制 + 一次未落盘的点击

| # | 机制 | 用户可见表现 | 处置 |
|---|---|---|---|
| A | 提示词【可用工作流】清单是**会话启动快照**，同会话内删除不刷新 | agent 照旧声称"能调用已删的工作流"，真调失败（工具已消失）→ 像"删了还能用" | 已修（缺陷 4） |
| B | 删除**平铺形态** `<id>.yml/.yaml` 会失败，而内核认它 | 面板看不见、删不掉，内核照旧可用 | 已修（缺陷 2） |
| C | 删除不清理 `_bindings.json` 引用；内置工作流无删除记账，重启被装回 | 重启后复活；重建同名工作流继承旧信任 | 已修（缺陷 1、3） |
| D | 那一次点击的 DELETE **从未发出**（无落盘、无日志、桥侧无痕） | 用户以为"删了"，实际一切照旧 | 未改动前端；见 §四 |

## 二、取证：本体从未被删除

| 观测点 | 实测值 | 推断 |
|---|---|---|
| `~/.yfw/workflows` 父目录 mtime | 09-12 11:43 | **删/建子项必刷新父目录 mtime** ⇒ 9/12 起该 home 无任何工作流增删 |
| `~/.yfw/workflows/spec-dev/workflow.yml` | 7139B，md5 `612d3063…` | 完好；与源、与旧 home 三份 md5 一致 |
| `~/.yfworking/workflows`（旧版 home） | mtime 09-14 15:37 | 同样无增删 |
| 桥权威列表 `GET /workflows` | root=`~/.yfw/workflows`、含 spec-dev、`valid:true` | 面板读的就是这份 |

> 注意：`copyFileSync` **保留源文件 mtime**（已实测），故**文件** mtime 不能作为"没删过"的证据；
> **目录** mtime 才可以 —— 删除子目录必然刷新父目录时间戳。这条是本次判定的关键依据。

### 删除链路本身是通的（零副作用实测）
```
DELETE /workflows/probe-not-exist → 200 {"ok":false,"error":"工作流不存在"}   # 鉴权/路由/store 全通
DELETE 不带 token                 → 401                                    # 鉴权闸门生效
OPTIONS 预检                      → 204 Allow-Methods: …PUT,PATCH,DELETE…   # 浏览器可发非简单请求
```

### 已排除的可能
- **不是点了「导出」**：`Downloads/` 无 `.yfwflow`。
- **不是 agent 删的**：9/14 起全部会话记录（`.yfw/projects/**/*.jsonl`）除本会话外无任何删除动作。
- **没有第三个 home**：`~/.yfw`（活跃）、`~/.yfworking`（旧版）之外无其他工作流根。

## 三、删除边界（隔离 home 逐项实测，不触碰真实数据）

| 删除面 | 修复前 | 代码位置 |
|---|---|---|
| 本体·目录形态 `<id>/` | ✅ 真删（含 versions/） | `server/workflow-store.mjs` `deleteWorkflow` |
| 本体·平铺形态 `<id>.yml/.yaml` | ❌ 返回「工作流不存在」、文件原地不动、**内核照旧发现它** | 内核 `kernel/workflow-dsl.mjs` 认平铺，而 store 只扫目录 |
| 信任清单 / agent 绑定 | ❌ 残留（`trusted:["spec-dev"]` 至今未清） | `deleteWorkflow` 不碰 `_bindings.json` |
| 工具池 `run_<slug>` | ✅ 删除后**同进程内立刻消失**（每次求值 + 盘面签名含根条目名列表） | `kernel/dyntools.mjs` |
| 系统提示词【可用工作流】 | ❌ **不重建**（启动时组装一次的快照） | `kernel/cli.mjs` `composeSystemPrompt` |
| 内置工作流·重启 | ❌ **dev 模式必定复活**（安装器无"用户已删除"记忆） | `server/workflow-install.mjs` |

**机制 A 的精确形态**：工具池会消失，提示词清单不会。于是 agent 一边说"我有 `run_spec_dev`"，
一边真调报错 —— 正是用户看到的"尝试使用但无输出"的分裂。

> 另注：spec-dev 本身"跑不出输出"与删除无关 —— 它在 9/17 有两次运行审计落盘，第一次跑完
> `impl_loop + end`，第二次只跑到 `converge`（**未执行 end 节点 ⇒ 自然无 outputs**）。
> 这是另一条独立线索，本次未处理。

## 四、为什么那一次点击没发出请求

前端删除入口（`src/components/workflows/WorkflowList.tsx:194`）：
```jsx
onClick={() => { if (window.confirm(`删除工作流「${meta.name || meta.id}」？`)) onDelete(meta.id) }}
```
`window.confirm` 在 Electron（`contextIsolation:true / sandbox:false`，未设 `disableDialogs`）下正常可用，
且全仓另有 5 处同款用法 —— 属既有惯例，非本处独有缺陷。

但它的失败模式是**静默的**：原生模态一旦未被应答（被忽略、显示在窗口之后、误按 Esc），
`confirm` 直接返回 false，**既不删也不提示**，用户看到的就是"点了没反应/删了还在"。
代码路径上无法复现"点了按钮却完全不发请求"，故最可能是确认框未被应答。

**已处置**（见 §五.5）：删除入口改为应用内 `WorkflowDeleteDialog`，未应答 = 对话框仍开着，
且提交失败会就地显示原因并保持打开。

## 五、已实施的修复（5 处）

1. **`server/workflow-store.mjs`**
   - 新增 `locateWorkflow()`：目录形态优先、回退平铺 `.yml/.yaml`（与内核扩展名判定同口径），
     `readWorkflowYml` / `deleteWorkflow` 收口到同一判定，消除"读得到却删不掉"的口径分裂。
   - `deleteWorkflow` 返回 `{ok,id,kind,bindingsPruned}`，并新增 `pruneBindings()`：
     尽力而为地摘除 `_bindings.json` 中该 id 的 `trusted` 与各 agent 绑定；
     无引用/文件缺失/JSON 损坏都不阻断本体删除，也不新建文件。
     **理由**：信任是运行前授权凭据，不该被"删掉后重建同名"继承。
2. **`server/workflow-install.mjs`**：用户删除记账（tombstone `.builtin-deleted.json`）。
   安装器见到「目标不存在 + 有记账」即跳过（`skippedByUser`）。三条刻意约束：
   只在目标不存在时生效（用户自建同名不被接管）／只在 id 确为内置时写入／`.` 前缀不进工作流列表。
   新增 `readDeletedBuiltins` / `markBuiltinDeleted` / `clearDeletedBuiltins`（恢复路径）。
3. **`server/workflow-routes.mjs` + `server/bridge.mjs`**：DELETE 成功后调用 `markBuiltinDeleted`
   （新增 `builtinSrcRoot` 注入）；启动日志出声说明"为何跳过安装"及恢复方法。
4. **`kernel/cli.mjs`**：提示词组装抽成 `refreshSystemPrompt()`，**每个用户轮入口重算工作流清单**
   （`currentVisibleWorkflows()` 不缓存）。`memory/knowledgeScope/skills` 仍沿用启动值，
   避免每轮图谱检索开销 —— 保持零行为变化。循环轮/子 Agent 轮不刷。
5. **前端删除入口去原生模态**（`src/components/workflows/`）：
   - 新增 `WorkflowDeleteDialog.tsx`：应用内对话框，**先说清影响面**（节点/边数、版本历史、
     该工作流当前被哪几个 Agent 绑定、是否在信任清单 —— 后两者正是本次新增的连带清理项，
     原本在界面上完全不可见）；`busy` 期间禁用按钮防重复提交；**失败就地显示原因且不关闭**
     （沿用 `AuthzDialog` 2026-09-12 的同一条教训：把失败丢到被遮罩挡住的顶部 notice，
     用户看不到就会反复点击）。
   - `WorkflowList.tsx`：卡片垃圾桶按钮改为 `onRequestDelete(meta)` 打开对话框，
     替换 `if (window.confirm(...)) onDelete(id)`；`onDelete` 契约升级为可返回 `{ok,error}`。
   - `WorkflowsPanel.tsx`：`remove` 回传 `{ok,error}`，并在**成功时也出一声**
     （原先静默，用户无从确认到底删没删）。

## 八、附：`spec-dev`「无输出」线索的调查结论

**结论：不是工作流定义缺陷，而是那次运行没跑完（被中断），叠加严重的上下文膨胀。**

对比两次运行审计（`~/.yfw/workflow-runs/spec-dev/*.jsonl`）：

| | 第一次 `00:38:28` | 第二次 `00:43:47` |
|---|---|---|
| 行数 | 12 | **8（中途停止）** |
| 节点序列 | start→specify→plan→tasks→implement→converge→implement→converge→implement→converge→**loop impl_loop→end** | start→specify→plan→tasks→implement→converge→implement→converge→**（止）** |
| 末条时间 | — | `01:41:54`（此后无记录） |

- **同一份工作流第一次跑到了 `end`** ⇒ 定义本身能产出最终输出，"配置有问题"这个假设不成立。
- 第二次缺的是**第 3 轮 implement + `impl_loop` + `end`**：`converge` 于 `01:41:54` 完成后再无记录，
  而应用仍在活动（日志 `01:45` 仍有 API 调用）⇒ 该运行是被中断的（应用重启/关闭会杀掉 `_wfhost`
  宿主进程，运行中断且**不写 end 节点**，用户侧即为"没有输出"）。

**为什么会被中断**：`implement` 节点单步耗时 **45 分钟**（`dur_ms=2735614`），用户在等不下去时才去动应用。而慢的根因是上下文膨胀：

```
[kernel] [compact] action=none reason=count-over-no-shrink msgs=309 est=76213 maxMessages=120
[kernel] msgs=496 ... body=415KB     ← 单次请求 415KB
```
三个会话（17895525 / 17896058 / 17896063）并发，压缩动作为 `none`（`count-over-no-shrink`）——
**该压缩却因"裁剪后不缩小"而未生效**，上下文堆到 500 条消息。

**另发现一处强异常**（值得独立跟进）：运行审计里 `out_hash` 显示
`specify:plan:tasks:converge` **四个不同节点的输出哈希完全一致**（均为 `9fbb5682`）。
已排除"空值哈希"（`""`/`{}`/`null`/`[]` 的 sha256 均不匹配），故它们**确实各有输出、且内容彼此相同** ——
这与各节点应产出的阶段成果不符，强烈提示这些节点返回了同一段内容（很可能是上下文超限下的同一回复）。
因输出正文**不落盘**（jsonl 只存哈希链 `sha256(JSON.stringify(r.output ?? r.error ?? ''))`），
无法从现有记录确认其内容。
